# Android 面试准备项目方案 v1.2

日期：2026-10-06。目标：12 年工作经验、外企 Senior，准备国内互联网公司 P7 左右岗位。本文是内容与实现设计，不包含网站或应用代码，也没有开启自动更新任务。

本次修订：默认按需阅读；进度管理与练习分别设置、默认关闭；跨端增加横向比较、选型和 App 实践案例；分类与功能采用可独立扩展的设计。原有七个技术分类与五个资深能力分类保留为初始目录，不作为数量上限。本文仅修改方案，不实施项目代码或后台任务。

专题入口：[Compose 由浅到深学习路径](./Compose-由浅到深学习路径.md)、[LeetCode 中国面经题单](./算法-LeetCodeCN面经题单.md)、[跨端技术对比与应用案例设计](./跨端技术对比与应用案例设计.md)。面经不限制 P7；算法累计最多 100 道，当前正式收录 9 道。

## 1. 项目定位

建议建设一个可持续维护的个人 Android 面试知识站，暂名 Android Interview Lab。

核心资产包括：有出处的面经索引、按原理组织的题目、可以分支的追问树、故障诊断实验、技术对比与案例、个人项目证据。网站首先是可选择性阅读和检索的知识库；进度管理与练习是用户自行开启的辅助功能，内容不依赖这些功能才能访问。

“P7 左右”在此仅作为准备强度的目标，各公司的级别、部门和职责不作机械换算。内容采用以下能力目标，这些是本方案的设计标准，并非公司的官方定级标准：

- 基础问题回答准确，能够说明版本和适用条件。
- 关键链路能够从业务 API 追到框架、运行时或操作系统机制。
- 能根据日志、trace、堆转储等证据定位问题，排除看似合理的错误解释。
- 能在性能、复杂度、交付成本和团队能力之间作出选择，并说明放弃了什么。
- 能解释自己的贡献、验证收益、推广方案及长期治理。

建议构建一个“T”形能力结构：Android、语言、并发、网络和算法全面补齐；另外选择两条与真实经历匹配的深度主线，如性能稳定性、客户端架构、跨端平台、音视频或 AI 客户端。暂以“性能稳定性 + 架构工程化”为占位，后续由经历决定。

### 2.1 可以据此支持的判断

- 多份样本反复出现：Java 并发与集合、Handler、生命周期、渲染与列表、内存、网络、项目细节和手写算法。
- Flutter、Kotlin 协程有具体提问样本，适合建设深入专题。
- Compose、KMP、AI 使用已有样本，但本轮不足以认定为国内 Android 岗的普遍高频，更不能直接外推到 P7。
- 故障场景、任务编排、缓存一致性、优化数据来源值得独立训练，不能只收集名词解释。

### 2.2 高频统计如何避免误导

未来以“独立候选人 × 公司/部门 × 一次招聘流程”为基础样本，轮次作为子记录。同一流程中重复问 Handler，基础出现率只计一次，追问深度另计。转载、合集、同文改写合并到原始来源，不增加频次。

原帖可信度、内容完整度、岗位匹配度、面试日期可信度分别标记。不能因为在牛客发布就自动标为可信，也不能因为有“P7”字样就按 P7 计入。

正式题目页面同时显示：

1. 近 12/24 个月该类岗位有效样本分母 N。
2. 提及该题的独立流程数 n、覆盖公司数、最近出现时间。
3. 校招、普通社招、明确资深社招分别展示，级别未知单列。
4. 样本偏差说明：公开发帖不代表真实招聘分布，n/N 不等于面试命中率。

初期只采用“跨样本重复 / 单例观察 / 待补样本 / 编辑补充”标签。例如，可把“至少 3 个独立流程且跨 2 家公司”设为编辑筛选门槛，但明确它是项目规则，不是统计学保证。个人学习优先级还要考虑岗位 JD、个人薄弱点及项目关联度，与频次分开展示。

01—07 在初始导航中组成“技术知识”，08—12 组成“资深能力”，十二项均有独立分类页。操作系统、工程化、安全等补充内容初始放在相应二级目录和跨分类标签；以后可按你的想法提升为一级分类。音视频、图形、车载、鸿蒙等可新增为专题或独立分类，现有内容通过关联复用。

内容采用“一级分类 → 二级专题 → 母题 → 深度分层/追问”的学习路径。每篇正文有一个主分类和稳定 ID，可以关联多个其他分类；多个目录入口指向同一正文，避免重复维护答案。一个能力专题可以汇集多个技术题、实验和项目案例，并增加自己的场景题。

五个能力分类的边界：技术决策回答“为什么选择”；复杂问题定位回答“如何找到根因”；性能治理回答“如何持续保持指标”；架构演进回答“系统如何分阶段改变”；项目成果与证据回答“你做了什么、如何证明”。各专题按需要关联这五类，不机械要求每道算法题都填满全部能力栏目。

检索必须支持一级/二级分类、公司/部门、面试日期、招聘类型/级别、真实面经或编辑补充、深度 L0—L5、技术版本与内容核验状态。掌握程度筛选只在进度功能开启时显示；其他筛选与搜索独立可用。学习优先级与面经频次分开展示。知识点建立中文、英文和缩写别名，例如“应用无响应 / ANR”。

交叉分类示例：“Compose 列表滑动卡顿”主分类为 05 Compose，同时关联 09 复杂问题定位、10 性能治理；涉及 View→Compose 的迁移取舍时关联 08 技术决策与 11 架构演进；用户真实案例及测量结果另存 12 的私有项目记录，通过 ID 关联。公开内容不得因此带出私有笔记或证据。

分类验收：从技术目录可以系统学习或跳读；从五个能力目录可以阅读场景与证据；同一主题能通过中文/英文别名和组合筛选找到；跨目录正文保持同一版本；启用进度时按内容稳定 ID 汇总，不重复计数。前置知识作为阅读提示，不设置必须完成上一章才能访问的限制。

6. 内存泄漏、OOM、图片内存与 GC。
7. Java 内存模型、锁、CAS 与线程池。
8. Kotlin 协程、结构化并发、取消与 Flow。
9. 生命周期、进程死亡和状态恢复。

11. 一次网络请求的全链路与弱网。

AI 先与项目主线一起做一个深度案例，再扩展题库，避免抢占基础诊断与代表项目梳理的时间。

## 4. 每道题的内容模型

题库的基本单位是“母题”。母题对应一种稳定机制或能力，原帖的不同问法映射到它，追问形成有条件的分支。不要把“Handler 原理”“Looper 原理”“MessageQueue 原理”做成互相矛盾的三篇重复长文。

### 4.1 单题页面固定结构

| 区域 | 应提供的内容 |
| --- | --- |
| 问题与适用范围 | 母题、原始问法、岗位/年限标签、学习前置知识 |
| 来源 | 原帖、日期、面试轮次、证据强度；“原帖问题”和“设计追问”清楚区分 |
| 60–90 秒回答 | 开场结论、机制主线、适用边界，一个具体例子 |
| 5 分钟展开 | 时序/数据流/状态图、关键对象职责、性能成本 |
| 原理深潜 | 源码入口、调用路径、关键不变量、线程与资源所有权 |
| 分支追问 | 正确回答后如何继续；答错时如何辨别概念误解；场景变化后如何反问 |

| 架构取舍 | 替代方案、适用规模、迁移方案、失败与回滚 |

| 版本与维护 | Android/API、JDK/ART、库/编译器版本、commit、最近校验时间、失效条件 |
| 可选学习区域 | 按开关分别展示进度标记、练习入口和已保存的练习记录；关闭时不显示，正文完整可读 |

### 4.2 深度分层

- L0：能定义并给出正确使用场景。
- L1：能解释执行过程，画出关键数据流和状态变化。
- L2：能通过源码/规范说明为什么成立，区分实现和约定。
- L3：能构造反例、注入故障、分析现场，验证或推翻假设。
- L4：能评估方案，说明收益、代价、边界、迁移与回滚。
- L5：能将一次解决方案变成可复用、可监测、可推广的长期机制。

建议通识题至少到 L2，核心专题到 L3，两条擅长主线和代表项目到 L4/L5。底层深度以“能解释观察结果并预测边界条件”为终点，不要求所有问题无限深入 CPU 电路，也不以记住函数名数量判定掌握。

开启练习后，可选择按准确性、机制解释、证据、取舍、表达五项 0–4 分自测；看过文章不自动计为掌握。0 分表示未知，1 分是提示后能答，2 分是独立回答基本正确，3 分是能解变式并给证据，4 分是能讲清边界与取舍。是否保存成绩、是否同步到进度由用户决定；未开启进度时不自动生成进度数据。分数只作学习参考，不预测 offer。

## 5. 六组追问树样例

以下追问是本方案的教学设计，除明确引用的起点外，不宣称某公司实际问过全部问题。这里展示内容深度和组织方式，后续单题正文再提供逐层答案、源码标注与实验结果。

### 5.1 Handler：从“切线程”深入到等待链

来源起点：小米原帖问到队列空闲时的挂起和唤醒；百度原帖问到 Looper 唤醒。

1. 发出消息之后，由哪个线程处理？Handler、Looper、MessageQueue 各负责什么？
2. 延迟消息如何决定何时可以执行？到期为何不意味着准时执行？
3. 为什么消息循环持续存在，界面还可以正常响应？什么时候是在等待，什么时候是在执行任务？
4. 新消息入队后，哪些条件要求唤醒等待线程？沿 Java、JNI、native Looper 看等待/唤醒路径。
5. 同步屏障的匹配规则是什么？异步消息与普通消息怎样被选择？不能把“异步消息”解释成另起一个线程。
6. 主线程堆栈落在 nativePollOnce，是否足以认定它导致 ANR？还缺什么时间点、输入窗口或其他线程证据？
7. 如果主线程在等同步 Binder，服务端线程又在等应用持有的锁，怎样建立等待图？
8. 设计线上消息耗时采样：如何控制开销、处理采样偏差、保护稳定性，并验证改动收益？

未来实验包：长任务、密集短任务、延迟消息、锁等待、Binder 等待的对照；结合 trace 与线程堆栈区分队列等待和任务阻塞。系统内部机制实验放在受控环境中，常规 App 不依赖隐藏 API。

内容验收：能解释具体时序，能指出单次堆栈的证据局限，并提出最低成本的下一步验证。

### 5.2 协程：从 suspend 到端到端取消

来源起点：腾讯 WXG 的协程实现与项目使用，滴滴的 A/B 并行、C 依赖 A/B 场景。

1. 协程与线程分别管理什么？suspend 是否意味着异步执行或切换到后台？
2. A/B 并行，C 依赖两者时怎样组织？如果 A 失败，B 是否还应继续？
3. coroutineScope 与 supervisorScope 改变的是哪种失败传播语义？如何结合业务选择？
4. 挂起时局部变量和下一步位置存在哪？Continuation、CPS、状态机分别解决什么？
5. 恢复是谁发起的？调度器如何影响恢复执行的位置？同步完成与真正挂起有何不同？
6. 页面退出、用户取消、超时、网络失败同时发生时，谁有权结束请求？怎样防止重复回调和泄漏？
7. 取消怎样传到 HTTP Call、订阅、数据库和 native 资源？哪些操作只能协作取消？
8. 设计统一请求组件：结构化并发、重试、错误模型、可观测性和测试怎样一起工作？

未来实验包：反编译最小挂起函数，保留编译器版本；取消与回调竞争；慢消费者下的 Flow；有/无监督关系的故障注入。编译原理依据可从 [Kotlin 协程规范](https://kotlinlang.org/spec/asynchronous-programming-with-coroutines.html)校验，库调度与取消语义另外绑定 kotlinx.coroutines 版本。

### 5.3 Compose：从重组进入编译器和性能证据

来源起点：[MetaApp 2026 年原帖](https://www.nowcoder.com/feed/main/detail/ffabbdfbab1a49c0a8a1c99b7d121535)询问重组原因与减少方式。

1. 状态变化后，哪些读取位置需要重新执行？Composition、Layout、Draw 是什么关系？
2. remember、rememberSaveable、ViewModel 分别解决哪一段生命周期问题？进程死亡后有什么区别？
3. 参数变化、身份变化与状态读取如何影响执行？列表 item 的 key 为什么重要？
4. Snapshot、Recomposer、Composer 各自负责什么？编译器生成的信息如何供 Runtime 使用？
5. 稳定性推断、跳过规则、lambda 捕获与 strong skipping 有什么联系？哪些说法依赖版本？
6. “重组次数减少”能否证明更流畅？如果瓶颈在布局、绘制、图片解码或 GPU 呢？
7. 怎样用可复现的 benchmark、trace 和编译器报告定位，而不是到处添加稳定性注解？
8. 将一个成熟 View 项目迁移到 Compose，如何选择试点、控制互操作成本、定义回归门槛和回滚条件？

官方将 Compose 描述为组合、布局、绘制等阶段，状态读取位置会影响后续工作，内容须按阶段解释，而不是把刷新全归因于重组。[Compose 阶段](https://developer.android.google.cn/develop/ui/compose/phases?hl=zh-cn)

例如 strong skipping 自 Kotlin 2.0.20 起默认启用，旧题库中关于不稳定参数与跳过的绝对结论需要版本校验。[Strong skipping 官方说明](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping)

系统复习另见 [Compose 由浅到深学习路径](./Compose-由浅到深学习路径.md)：开发基础→状态与副作用→布局输入动画→身份与刷新→Snapshot→Composer/SlotTable→编译器→性能测试→架构迁移。每阶段包含必修知识、追问、实验设计与验收产物。编译器生成协议，运行时建立和更新组合结构；经典 SlotTable 存储实现与新实现分开学习，版本依据见该文。

### 5.4 性能：从“优化了 18%”进入因果验证

来源起点：[滴滴 2025-10-26 原帖](https://www.nowcoder.com/feed/main/detail/864651bb82764281a3f0f5af7a9b6d0a)追问性能改善数字怎么得到。

1. 改善的是冷启动、首帧、可交互、卡顿还是内存？起止点怎么定义？
2. “降低 18%”的分母、基线、样本量、观察周期是什么？均值、P50、P95 哪个变好了？
3. 两组设备、版本、网络、账户状态、缓存状态是否可比？
4. 通过什么 trace 证明关键路径发生变化？是否只是把耗时推迟到用户下一次交互？
5. 降低延迟是否增加内存、网络、功耗或失败率？低端机是否退化？
6. 如何设计实验排除服务端提速、流量变化等因素？没有 A/B 条件时怎样说明证据限制？
7. 如何让团队后续迭代保持收益：预算、门禁、监控、负责人、豁免和回归处理？

未来实验包：原始数据、环境说明、trace、测量脚本说明、前后对比和副作用观察。可模拟项目，但必须与真实工作成果分开，不能生成虚构线上数据。

### 5.5 跨端：从调用原生进入协议和生命周期

入口：Flutter 三棵树与原生通信在百度/腾讯样本中出现；KMP 在猿辅导社招样本中出现。RN、JSBridge 的以下深入问题主要是编辑补充。

1. 为什么这段业务适合跨端？复用 UI、业务逻辑、模型还是基础能力？
2. UI 谁负责绘制？代码运行在哪？跨越哪些线程、进程、语言和内存边界？
3. 一次原生调用的序列化、调度、数据复制和返回路径是什么？
4. 高频事件会发生什么？批处理、背压、二进制协议或共享资源分别适合何种情形？
5. 页面或引擎销毁时，回调、监听、协程和 native 资源由谁回收？
6. 新老协议如何兼容？崩溃、超时、权限拒绝、重复调用如何映射成一致的错误模型？
7. WebView 的调用方如何验证？远程页面能否获得超出需要的能力？
8. 如何用同一业务、同一设备、同一质量门槛对比原生与跨端，并组织渐进迁移？

Flutter 内容按框架、引擎、嵌入层展开，渲染器行为绑定实际版本和平台。[Flutter 架构概览](https://docs.flutter.cn/resources/architectural-overview/)

RN 内容明确旧 Bridge 与新架构路径；KMP 的逻辑复用与 Compose Multiplatform 的 UI 复用分别讨论。不要把所有跨端方案都描述成“JSBridge”。

### 5.5.1 新增：跨端全景、对比、场景和 App 实践

独立设计见[跨端技术对比与应用案例设计](./跨端技术对比与应用案例设计.md)。阅读入口先提供横向总结，再进入各技术底层专题，不要求先读完所有框架。

- 对比对象：原生作为基线；WebView/H5 + JSBridge、Flutter、RN、KMP 共享逻辑、KMP + Compose Multiplatform 分开比较；Hippy、Lynx、Kuikly 作为国内工程化扩展。
- 对比维度：复用层次、运行与渲染方式、通信、平台能力、体验一致性、性能成本、包体启动、发布与动态化、团队能力、工程化、迁移和退出成本。
- 场景分析：运营活动页、复杂列表/交易链路、统一品牌 UI、平台交互密集业务、共享 SDK/业务规则、既有大型 App 渐进迁移。
- App 案例：记录公司、App、业务模块、平台、技术与分支版本、采用动机、收益与代价、披露日期、最近核验日和证据状态。公开披露与编辑推断分别显示，不能从 SDK 存在推断全站使用。
- 面试表达：先讲业务约束与复用目标，再解释两三种候选方案、验证指标、接入和回滚，最后引用范围准确的行业案例。

技术团队实践是“采用情况”的证据，与候选人面经分开存储；不因某 App 采用某框架就计为面试高频。

### 5.6 AI：从聊天界面进入系统约束

来源起点：腾讯 CSIG 样本问到 AI 使用与开发流程；字节飞书样本涉及候选人的智能体项目。以下深度为本方案按目标岗位补充。

1. 用 AI 辅助开发时，如何拆任务、提供上下文、检查代码、验证效果和收敛失败？
2. 设计 Android AI 助手，哪些工作在端上，哪些在服务端？如何衡量首 token 时间、整体耗时与失败率？
3. 流式数据如何解析、缓冲并驱动 Compose，避免每个 token 都触发昂贵工作？
4. 断网、重连、页面退出、进程被杀后，会话如何恢复？重复消息和重复工具执行如何避免？
5. RAG 的分块、召回、重排、引用和权限过滤分别解决什么？如何判断回答忠于资料？
6. 工具调用如何限制权限，如何处理提示注入、超时、幂等、审计和用户确认？
7. 如果端侧推理，如何估计权重、KV cache、峰值内存、带宽、温升和功耗？量化带来哪些质量损失？
8. 如果改模型后平均质量提高但关键任务退化，怎样通过固定评测集、分场景指标、灰度和回滚发现问题？

普通 Android 资深岗位建议把重点放在可靠的 AI 工程与客户端集成。模型训练、优化器、分布式训练作为 AI 深度岗位选修，不默认要求全部掌握。

## 6. 算法内容：面经对应的力扣中国原题，最多 100 道

按用户最新要求，算法以精简原题目录交付：**题号、中文题名、LeetCode 中国链接、难度、分类、面经出处与匹配依据**。本轮不写题解代码，不为覆盖所有模式而加入无面经依据的通用题单，也不要求刷满 100 道。

当前正式收录 9 道：206、92、20、3、94、109、213、68、2520。对应关系、公司与日期见[独立算法题单](./算法-LeetCodeCN面经题单.md)。编号明确或唯一题名与“按题意映射编号”分开标记；不把该小样本称为全行业高频排名。

模糊简称、题面变式、仅口述概念的条目放候选区。例如螺旋数组、字符串压缩、三元组小于 target，不能直接认定为某道标准原题。新增面经先补证据，同题合并，活动题单总数始终不超过 100。

工程场景题仍可放在并发、架构和复杂问题定位分类，例如 A/B→C 依赖、单飞 token 刷新、取消安全的回调封装；它们不包装为力扣原题，不占这个题单名额。

## 7. 为你单独建设“个人项目证据库”

建议优先整理三个真实案例：一次性能或稳定性问题、一次架构/平台演进、一次跨团队或高不确定性交付。如缺少某类经历，保留缺口，不替换成虚构项目。

每个案例形成一份 2–4 页的主文档，并提供 90 秒、5 分钟、20 分钟三种讲述长度：

1. 背景和约束：用户/设备/系统范围、遗留系统、资源和时间限制。
2. 问题定义：现象、影响、业务目标、为什么值得解决。
3. 基线和证据：数据口径、trace、故障记录、用户反馈；敏感数据脱敏。
4. 个人职责：你决定了什么、实现了什么、别人完成了什么。
5. 备选方案：至少两个替代方案，为什么没有采用。
6. 技术细节：一张链路图、一段关键机制、一个最难问题。
7. 推进过程：如何协调产品、服务端、QA 或其他客户端团队。
8. 验证和上线：实验条件、灰度、观测、风险控制、回滚。
9. 结果：性能/可靠性/效率/成本变化；没有可信数字时明确使用定性证据。
10. 反思：未解决的问题、收益边界、今天重新做会改什么。

面试官追问库至少包含：为什么由你来做；如果没有你会怎样；为何不采用更简单的方案；你如何说服反对者；指标是否归因于你的改动；如果规模变大或团队减半会怎样；如何证明方案被团队持续采用。

外企经历的准备重点是把质量标准、跨地区协作、设计决策与长期维护成果转换成具体案例，再练习中文口头表达。不要只做职级名称的翻译，也不要假设外企经验天然适配或不适配国内团队。

如选择系统备考，可参考投入比例：项目与系统设计 30%，原理与性能深挖 30%，算法/工程编码 15%，Compose/跨端/AI 岗位专题 15%，模拟面试与表达 10%；选择性学习时无需遵守该比例。它是可选建议，不是市场统计或默认任务。

## 8. 阅读形式与页面设计

推荐 Markdown 为内容源、文档型网站为主要入口。**默认首页是知识目录与搜索，不是学习打卡或任务面板。** 所有内容允许按分类、关键词、公司或场景直接阅读。

常驻入口：知识目录与搜索、专题路线、技术对比与案例、面经与岗位、收藏/笔记、设置。个人项目证据可直接维护，不要求开启练习。

普通阅读的题目页：目录 → 核心回答 → 调用链 → 追问解析 → 故障证据 → 相关内容。正文中的追问、实验设计和答案始终可读；“练习功能”特指交互答题、计时、评分、模拟面试等。

### 8.1 可选进度与练习

| 设置 | 默认值 | 开启后 | 关闭后 |
| --- | --- | --- | --- |
| 进度管理 | 关闭 | 手动标记掌握程度、选择跟踪范围、查看个人进度 | 隐藏进度面板与相关筛选，停止新增进度记录 |
| 练习功能 | 关闭 | 口答/答题、自测、计时、模拟面试入口 | 隐藏交互训练入口，保留完整学习正文 |
| 保存练习记录 | 关闭；仅练习开启时可用 | 用户选择保存的回答、评分和复盘进入私有记录 | 可以临时练习，结束后不留存会话；普通笔记不受影响 |
| 学习计划与复习提醒 | 关闭；需要进度管理 | 用户选定范围和节奏后才生成计划或提醒 | 停止提醒与排期，不制造逾期任务 |
| AI 模拟面试 | 关闭；需要练习功能 | 用户显式发起后才调用 AI | 不加载训练服务、不发起模型调用 |

四种组合必须成立：两项都关闭＝自由阅读；仅进度开启＝手工标记而不做题；仅练习开启＝临时或自选保存的练习、不累计掌握进度；两项都开启＝可以关联结果，但仍由用户选择是否用成绩更新掌握程度。

进度范围可以是指定分类、单篇内容或自选清单。例如只选 Compose 和网络，就只展示该范围的进度，不把全站未读内容算作欠缺。内容因交叉分类出现多次只计一次。完成状态由显式操作产生，不通过停留时长或滚动到底自动判定。

自选清单保存成员和内容版本；后续新增分类/文章进入“可加入内容”，不静默扩大既有计划分母。已有内容更新时显示变化提示，不直接撤销用户完成状态；重新验证与重置由用户决定。

关闭功能时保留此前明确保存的私有数据，便于以后恢复，但停止相关写入和任务；清空历史是独立动作，先展示范围再确认。再次开启不补算关闭期间的阅读行为，不自动恢复之前的提醒，提醒需单独开启。收藏、笔记和手动导出始终独立。

需要支持手机阅读、全文搜索、深链接、深色模式、折叠源码、图表、收藏、笔记及 Markdown 导出。内容更新列表可直接查看；主动通知另行设置，默认关闭。全局关系图可选，避免图大而难用。

同一内容可导出 Markdown/PDF 或复习卡片；PDF 是阶段快照，持续更新仍以 Markdown/网站版本为准。

## 9. 技术实现思路

### 9.1 首版推荐：内容仓库 + VitePress + 少量交互

[VitePress](https://vitepress.dev/zh/guide/what-is-vitepress)以 Markdown 文档为基础，可生成静态站点并扩展 Vue 组件，适合本项目以内容为中心、交互逐步增加的形态。它提供[本地搜索](https://vitepress.dev/zh/reference/default-theme-search)，中文检索效果要用真实题目验收，必要时加入分词、别名和专用索引。

- 内容：Markdown + YAML frontmatter，Git 保存版本和审阅差异。
- 元数据：结构化 JSON/YAML；用 schema 验证必填字段、枚举、引用和版本范围。
- 前端：VitePress + TypeScript；正文、来源和筛选是基础能力，评分、进度、练习按独立功能模块设计。
- 图：Mermaid 维护时序、状态与依赖图，复杂性能图来自真实实验产物。
- 搜索：首版关键词、中文别名、标签和源码符号检索；语义检索放后续。
- 个人数据：收藏/笔记、进度、练习记录分别存储；可选模块关闭时不初始化其记录流程。单设备阶段考虑 IndexedDB，提供导出/导入和备份；它不天然具备跨设备同步。
- 内容构建：校验完成后生成页面、题目索引、公司筛选视图和变更日志。
- 托管：选择用户可稳定访问的静态托管；部署渠道在实现阶段确定，本轮不发布网站。

公共学习资料与个人项目、模拟面试记录要分开构建。静态页面隐藏入口并不等于鉴权，个人材料不能进入公共构建产物或客户端搜索索引。

### 9.2 数据模型

| 实体 | 关键字段 |
| --- | --- |
| Category | 稳定 ID、名称、父分类 ID、导航组、显示顺序、别名、状态；编号仅用于展示 |
| Content | 稳定 ID、类型、标题、主分类 ID、关联分类 ID、标签、可见性、schema 版本、内容版本、URL 别名 |
| Source | 来源 ID、原帖 URL、平台、作者公开标识、发布时间、更新时间、访问时间、可访问状态、来源类别 |
| InterviewSession | 流程 ID、公司/部门、岗位、招聘类型、年限/级别及可信度、面试日期和日期精度、轮次 |
| Question | 稳定 ID、母题、主题、别名、前置题、学习深度、内容版本、审核状态 |
| Occurrence | 流程/轮次、母题 ID、原问题摘要、明确追问、原帖定位、是否同源重复 |
| FollowUp | 前题/后题、触发条件、预期要点、错误诊断、终止条件、真实来源或编辑生成标记 |
| Claim/Evidence | 技术结论、源码/规范引用、适用版本、实验 ID、核验日期、争议状态 |
| Lab | 环境、步骤、预期、实际观察、产物路径、复现状态、性能成本 |
| Practice | 题目与内容版本、回答、五项评分、错误标签、复习日期、评分者 |
| ProjectCase | 私有项目素材、个人贡献、指标口径、证明材料、可公开范围 |
| TechnologyProfile / Comparison | 技术 ID、版本/平台边界、对比维度、结论、依据、适用场景 |
| AdoptionCase | 公司/App/模块、技术 ID、平台、采用状态、披露日期、核验日期、来源、未知项 |
| UserPreferences | 进度、练习、留存、提醒、AI 的独立设置与设置版本 |
| LearningSelection / Progress | 自选范围与成员快照、内容 ID、手工状态、对应内容版本；仅开启时产生 |

关键约束：面经“提到了问题”和技术“结论有依据”分开建模；来源更新不直接覆盖答案；答案升级不抹除旧练习记录。

Content 是所有内容的公共外壳；Question、Comparison、AdoptionCase 等保存各自专有字段。Practice 和 Progress 属于可选私有数据，任何公共内容都不要求必须关联它们才能发布。

### 9.3 自动校验与质量门槛

- 每条正式题必须有稳定 ID、来源类型、版本范围、答案状态和校验日期。
- 原帖真题必须关联 Occurrence；编辑自拟题也允许发布，但必须明确标注。
- 核心结论与源码/规范引用对应；只放一串无对应关系的外链不能通过内容审核。
- 检查链接、孤立追问、缺失前置题、重复内容、日期冲突和更新影响范围。
- 代码示例进入对应语言/版本的验证流程；本轮仅设计，后续有代码才执行。
- 实验区分计划、已复现、失败、待重新验证，不能将预期现象写成已测结果。

### 9.4 后续何时引入服务端

需要跨设备同步、账号、在线录音或 AI 模拟面试时，再加认证 API 与数据库。单用户可从轻量存储起步；多用户或明确同步需求再选 PostgreSQL 等方案。无需在首版同时部署复杂 CMS、向量数据库和多个服务。

AI 服务通过后端访问模型，不在静态网页中放服务密钥。检索先按主题、版本和权限过滤，再结合关键词/向量召回，返回带题目版本的证据块；没有可靠依据时显示“不足以判断”。

### 9.5 扩展设计：分类、内容和功能分别变化

采用单一文档站内的模块化结构，不为扩展性先建设微服务或复杂插件平台。以下均为设计约束，本轮不编写实现。

| 层次 | 负责什么 | 独立变化方式 |
| --- | --- | --- |
| 内容层 | Markdown 正文、来源、技术结论与案例 | 修改内容即可更新正文；不依赖学习状态 |
| 分类与索引层 | 分类树、标签、导航、关联、搜索索引 | 从统一分类注册表生成导航和筛选，不在每个页面重复写分类枚举 |
| 阅读层 | 目录、详情页、比较表、搜索、导出 | 使用统一内容接口；无练习模块时完整工作 |
| 可选功能层 | 进度、练习、复习、AI、以后新增功能 | 通过明确入口、设置和数据接口接入，不改写正文 |
| 数据与外部服务层 | 私有存储、导入导出、后续同步与模型服务 | 经适配接口访问，替换存储或服务不改变内容 ID |

分类注册信息包括稳定 ID、名称、父级、导航组、顺序、别名和是否展示。分类 ID 不包含可变显示编号；内容 URL 不依赖分类层级。调整顺序、中文名称或父级不改变内容 ID；旧分类入口保留别名或重定向。分类隐藏或归档不删除其内容、笔记或练习记录。

新增分类的设计流程：填写分类信息 → 新增或关联内容 → 校验唯一 ID、父级存在、无循环及引用有效 → 生成目录、筛选、面包屑和索引 → 预览后发布。此类操作应只改分类/内容数据，不要求修改进度、算法、AI 或各页面组件。

新内容类型先复用通用文章模板；确需比较表、案例卡等特殊展示时，只新增该类型的 schema 和渲染器。未知可选字段应可忽略，未知类型提供安全的通用阅读降级。新增字段优先可选并设默认值；破坏性变化才引入 schema 升级及迁移，保留原数据备份与回退路径。

功能模块声明自己的 ID、入口、设置、依赖、数据命名空间和接口版本。开关既控制界面，也控制初始化、后台任务和数据写入；仅隐藏按钮不算关闭。可选模块发生错误时应隔离到该模块，正文和搜索继续可用。第一版不提供任意外部脚本插件加载。

新增功能不复制正文，读取内容 ID 与版本即可；进度、练习和收藏各自拥有数据，禁止互相直接修改存储。需要关联时使用明确的应用接口，用户设置决定是否传播结果。公共构建和私有数据继续保持隔离，不能因增加新的内容类型而把私人材料纳入搜索索引。

### 9.6 扩展与开关的验收场景

1. 新增“鸿蒙”一级分类或将已有专题提升为一级分类，旧链接、收藏和内容引用仍有效；现有学习清单不自动扩张。
2. 将同一篇 KMP 文章关联到跨端、技术决策和架构演进，正文仍只有一份；进度开启时只计一次。
3. 重命名或移动分类，原文章和保存记录保持同一 ID；归档分类也不删除数据。
4. 进度与练习四种开关组合均可阅读全部正文；关闭时停止对应记录、提醒或调用。
5. 新增“跨端采用案例”类型，只增加本类型元数据与展示；搜索与导出可使用公共字段，旧文章无需补新必填字段。
6. 可选练习服务异常或私有记录迁移失败，目录、正文和搜索仍可用；既有数据可恢复。

这些是未来实现的验收条件，当前没有执行功能测试或构建应用。

## 10. 内容更新机制

建议采用“发现 → 候选池 → 去重与分类 → 技术核验 → 发布”的流程，自动化发现与整理，关键结论经过核验后再进入正式答案。

1. 发现：宽关键词检索与公司/年份/高级资深定向补充结合，不以 P7 或完整精确组合为硬过滤条件；公开页面、RSS 或平台允许的接口优先。登录后内容由用户在有权访问时提供链接或摘录，不把绕过登录作为依赖。
2. 入库：记录原文链接、日期和最小必要摘要；不镜像搬运完整面经。
3. 去重：URL 归一化、文本指纹、相似候选聚类，再结合作者、题序和流程检查；不能仅因题目相同就合并不同候选人的真实面试。
4. 过滤：排除非目标公司、非 Android 相关岗位、无法核验的转载、营销合集和日期错配；被排除条目保留理由。
5. 映射：映射到既有母题，新增问法或追问边，不为每个相似帖子创建一篇答案。
6. 校验：用官方文档、源码及可复现实验校验技术内容。面经来源仍限定中文网络和国内公司；官方技术资料属于答案校验层，不计面经统计。
7. 发布：生成内容差异和版本变化；仅在用户开启进度/复习功能并选择范围后，才派生待复习提示。允许回退到上一版。

建议节奏：每周检索近期面经；每周整理一次有效变化；Compose、Kotlin、RN、Flutter、AI 等快速变化主题每月检查版本，遇到明确行为变化立即开复核项；稳定基础专题每季度复核。距离面试两周时，可将目标公司的检索提高到每 2–3 天一次。

变化分类包括“新增面经证据”“补充追问”“答案纠错”“版本行为变化”“来源失效”。仅发现标题更新或重复转载时不打扰学习计划。

来源失效时保留 URL、日期和合法保留的摘要，标注无法重新核验并降低证据状态。旧答案可能因版本仍然正确，不能一律删除；呈现当前版和历史版的适用条件。

以上是拟议机制，没有在本轮建立后台任务、订阅或定时器，也不承诺脉脉/看准受限内容能全量及时采集。

## 11. AI 模拟面试设计

模拟面试属于可选练习模块，默认关闭。固定追问树及解析作为普通内容始终可读；开启后才提供交互训练。AI 版再由用户单独开启、显式发起，价值是按回答选择分支；仅在留存开启时保存会话，不自动给自由阅读用户安排面试或评分。

一次模拟以 45–60 分钟为例：开场与项目简述 → 一个机制深挖 → 一个故障/系统设计场景 → 编码或变式 → 复盘。专项场次可缩短为 15 分钟。

面试官策略：

- 回答只有名词，要求说明执行过程或画图。
- 原理准确，改变版本、线程、生命周期或负载条件。
- 给出优化结论，要求基线、指标和验证证据。
- 给出方案，要求比较替代方案、失败模式和回滚。
- 不确定时允许明确说明，并考察如何验证；不会把合理承认边界当作胡乱扣分理由。

评分必须引用回答中的具体表述和题库依据。事实错误、证据不足、表达不清分别标记；多种合理方案按约束评价。模型低置信度结论进入待核验，不自动判定为错误。

系统自身需要一个人工标注的小型评测集，覆盖正确答案、部分正确、常见错误、合理替代方案和版本冲突，检验引用是否支持评分、是否过度追问、是否泄露答案。评分器改变时保留版本，避免新旧分数不可比。

## 12. 分阶段建设与学习安排

### 阶段 A：内容试点

交付 15 个完整母题、3 个个人案例框架、Compose 独立学习路径、面经对应的力扣原题索引、种子面经索引；先验证内容能否支持连续追问及阅读体验。算法索引本轮已有首批 9 道。

验收：核心结论可追溯，追问分支不是重复改写，至少包含错误反例、实验设计和工程取舍。当前文档只是设计稿，尚未完成这些题目的正式正文。

### 阶段 B：可用知识站

扩展到约 60 个核心母题、8–12 个故障/系统设计案例，算法随有效面经增量扩充且不超过 100 道；加入全文搜索、折叠深度、跨端比较与案例、来源与版本页。进度和练习可分批建设并默认关闭，不作为纯阅读版本的使用前提。完整题目逐批交付，避免一次生成大批浅答案。

验收：每道题的内容核验状态明确；没有证据的内容不冒充近期真题；可导出和恢复已保存的个人数据；私有材料不会进入公共包；新增分类与关闭可选功能不破坏阅读和搜索。

### 阶段 C：持续维护与模拟面试

补足目标部门和资深社招样本，建立增量发现与发布流程，再加入 AI 追问、跨设备同步、岗位差距分析。长期可扩展到 150–200 个母题，但数量不作为首要目标。

### 建议个人学习节奏

以下仅为选择系统备考时可参考的模板，不是默认计划，也不要求启用进度和练习。选择性学习可直接跳到所需专题；目录中的前置关系只作建议。准备周期尚未确定，模板暂按每周 12–15 小时、10 周设计，不保证完成全部深度内容。

| 周期 | 重点 | 可检查产物 |
| --- | --- | --- |
| 第 1 周 | 能力诊断、目标 JD、项目盘点，开始算法 | 薄弱项清单、3 个真实案例提纲、两条深度主线 |
| 第 2–3 周 | Framework、OS、Java/Kotlin 并发 | 核心链路图、口答录音、原理/反例笔记 |
| 第 4–5 周 | 性能稳定性、网络和数据一致性 | 两个诊断案例、一个完整实验、项目指标口径 |
| 第 6–7 周 | 系统设计、工程化、Compose/跨端 | 两份架构设计与取舍记录、迁移方案 |
| 第 8 周 | AI 客户端或岗位专项 | 一份端云设计与评价方案，明确实际完成与仅设计部分 |
| 第 9–10 周 | 公司/部门定向复盘、模拟面试 | 真实投递岗位清单、模拟反馈、查缺补漏 |

算法从第一周持续练习，项目证据也从第一周开始补充。学习日可采用原理 45 分钟、算法 30 分钟、口答/项目 20 分钟；周末集中做实验和一轮模拟，具体按时间调整。

准备完成的判断：核心母题能独立说清，变更条件后能推理；两条主线有源码与诊断证据；三个真实案例能展开到个人贡献和指标；算法能处理边界与复杂度；至少几轮模拟暴露的问题已复练。阅读篇数和收藏数量不作为完成标准。

## 13. 本轮建议确定的第一版范围

采用 Markdown 内容源与可扩展的文档网站；默认自由阅读；围绕 15 个深度专题建立内容质量标准，增加跨端比较与应用案例；面经证据、官方原理和自拟追问分别标记。分类由数据驱动、内容保持稳定 ID，进度、练习和 AI 按用户开关独立接入。本轮只修改方案文档，具体功能建设另行启动。

后续个性化最有价值的信息是：你当前业务领域、真实使用的技术栈、最强的两个项目、希望投递的岗位/部门、预计面试时间和每周可投入时间。这些信息影响主线和顺序，不影响本方案先行建设。
