## 1. 从“我会哪些技术”走到“我能处理什么问题”

资深岗位的能力不能只由 API 数量表达。以一个教学任务为例：交易页在弱网下重复提交，首屏也慢，团队计划同时改架构。知道协程、MVVM 和缓存只是起点；需要决定先处理哪个风险、怎么证明原因、如何协调上线，以及怎样避免改造引入新问题。

本文是用于国内资深岗位准备的编辑框架，不是任何公司的 P7 官方标准，也不把所有岗位要求视为一致。你已有较长工作经验，复习更适合围绕真实项目补齐解释与证据，而不是重新收集名词。

## 2. 基础机制决定诊断能走多远

重复提交先问结果是否真的失败，还是服务已提交但响应丢失；首屏慢先问等待、计算还是加载资源。然后才进入 [网络可靠性](#/article/network-reliability)、[线程与锁](#/article/java-threads)、[启动路径](#/article/startup-governance)。

```text
现象：按钮超时后重试产生两单
机制假设：超时只终止等待，未撤销服务端事务
需要证据：同一业务操作的请求 ID、服务提交与响应时间
修复方向：稳定幂等键 + 状态查询，而非只缩短超时
```

这是原创案例推演，不是线上事实。基础知识的深度体现为能解释这个因果链，并指出反例：若两次操作 ID 本来就不同，还要查 UI 是否错误创建了两个业务意图。

## 3. 决策能力体现为知道何时不扩大改造

如果重复订单风险已明确，先止损、补协议并验证，比同时重写整页更容易控制变量。架构迁移可以继续，但不应让紧急修复依赖一个长期工程全部结束。

评审时列出候选：禁用重复点击、客户端排队、服务端幂等、结果恢复。禁用按钮改善交互，却挡不住进程重启或网络重试；服务端幂等覆盖业务重复，但需要存储和并发约束。能够给出每层措施的边界，比说“做了防抖”更完整。决策记录详见 [技术决策第 4 节](#/article/technology-decisions?section=4)。

## 4. 治理能力把一次修复变成持续约束

修复合入以后，新入口可能绕过旧封装，问题重新出现。持续治理需要把稳定操作 ID、错误语义和监控分母变成团队共同契约，并通过测试与发布检查保护。

|一次性交付|持续能力|
|---|---|
|修某次重复请求|统一操作身份与重试契约|
|优化一个首屏|定义场景、预算、基准与回归处理|
|拆一个大类|明确所有权、依赖方向与迁移出口|
|补一条监控|确保口径、采样与行动责任清楚|

不是所有问题都需要平台化。使用者少、变化快时，一个小的公共约定和契约测试可能足够；平台本身也会带来维护负担。治理应减少重复故障，而不是增加流程数量。监控方法可参考 [Google SRE 的监控原则](https://sre.google/sre-book/monitoring-distributed-systems/)，客户端场景仍需自行定义指标。

## 5. 影响力要落实到可辨认的个人贡献

一个跨客户端与服务端的修复通常由多人完成。准备材料时分清：自己提出了什么假设、取得哪些证据、推动哪个接口决策、实现与验证哪些部分，其他同事负责什么。不要把团队全量结果改写成个人独立完成。

若没有线上对照数据，可以诚实提供故障复现、关键 trace、契约测试和灰度记录；它们证明不同范围的工作，不能包装成全站收益。对失败方案也应说清淘汰原因，而不是抹去所有试错。证据组织见 [项目证据](#/article/project-evidence)。

## 6. 用能力缺口选择复习顺序

拿一个真实项目写一页：现象、约束、机制、备选、决定、验证、未解决问题。写到哪一步只能用口号，就回到对应文章补机制；如果机制清楚却没有数据，下一步是找可公开/可脱敏证据，而不是继续背更多概念。

学习与练习开关保持可选。可以先攻最薄弱的等待链、离线一致性或 AI 评估，再回到项目复盘串联。目标是能从简单问题逐层解释并承认边界，不是把教学案例当作自己的工作经历。

## 面试提炼

1. 一个资深项目说明怎样从技术名词转成因果链？（第 1、2 节）
2. 为什么紧急修复不宜绑在全量架构改造上？（第 3 节）
3. 一次优化怎样变成持续治理，又怎样避免过度平台化？（第 4 节）
4. 如何区分团队结果与个人决策贡献？（第 5 节）
5. 怎样依据真实项目缺口选择复习内容？（第 6 节）
