## 1. OOM 的失败资源

OOM 表示某类内存／资源申请无法满足，必须结合异常细节与运行时看是哪一类。Java heap、类元数据、直接内存、native 资源、线程创建等限制不相同；Android 系统低内存终止进程也可能没有 Java OutOfMemoryError。

最后触发失败的分配者不一定是长期占用的根因。一张图片申请失败，可能只是撞上此前其他模块占用造成的余量不足。先保留原始错误，不能一上来就写“图片泄漏”。

## 2. 泄漏与回收的关系

泄漏是一类资源保留不符合业务生命周期的原因，可能最终耗尽；峰值、合理存活集过大或资源限制也能造成 OOM。GC 只能按运行时规则回收可回收对象，不知道强可达对象是否业务上已经无用。

所以 OOM 不证明有泄漏，发现泄漏也不自动证明它造成这次 OOM。需要把保留规模、增长速率、时间线和实际资源上限关联起来。

## 3. 现场信息与诊断入口

收集应用与依赖版本、系统／设备档位、前后台、业务路径、异常资源类型、分配申请大小、进程与各资源曲线、线程数和并发任务量。按场景决定 Java heap dump、native 分配、图形或线程证据。

不要等接近耗尽时才执行无限制的大型诊断，dump 本身有成本，线上应采用适当采样和脱敏。环境不允许拿完整 dump 时保留间接证据并明确结论置信度。

## 4. 增长曲线与峰值

重复相同进入／退出路径后，回收后的基线持续上移，提示累积存活；高频锯齿但回收后基线稳定，提示分配压力；某并发动作触发短时尖峰，提示重叠资源预算。正常缓存也可能先增长后稳定，需要对照容量策略。

曲线提供假设而非结论。固定数据量、操作次数与等待条件，再查具体对象或资源。调试器和 profiler 会改变时序，应该与低干扰的线上指标交叉核对。

## 5. 根路径和支配树

从不该存活的实例反查到根的强引用路径，确定保留者与业务生命周期。最短路径帮助找到一条连接，但并不保证唯一。支配关系表示到某对象的所有根路径都经过某节点；retained size 可帮助估计移除保留者的潜在影响，不能把所有大对象的 retained size 简单相加。

例如 static listener 列表 → 回调 → binding → View 树 → Activity，真正的修复可能是注册与注销配对。给某个 View 置 null 后若还有另一条路径，页面仍不会释放。

## 6. LeakCanary 的证据边界

它在对象按生命周期应可回收时通过弱引用等机制观察保留，经过相应检测流程后分析堆与根路径，帮助定位持续保留。检测到的是需要解释的可疑对象，不是对所有线上 OOM 的自动因果证明。

要结合等待条件、业务允许的暂时保留、实例数量、保留大小与故障资源。不能把一次 GC 后仍未立即消失当作完整证明，也不能因为报告有某 SDK 类名就断言全部责任在 SDK。

## 7. native 与图形内存

查 native malloc、JNI 全局引用、映射、线程栈、图形缓冲、图片与音视频／模型引擎资源。先用场景隔离和模块开关缩小范围，再用对应分配工具与符号查申请栈；对象 heap dump 无法解释全部驱动或 native 使用。

进程 PSS 增长也可能涉及共享页变化或缓存驻留，不能只凭曲线斜率定性泄漏。需要同负载、同口径和资源生命周期对照。

## 8. 线程资源耗尽

每个线程消耗栈、内核及运行时结构，还受系统与进程限制。创建失败时堆可能并未到上限；盲目给应用增大堆可能挤压其他余量。观察线程数、创建来源、终止情况与线程池扩容策略。

无界任务队列则可能主要保留任务及其捕获对象，即使工作线程数量固定仍会耗尽堆。分别治理执行并发与等待队列，不能只把线程池换成另一个默认配置。

## 9. 修复策略与代价

大堆可能改变可用资源但不消除持续增长，并带来其他成本；弱引用会改变可达性却不替你取消工作或关闭资源；GC 无法回收仍然强可达的对象。应按根因修复所有权、注销、显式释放、有界缓存、解码尺寸、并发预算或模型重叠加载。

内存不足时的降级也应可解释，例如停止非关键预取、降低缓存或暂不加载大模型，而不是让用户反复触发崩溃循环。

## 10. 修复闭环与回归

重复同一生命周期和压力路径，验证目标实例可回收、增长斜率消失或峰值落入预算，同时看是否增加重加载、卡顿、流量和耗电。记录修复前后根路径、资源归属、设备组、操作脚本与长期指标。

若只有某组设备的间接证据，明确是高置信假设而不是“所有 OOM 已解决”。本文给出排查方法，没有执行用户设备的内存耗尽或泄漏实验。
