## 1. 先读失败申请，而不是先寻找泄漏

相册打开时抛出 OutOfMemoryError。它说明某项内存相关申请无法满足，却没有直接告诉我们“某个 Activity 泄漏了”。可能是托管堆接近限制、native 资源压力、线程创建失败，或一个瞬时大对象超过可用空间。

先保存完整异常、失败申请大小、设备与 ABI、系统版本、进入路径和并发任务。系统低内存终止进程又是另一条路径，可能根本没有 Java OOM；区分方法见 [ART 第 8 节](#/article/memory-art?section=8)。没有这些分类就马上改弱引用，容易修错对象。

## 2. 用一张图片算出最小压力

设图片 4000×3000，理想像素格式每像素 4 字节：

```text
4000 × 3000 × 4 = 48,000,000 bytes ≈ 45.8 MiB
若原图、变换输出同时存活：仅两份像素约 91.6 MiB
```

这是算术下界示意，未包含行对齐、解码临时区、纹理与其他对象。压缩文件只有几 MB 并不改变解码后的像素数量。若三张同时解码，还要把生命周期重叠算进去；不能只看最终缓存里留下几张。

因此先按展示尺寸采样、减少无用中间副本并限制解码并发。Bitmap 的存储位置与复用约束依版本/配置，参见 [Bitmap 内存](https://developer.android.com/topic/performance/graphics/manage-memory)，不能统一说都在某一个堆。

## 3. 三种曲线对应三种假设

```text
A 每轮退出后的基线：40 → 55 → 70 → 85    持续保留的嫌疑
B 每轮基线：40 → 40 → 40；进入峰值 150   瞬时重叠的嫌疑
C 基线稳定，但频繁锯齿与分配很高          分配抖动的嫌疑
```

数值仅为教学示意，不是测量结果。A 要查哪些对象与资源没有释放；B 要查同时存活的任务和缓冲；C 要查重复创建与回收开销。三者可能共存，也不能只凭形状确认根因，需要对象、分配和时间线证据。

只在退出后拍一张 heap dump 很容易漏掉 B；只盯峰值则可能看不出 A 缓慢累积。采样时点必须覆盖触发前、峰值与恢复后。

## 4. 从最大对象走到真正所有者

Heap dump 中 shallow size 是对象本身占用，retained size 表达在相关引用图分析下由它支配保留的对象规模。一个很小的缓存管理器可能保留巨大对象图；大数组也可能只是正常内容，不一定是根因。

```text
应用单例 → listeners → 旧页面 listener → Activity → 大图
```

要问这条强引用链是否仍符合业务寿命。若页面已结束而 listener 从未解绑，修复点在注册/注销协议；把大图变量临时设 null 可能只是削弱症状。Dominator 帮助发现保留支配关系，但不自动判定业务是否合理。取 dump 本身也会扰动进程，分析结论要结合发生时机。工具基础见 [Android heap dump](https://developer.android.com/studio/profile/capture-heap-dump)。

## 5. GC 不能替应用判断“已经没用了”

GC 从根可达性出发，不理解页面退出、订单完成或缓存过期。一个业务无用但仍可达的对象对 GC 仍是活对象；循环引用只要整体不可达则可以回收。调用 System.gc 不是稳定修复，更不能保证回收时刻。

弱引用能让 GC 忽略某条强保留关系，但也可能让业务需要的数据提前消失。缓存通常应有明确容量和淘汰策略；SoftReference 也不是精确内存预算。引用与回收原理见 [GC 第 1–3 节](#/article/gc-runtime?section=1)。

## 6. Java 堆稳定以后继续看 native 与线程

native 解码器、推理 session、直接缓冲等可能在托管堆外持有大量资源。Java 包装对象消失不代表底层一定及时关闭；JNI 全局引用还可能反过来保留托管对象。每个 create/open 要能找到对应 release/close，并覆盖异常、取消和重复关闭。

线程也消耗栈及系统资源。不断新建 executor 而不结束，可能先遇到线程创建失败；这时删图片缓存未必解决。记录线程数、名称、创建来源与 native 分配趋势，按症状选择工具。Android 内存口径见 [内存管理概览](https://developer.android.com/topic/performance/memory-overview)。

## 7. 剩余总量足够也不必然能完成申请

分配还受单次请求、分配器空间组织、虚拟地址空间、运行时限制和系统条件影响。特别是 32 位进程，地址空间限制不能简单靠设备拥有更多物理内存解决。不能看到“还剩几十 MB”就断言错误报告不可信。

但“碎片化”也不能作为没有证据时的万能解释。应查看具体失败信息、ABI、映射与分配方式，再判断是否与连续地址需求或堆空间组织有关。减少大块同时存活、采用流式处理可能有帮助；具体因果必须通过相同负载复现确认。

## 8. 把缓存和并发一起纳入预算

只限制缓存 50 MiB，却允许四个 45.8 MiB 解码任务同时运行，峰值仍可能远超缓存预算。应按资源生命周期建账：

```text
峰值预算 ≈ 稳态工作集 + 缓存 + 在途解码/变换 + 渲染重叠 + 余量
```

这是设计估算，不是 Android 精确记账公式，有共享与归属差异。缓存按字节而非图片张数计量；并发限制作用于真正占资源的阶段。队列也要有上限，否则排队请求捕获的大对象仍可能累积。拒绝、降采样和取消旧请求是产品需要明确的降级行为。

## 9. 用相同生命周期验证修复

固定设备、数据集、图片配置与操作，重复进入退出到足够暴露增长趋势；比较旧页面数、GC 后存活基线、native/线程趋势、峰值和失败率。修复保留链应让旧对象不再累积；峰值优化应降低重叠压力，不能只依赖更频繁 GC。

再测取消、失败重试与后台恢复，避免只修成功路径。不要凭一次未崩溃就声称解决 OOM，也不要编造下降比例。本文是诊断教学与验证方案，实际项目需附原始证据；报告结构见 [性能证据](#/article/performance-proof)。
