## 1. 端侧 AI 的任务范围

端侧任务包含分类、检测、OCR、语音唤醒、转写、Embedding、重排、生成与多模态理解。传统小模型可能更稳定、更省电，也更容易验收。先确定用户任务，再决定是否需要生成模型。一个离线文档定位工具也许只需要解析、向量检索与高亮，未必必须生成长答案。

端侧优势常包括离线可用、减少网络往返和数据外发，代价是设备差异、内存与功耗限制、模型分发和本地攻击面。云端有更灵活的算力与更新能力，但受网络、服务成本和数据约束影响。两者都应在同一质量门槛下比较，而不是只看峰值速度。

## 2. 场景与资源预算

|场景|候选设计|首先验证|
|---|---|---|
|离线语音控制|本地 VAD／识别与确定性动作映射|噪声下误触发和持续耗电|
|私有文档检索|本地解析与 Embedding，权限范围内检索|资源占用、删除与账号隔离|
|复杂跨文档分析|本地预处理，允许时云端推理|证据保真、外发边界、弱网体验|
|实时视觉辅助|本地轻量感知，必要时抽帧深分析|帧预算、发热和过期结果丢弃|
|长篇生成|按设备与任务路由本地小模型或云端|质量、等待时间、降级语义|

这些是可讨论的设计方案，不是某个 App 当前实现的声明。公司官方开源一个引擎，也不能推断其所有 App 都部署相同模型。

## 3. 端云协同的切分

按任务阶段切分通常比按神经网络层切分更易维护：本地去噪、提取文字或检索片段，云端做复杂推理。按网络层分割涉及中间张量带宽、形状兼容和跨端版本耦合，不能默认比传文本更省流量。

本地预处理可能丢信息。例如只上传 OCR 文本会失去版面、图片和手写标注，必须在质量评测里覆盖这些场景。离线期间承诺的能力也要明确：离线检索可用，不代表离线深度推理与在线效果一致。

## 4. 设备状态与降级路由

输入任务后，读取设备能力、模型可用性、当前内存压力、温度状态、网络与数据政策，选择本地、云端或暂不可用。路由规则可版本化，并保留可解释原因。设备支持某个加速 API 只是候选资格，不代表目标模型的全部算子真的在该硬件执行。

不要仅凭模型“自报置信度低”自动上传私有数据。外发必须符合用户选择和应用的数据边界，且传输内容最小化。云端失败后切回本地，需告知能力变化，并保持同一任务的取消、结果排序和防重复机制。

## 5. 客户端生命周期集成

模型推理服务与 UI 生命周期解耦，由受控队列管理，界面退出后取消任务并丢弃过期输出。会话持有 native buffer、模型句柄和缓存，需要明确所有权；Java/Kotlin 对象变得不可达，不意味着 native 资源已按预期释放。

账户切换时清理或隔离个人 KV、向量索引、历史对话和临时文件。模型可以共享，但用户派生数据不能随意共用。跨端 UI 框架不改变这些底层责任，JNI、FFI 或 JS Bridge 应只暴露受控任务接口，避免逐 token 的高频跨边界拷贝。

## 6. 收益验证与隐私边界

**数据在本地就绝对安全吗？** 不是。日志、备份、缓存、崩溃上报、共享存储和设备被攻破仍可能暴露信息。解释信任边界与删除策略比说“离线所以安全”更准确。

**如何证明端侧值得做？** 选取低中高档真实设备，比较同质量门槛下的离线覆盖率、首结果时延、持续性能、能耗与每用户分发成本；包含安装失败、低电量和模型未下载的场景。

**项目成果如何讲？** 给出选型前假设、最有代表性的失败场景、机型覆盖与灰度结果。本文没有进行设备测量，所有方案都需按项目约束验证。
