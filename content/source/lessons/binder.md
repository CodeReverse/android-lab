## 1. 普通方法调用为什么跨不过进程

音乐应用把播放服务放到另一个进程。界面想调用 `player.play(songId)`，但两个进程有各自的虚拟地址空间：UI 中的对象引用不是服务进程可直接解引用的地址。共享同一 Java 类定义，也不会自动共享实例。

需要一份双方认可的协议，把调用意图与参数送过去，再取回结果。AIDL 描述接口并生成适配代码；Binder 提供 Android 的 IPC 机制。它让调用形式像方法，但不消除跨进程的延迟、失败、权限和线程差异。

```aidl
// 教学接口：只表达命令，完整产品还需要状态订阅与错误模型
interface IPlayer {
    void play(String songId);
    boolean isPlaying();
}
```

为什么传 ID 而不是整首音频？ID 是小而稳定的协议数据，服务可自己读取资源；大字节数组增加序列化、复制和事务缓冲压力。共享内存或文件描述符能承载大数据，但会新增生命周期、访问范围和同步责任。

## 2. 沿一次远程调用走过代理与分派

```text
UI 调用 IPlayer
 → Proxy：把参数写入 Parcel，发起 transact
 → Binder 驱动：按目标引用路由事务
 → 服务端 Binder 线程接收
 → Stub：识别方法并读取参数
 → 业务实现
 → 回复 Parcel → UI 读取返回值/异常
```

这是机制示意，生成方法及驱动数据结构随版本而变。Parcel 不是 Java 对象原样“传送”，接收侧按协议重建值；Binder 引用和文件描述符另有跨进程语义。双方必须兼容字段、类型与接口演进策略。

若服务与调用者恰好在同一进程，`asInterface` 可能返回本地实现，直接在调用线程执行。只测本地服务就声称“所有 AIDL 都在线程池运行”会漏掉这一差异。线程规则见 [AIDL 官方指南](https://developer.android.com/develop/background-work/services/aidl)。

## 3. 同步调用会把等待传回调用者

默认同步调用要等远端回复。若主线程调用 isPlaying，而服务先等数据库锁，UI 就把远端等待纳入了自己的响应时间。服务端用了线程池，不代表调用端不阻塞。

```text
主线程等回复 → 服务线程等锁 → 持锁线程等磁盘
```

这是 [ANR 等待链](#/article/anr-diagnosis) 的跨进程版本。改成后台调用能避免直接堵主线程，但仍需要超时语义、取消与页面生命周期；并不使服务突然更快。

`oneway` 可表达不等待返回结果的远程事务，但没有业务成功确认，队列与服务资源仍有限。同一 Binder 节点的异步调用还有序列化规则；不能推成“每次调用任意并行”。本地调用仍直接执行。相关细节以 [Binder 线程模型](https://source.android.com/docs/core/architecture/ipc/binder-threading) 为准。

## 4. 重入让持锁远程调用更危险

A 调用 B，B 在处理时回调 A。Binder 支持嵌套事务，回调可能在原先等待的调用链上重入。假如 A 以为“我正在等回复，不会再有人访问这份状态”，就可能在中间状态下再次执行自己的逻辑。

因此不应随意持有业务锁跨 Binder 调用。一个更容易审查的设计是：锁内生成不可变请求快照，释放锁，执行远程调用，再回到锁内按版本条件提交结果。若期间状态变了，应重算或拒绝旧结果；不能认为两次短锁天然等于原来的大事务。

服务端也要按并发入口设计。多个 Binder 线程访问共享播放器时，可由专门串行状态所有者处理命令；它增加排队与确认协议，但避免任意线程直接修改内部状态。这是工程选择，不是 Binder 自动提供的业务保证。

## 5. 调用身份只在正确的边界才有意义

暴露服务不等于授权所有调用。权限检查、参数验证和 `Binder.getCallingUid()` 等身份判断应在接收事务的边界进行。把任务丢到另一个线程后再读调用身份，通常已不是原始事务的身份上下文；需要在入口验证并保存必要的可信信息。

客户端传来的 `userId` 只是参数，不能替代系统提供的调用方身份。`clearCallingIdentity` 是受控地改变当前身份上下文，配对恢复应放 finally；不能拿它绕过本应执行的授权。具体跨应用安全还见 [组件权限与信任边界](#/article/android-security)。

## 6. 服务死亡以后，命令究竟执行了没有

远端死亡可能发生在执行前，也可能发生在执行后、回复前。捕获 DeadObjectException 只知道通信失败，不能推出业务没做。重复播放或下载还好，扣款一类动作必须有稳定操作 ID、可查询状态和服务端去重。

`linkToDeath` 用于感知远端死亡并清理连接状态，但不能保证“检查活着之后下一次调用一定成功”；检查和调用之间始终存在竞态。重连应恢复订阅与必要状态，而不是无条件重放所有有副作用命令。

验证时分别安排本地/远程服务、服务延迟、回调重入、死亡前后和大参数；检查线程、等待时间、重复副作用及清理。事务缓冲是进程共享资源，不能把文档中的量级当作单次安全载荷上限，参见 [TransactionTooLargeException](https://developer.android.com/reference/android/os/TransactionTooLargeException)。这些是测试设计，非已执行报告。
