## 阅读方式

按定义、结构、运行过程、实现细节、故障与验证逐层阅读。问题顺序由本站编写；文末面经映射只证明相应主题被问过，不代表原帖出现了本篇全部追问。每问下方即为对应讲解。

## 第 1 问：什么是生命周期与状态恢复？为什么页面重建不等于用户重来一次？

生命周期描述组件从创建、可交互到离开和销毁等阶段。配置变化、导航和进程死亡会以不同方式重建组件；状态恢复是在这些条件下恢复用户有意义的操作上下文，而不是序列化整个界面对象图。先区分短暂 UI 状态、可重建业务数据和进行中的外部副作用，再决定保存位置与时机。

## 第 2 问：页面状态应该按什么生命周期划分？

一个搜索页面通常包含输入词、筛选条件、当前滚动位置、服务器返回列表和正在进行的请求。它们不应全部放进同一个 Bundle。输入与筛选是重建页面需要的少量状态；列表是可从本地库或服务端重建的数据；请求的生命周期又是另一回事。

Activity 的生命周期表达宿主可见性与交互状态，Fragment 还同时具有自身与 View 的生命周期。Fragment 实例可能仍在返回栈中，而其 View 已销毁。此时继续持有 binding 或以 Fragment 生命周期收集并更新旧 View，容易产生泄漏或无效更新。界面观察通常应绑定 viewLifecycleOwner。

## 第 3 问：ViewModel 能跨旋转和进程死亡保存同样的状态吗？

ViewModel 帮助跨配置变化保留内存状态，但进程被杀时它也会消失。SavedStateHandle 和可保存 UI 状态用于在系统支持的重建流程中恢复少量必要值；它们不是数据库，也不是用户主动移除任务后仍必然存在的永久存储。真正不能丢失的草稿或业务事务应落盘。

一个可维护的策略是：持久业务数据在数据层；ViewModel 持有当前页面状态；保存机制只记录重建入口，比如订单 ID、查询词和必要的滚动锚点。恢复后依据这些标识重新读取数据，而不是把整个复杂对象图塞进 saved state，避免事务体积与版本兼容问题。

## 第 4 问：恢复过程中为什么需要幂等与单一状态来源？

假设页面打开时提交一个支付请求，然后旋转屏幕。如果提交动作无条件写在 onCreate 或 Composable 函数体里，就可能再次发生。正确性不能仅靠“只执行一次”的内存布尔值：进程重启后它仍会丢失。支付结果应由业务请求 ID 查询，提交由明确用户事件触发，服务端再提供幂等约束。

同样，恢复筛选条件后自动请求可能与原有请求结果竞争。给查询状态附带版本或请求键，只接受仍匹配当前条件的响应。页面可见性决定是否收集 UI 更新，数据层是否继续同步则由业务归属决定，两者不要捆绑。

## 第 5 问：生命周期回调顺序能回答全部恢复问题吗？

A 启动 B 的具体回调序列受全屏或透明窗口、配置变化、多窗口和系统版本影响。回答时先给出常见全屏场景，再说明 onPause 不意味着完全不可见，onStop 也不是进程死亡通知。不能依赖 onDestroy 一定执行来提交关键数据；进程可能被直接终止。

### 逐层追问与回答支点

- 旋转后请求为什么重复？检查请求触发位置、状态所有者和恢复策略，不只是加一个全局单例。
- 为什么 SavedStateHandle 不能代替 Room？生命周期与容量不同，也不提供业务所需的事务、查询和长期存储语义。
- 切到后台是否取消全部工作？上传草稿和当前页动画的归属不同，应逐项定义。

## 第 6 问：怎样验证旋转、后台回收与进程重建？

测试矩阵至少区分配置重建、导航离开、后台进程被系统回收、用户主动结束任务。开发者选项“不保留活动”主要模拟 Activity 销毁，并不能完整模拟进程死亡。测试时记录进程 ID，确保真正重新启动后，页面没有重复提交、隐私数据没有串账号、必要草稿能恢复。
