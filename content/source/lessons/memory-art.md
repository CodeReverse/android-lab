## 1. DEX 与 ART 执行

源码经相应编译与 D8/R8 等构建处理，通常以 DEX 形式进入应用，由 ART 运行。ART 管理执行、类、对象和垃圾回收，并结合系统版本与配置采用解释、JIT、AOT 及 profile 相关优化。不能把它等同于桌面 JVM 加一个 Android UI 库。

讨论语言同步语义时可以参考 Java/Kotlin 契约；讨论对象布局、GC、编译策略和诊断参数时必须回到目标 ART 分支。

## 2. 进程内的内存组成

还包括 native 分配、线程栈、代码与文件映射、图形 buffer 和运行时等资源。Java 堆上限不是整个进程能够无限增加 native 内存的许可证；系统还根据整机压力管理进程。

模型推理、图片、音视频和跨端引擎经常在 native 或驱动侧持有大量资源，因此 Java heap 看起来平稳时仍可能内存持续增长。先定义资源归属，再选择测量工具。

## 3. RSS、PSS 与对象大小

RSS 反映驻留页面口径，PSS 对共享页按共享比例分摊；对象 shallow size 描述本体，retained size 用于估计因某个保留者存活而被间接保留的量。Java heap 的分配／使用／上限也是不同数字。

这些指标不能不加区分地相加，文件映射中的共享页可能被重复计算，驱动资源也有不同统计方式。比较前后要固定设备、场景与采样口径。PSS 变高可以提示问题，但单独不能证明是哪段代码泄漏。

## 4. ART 的回收范围

ART 对托管对象图进行相应追踪与回收，其具体收集器、屏障和空间策略随版本变化。可达性和分配压力的思想可迁移，但 G1 的 region、HotSpot 参数和旧版对象头图不能直接当成 ART 实现。

仍被长生命周期引用保留的页面，不会因为“系统 GC 很先进”就自动释放。native 资源由库的所有权与释放机制管理，不能依赖 Java 包装对象最终一定及时被回收。

## 5. JNI 引用与原生资源

JNI 的引用与普通 Java 局部变量不完全一样；全局引用需要按契约显式删除，否则可能持续保留对应对象。native 分配需要配对释放，DirectByteBuffer 或 Java 包装句柄的生命周期也必须与底层 buffer 对齐。

泄漏既可能是 Java 对象把 native 句柄长期保留，也可能 Java 包装对象已经丢失而底层资源未释放。跨边界取消和 close 要有幂等语义，避免漏释放或 double free；清理兜底不能替代明确所有权。

## 6. Bitmap 解码与内存

压缩文件大小和解码后的像素 buffer 大小不同。以不含额外开销的 ARGB_8888 示例，4000×3000×4=48,000,000 字节，约 45.8 MiB；解码临时区、缩放副本或并发多张会进一步增加峰值。像素存放与统计位置还受系统版本和配置影响。

按显示尺寸采样、控制并发、避免同时保留多份变换结果和使用有界缓存，通常更直接。缓存需按成本计量而不仅按图片张数；清空缓存后重解码造成卡顿和发热，也要一起验证。

## 7. 泄漏、抖动与峰值

泄漏强调不该存活的资源持续保留；抖动强调高分配与回收速率；峰值强调短时间重叠资源超预算，即使最后都释放也会失败。曲线阶梯上升、锯齿、高尖峰可提示方向，但都需引用、分配或资源证据确认。

例如 AI 模型更新同时驻留新旧两份权重属于可能的峰值问题；无限任务队列保留页面可能同时造成泄漏与积压。不能把全部内存故障都改成弱引用处理。

## 8. 进程回收与分配失败

系统在整机压力下终止进程不一定抛 Java OOM；Java 分配失败、native malloc 失败和创建线程失败也不是一个限制。trim 等资源信号适合释放可重建缓存，但回调时机与级别需按平台版本核验，不能依赖最后一次通知完成全部持久化。

状态恢复应在正常生命周期就设计好，资源释放按所有权完成。遇到失败先保留异常、设备、内存曲线和资源类型，再读 [OOM 排查](#/article/oom-diagnosis)。

## 9. 内存优化的验证

固定相同操作和数据规模，比较修复前后峰值、稳定平台、分配速率、目标实例保留与卡顿／耗电。分别测试页面退出、旋转、账号切换、后台与压力下恢复。若减少缓存换来每次都重新解码，需要报告这一代价。

保留 heap/native 分配证据、运行时版本与测量口径，避免只给一张内存下降截图。本文算例是像素数量推算，未在设备上测量这些场景。
