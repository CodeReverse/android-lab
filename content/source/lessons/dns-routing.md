## 1. DNS 在请求链路中的职责

一次请求可能依次经历调用排队、DNS、TCP、TLS、请求发送、服务端处理与响应读取；复用已有连接时，DNS 和握手甚至不会再次发生。域名解析只是把名字转换为可尝试的地址集合，并不保证每个地址都可达，更不保证后端业务健康。

DNS 查询可能命中客户端、系统、递归解析器等不同层的缓存。TTL 表达记录在缓存中可被使用的时间范围，实际链路还有负缓存、平台策略与连接池存活等影响。修改 DNS 后旧请求仍去旧地址，不一定是 DNS 没生效，也可能旧连接仍在被复用。

## 2. 多地址与路由质量

移动端可能同时得到 IPv4 与 IPv6 地址。一条路线连不通时，如果串行等待完整超时才试下一条，会放大尾延迟。Happy Eyeballs 一类机制通过安排多地址连接尝试来改善体验，具体时间间隔和实现应按客户端版本验证，不能把“永远先 IPv6”当作通用结论。

CDN 的地址选择还可能受解析位置影响。运营商解析、公共解析与 HTTPDNS 各自改变链路中的信任与故障域。HTTPDNS 能针对部分解析问题提供手段，但新增服务可用性、缓存、合规和运维依赖；不是无条件替代系统解析的性能开关。

## 3. IP 直连的身份和路由约束

HTTPS 需要校验目标主机身份。直接把 URL 域名改成 IP，可能同时改变 SNI、Host 与证书主机名验证语义。正确集成应让传输目的地址与被认证的业务域名保持清晰关系，不能为了“连得上”关闭证书检查。代理、负载均衡、HTTP/2 连接复用也可能依赖这些身份信息。

地址缓存至少要区分网络与账号相关上下文，尊重过期策略，失败后允许重新解析。Wi-Fi 切蜂窝时，已有 socket 不会自动获得新连接的所有属性；网络变化可能导致连接失效，重试仍须遵守业务幂等和总超时预算。

## 4. 解析故障的定位顺序

先把请求 ID 与各阶段耗时关联。如果 dnsStart 到 dnsEnd 长，检查解析器、缓存命中与网络环境；如果解析快但 connect 阶段长，检查地址族、路由和防火墙；若只有首请求慢而后续快，再区分连接复用和 DNS 缓存。记录失败的地址、网络类型和异常种类，但不要把用户敏感域名或完整 URL 参数无差别上传。

## 5. DNS 与连接耗时的分离验证

分别构造 DNS 超时、返回不可达 IP、仅一种地址族可用、网络切换和缓存过期。每种故障只改变一个变量，并在事件时间线中确认它落在哪一阶段。实验预期是正确归因与受控回退，不是宣称所有网络都能提速。
