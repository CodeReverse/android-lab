## 1. 先把一个域名还原成连接所需的信息

搜索接口第一次打开要等一秒，第二次却很快。直接结论“DNS 慢”还缺证据：第二次可能复用了连接，连 DNS、TCP、TLS 都没重新做。先把请求拆成可观察的步骤，再找哪个结果被复用。

```text
业务发起调用 → 客户端排队 → 查找可复用连接
                                  ├─ 可以复用 → 发送 HTTP
                                  └─ 需要新连接 → 解析地址 → 尝试连接 → TLS → HTTP
```

DNS 将域名查询映射为资源记录。A、AAAA 分别提供 IPv4、IPv6 地址，CNAME 表达别名；得到 IP 只说明拿到了候选目的地，不说明该地址可达，更不说明订单服务正常。端口、代理、TLS 主机身份和 HTTP 路由还需要其他信息。

把所有域名写死为 IP，确实能省掉查询，但服务器迁移、CDN 调度和故障切换就要由应用自行分发地址。DNS 的价值是把稳定名称与可能变化的部署地址分开。它引入了查询、缓存与信任链成本，因此小型内网也可以采用固定配置，但必须自己承担这些变化。

## 2. 用一次缓存命中理解递归与 TTL

假定手机查询 `api.example.com`，这里仅用保留示例域名作假设，不代表真实解析或业务服务。常见链路是本机 stub resolver 向递归解析服务求答案；递归服务已有缓存就直接返回，否则沿命名委派寻找权威答案。不是每个手机请求都依次访问根服务器、顶级域和权威服务器。

```text
手机 → 递归解析服务
         缓存未命中：根/委派信息 → com 区域 → example.com 权威记录
         缓存命中：直接使用仍有效的结果
```

设权威响应 TTL=60 秒，递归缓存已经保存 40 秒，那么能继续缓存的时间应考虑已消耗的寿命，不能每传一层都重新计 60 秒。这个数值例子忽略传输时间，只用于理解“剩余寿命”。实际还包括负缓存、平台配置和扩展策略，应对照 [DNS 基本模型](https://www.rfc-editor.org/rfc/rfc1034) 与 [负缓存规则](https://www.rfc-editor.org/rfc/rfc2308)。

现在服务端把地址由 A 切到 B，为什么应用仍访问 A？至少有两种不同原因：解析层仍持有未到期记录；解析已经变成 B，但客户端仍使用连向 A 的已有 socket。TTL 限制记录缓存，不会主动把连接池所有连接关闭。只清 DNS 缓存可能完全不改变第二种路径。

因此故障切换需要同时考虑旧服务保留时间、连接存续和客户端重试。把 TTL 调成极小会增加解析流量，未必等于切换立即完成。

## 3. 多地址让解析成功与连接成功分开

一个域名同时返回 IPv6 A6 和 IPv4 A4。假设 A6 路径黑洞，A4 可在 30ms 建连；若先为 A6 等完整 5 秒，再试 A4，用户等待至少五秒，但解析可能只花 2ms。

Happy Eyeballs 的方向是把地址族和连接尝试安排得更合理，避免一条差路径长期阻塞另一条。可以用简化时间线理解，而不是背一个永恒固定的间隔：

```text
t=0：尝试候选 A6
t=某个受策略控制的时刻：A6 尚未成功，启动 A4
A4 先成功：采用成功连接，结束不再需要的竞争尝试
```

并发竞速减少等待，但消耗额外连接尝试和网络资源；无限同时连接所有 IP 又会增加负担。地址排序、延迟、取消和重复失败记录共同决定行为。标准可查 [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305)，具体库是否实现以及怎样实现要按版本确认。

这也说明不应把“先 IPv6”当作业务保证。移动网络、VPN、代理和 DNS64/NAT64 都可能影响地址选择。网络切换以后，缓存的地址与路由经验需要重新评估，不能假定原 Wi-Fi 上可达的地址在蜂窝上仍是最优。

## 4. 保留域名身份，再改变连接地址

既然 A4 更快，可以把 HTTPS URL 改成 IP 吗？这样不只跳过解析，还改变了被认证的服务身份。证书检查、SNI 和 HTTP authority/Host 可能都受影响。

更清晰的建模是保留 URL 中的域名，只让解析接口提供候选地址。以下为 OkHttp 的教学片段，假设 `resolver.lookup(hostname)` 返回已核验、按寿命管理的 `InetAddress` 列表；它不是一份完整 HTTPDNS 产品实现。

```kotlin
val client = OkHttpClient.Builder()
    .dns(object : Dns {
        override fun lookup(hostname: String): List<InetAddress> {
            val addresses = resolver.lookup(hostname)
            if (addresses.isEmpty()) throw UnknownHostException(hostname)
            return addresses
        }
    })
    .build()
val request = Request.Builder()
    .url("https://api.example.com/search?q=compose")
    .build()
```

片段需要 okhttp3.Dns、OkHttpClient、Request 及 java.net.InetAddress/UnknownHostException。按 [OkHttp 4.12.0 Dns 接口](https://raw.githubusercontent.com/square/okhttp/parent-4.12.0/okhttp/src/main/kotlin/okhttp3/Dns.kt) 使用对象实现：该 Kotlin 接口不是 fun interface，不能把这里简写成 SAM lambda；自定义 resolver 还必须支持并发调用。URL 仍表达业务主机，连接地址由解析结果提供。默认 TLS 校验不能为了让实验通过而关闭；IP 本身不是证明服务身份的凭据。自定义解析还要考虑代理、不支持的域名、故障回退、IPv6 和缓存过期，不能把上面几行作为上线方案。

系统 DNS、加密 DNS、HTTPDNS 是不同选项。加密传输保护的是到解析服务的这段通信，不自动证明解析服务自身可信；自建服务还增加可用性和运维依赖。选型前先用阶段证据确认问题确实在解析，而不是以更复杂基础设施替代诊断。

## 5. 用阶段时间线排除相似症状

给每次调用一个脱敏关联 ID，记录排队、解析、连接、TLS 和响应阶段。下面都是人为算例：

| 请求 | 解析 | 连接 | TLS | 等待响应 | 优先假设 |
| --- | --- | --- | --- | --- | --- |
| A | 400ms | 30ms | 40ms | 50ms | 解析路径或缓存 |
| B | 2ms | 430ms | 40ms | 50ms | 地址可达性与竞速 |
| C | 无新解析 | 无新连接 | 无握手 | 520ms | 复用后的服务或链路 |

“无事件”不等于耗时为零，也可能说明复用或观测缺失。必须把连接是否复用、尝试过哪些地址、是否换网络放在同一记录里。一次业务调用可能多次重定向或尝试地址，不应拿多个子阶段随便拼成一次连接。

Spike 依次模拟解析超时、解析成功但地址不可达、单地址族可达和切网。每次只改变一个条件，检查日志是否落在预期阶段，然后才比较策略。本文未执行这些网络实验；来源只支持机制，不证明任何环境提速。请求总预算和可重试性继续读 [弱网可靠性](#/article/network-reliability?section=2)，握手内部见 [TCP 与 TLS](#/article/tcp-tls?section=2)。
