## 1. 从重复收藏状态找到真正的边界问题

列表页显示商品已收藏，详情页却仍显示未收藏。两个 ViewModel 各保存一份 mutable 状态，网络成功后又各自修改。此时问题不是“还没上 MVI”，而是同一业务事实有多个写入者、更新顺序不明确。

先画当前数据流：

```text
列表 ViewModel ↔ 网络
详情 ViewModel ↔ 网络
两份本地收藏状态，失败和刷新各自处理
```

如果只把类重命名为 Intent、Reducer、Store，两份事实仍会漂移。架构首先要规定谁拥有收藏事实、谁允许修改、UI 如何观察，再决定代码模式。

## 2. 单一事实来源不等于一个全局巨型对象

可让 repository 协调收藏写入，以数据库作为可观察的本地事实来源；两个页面读取同一来源。UI 的临时展开、焦点等仍可由页面持有，不需要全部进入数据库。

```text
用户意图 → repository → 本地事务/同步协议
                            ↓
                       数据库状态
                      ↙          ↘
                 列表 UI        详情 UI
```

这里“单一”针对某项事实和作用域，不是所有数据只能放一个单例。服务端可能是最终业务权威，本地数据库是客户端读取入口；二者通过同步状态连接。相关模式见 [Android 数据层](https://developer.android.com/topic/architecture/data-layer) 与 [离线数据](#/article/offline-data)。

为什么不让每个页面自己缓存？简单页面可以这么做，但跨页面一致性、重试和账号切换增多后，重复协议成本会上升。新边界的价值应由这些变化解释，而不是仅由分层图解释。

## 3. 依赖方向决定模块能否独立演进

定义页面需要的能力，而不是把数据库实体与 HTTP DTO 直接泄漏到全部 UI：

```kotlin
interface Favorites {
    fun observe(): Flow<List<FavoriteItem>>
    suspend fun setFavorite(itemId: String, selected: Boolean)
}
```

这是边界示意，真实 API 还需表达失败与同步状态。接口放在调用者与实现都能依赖的合适模块，实现依赖网络/数据库，UI 依赖能力契约。DTO 的字段调整不应迫使无关页面全部理解服务端协议。

但一方法一模块、所有类都抽接口，会增加配置与导航成本。模块边界应对应变更、所有权和复用需求；构建收益还受依赖扇出和 ABI 变化影响，不能承诺“拆模块必然提速”。参见 [模块化模式](https://developer.android.com/topic/modularization/patterns)。

## 4. 迁移时保留旧入口，逐步替换内部

不要同时重写所有页面。先用适配器把旧收藏接口接到新 repository，保持调用契约，再迁移一个页面的读取。新旧路径共存时，尤其要避免两套写入都在发请求或各自覆盖数据库。

```text
阶段 A：旧 UI → 旧接口 → 新适配器 → 单一数据入口
阶段 B：部分 UI 直接读新状态，其余仍经适配器
阶段 C：验证覆盖后删除旧入口与重复状态
```

影子比较适合无副作用的计算结果；不能对一次收藏写入或下单调用双执行后再比较。回退需要数据格式仍兼容、未完成任务有接管策略，不能只保留旧代码分支。

## 5. 状态机减少隐含组合

如果页面分别维护 loading、error、items、submitting 四个可独立变更字段，可能出现“已成功但仍显示提交中”等非法组合。显式状态转移可把合法路径写出来：

```text
Ready → Saving(operationId) → Ready(newValue)
                          ↘ Failed(previousValue, retryPolicy)
```

不是所有 UI 都必须用单一密封类；复杂并行区域可能需要组合状态。关键是哪些字段必须原子变化、哪些结果属于旧请求。Reducer 纯计算有利于测试，但 I/O、取消与事务仍要在明确边界执行；架构模式不会自动获得分布式一致性。

## 6. 用变化成本和故障证据验收

教学验证包括两个页面同时观察、离线写入、旧响应晚到、账号切换、数据库迁移和回退。除了功能正确，还观察新增字段要改多少模块、构建影响、测试隔离与定位成本。

如果只是目录更整齐而重复状态仍存在，说明没解决原问题。把“旧状态漂移如何复现、新入口怎样消除它、仍有哪些一致性限制”写进决策记录。本文案例为教学构造，未宣称真实团队改造收益；具体测试层次见 [测试策略](#/article/testing-strategy)。
