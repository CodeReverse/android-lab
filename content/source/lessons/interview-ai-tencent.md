## 1. 工作流与 Agent 应怎样选择？

原帖位置：八股第 1 项。

### 参考回答

主要区别是后续控制路径由预设代码决定，还是由模型根据观察动态选择。两者都可以调用 LLM，也可以混合：严格权限检查、提交事务等固定执行，资料调查等可探索部分交给 Agent。选型依据是路径不确定性、可验证性、风险和成本，而不是把 Agent 作为工作流的升级版。

### 原理与继续追问（编辑扩展）

追问：开放任务必须多 Agent 吗？不必。先建立单 Agent 基线；只有子任务能够独立验证且隔离上下文或并行带来净收益时再拆。总 token 和协调成本相同条件下比较，避免误把增加算力当成架构收益。

继续学习：[工作流与组织方式](#/article/ai-agent-runtime)

## 2. 如何区分 ReAct 与多 Agent 组织架构？

原帖位置：八股第 2 项。

### 参考回答

先澄清问题中的维度：ReAct 描述推理、行动和观察交替的循环，可用于单个 Agent；多个这样的 Agent 又能组成协调者—执行者、分层委托、流水线、并行独立分析或评审循环。不能直接说 ReAct 是一种多 Agent 拓扑。选择拓扑应说明任务依赖、共享状态、汇总策略和失败处理。

### 原理与继续追问（编辑扩展）

追问：两个 Agent 意见一致能证明正确吗？不能，它们可能依赖相同错误资料或同模型偏见。用可追溯工具结果和独立验证器判断；冲突时回到证据，而不是只按多数投票。共享写状态还要控制并发和重复副作用。

继续学习：[ReAct 与多 Agent](#/article/ai-agent-runtime) · [评估与偏差](#/article/ai-quality)

## 3. RAG 的数据应该存在哪里？

原帖位置：八股第 3 项。

### 参考回答

按数据职责拆开：原始文件在可靠文档／对象存储，文档 ID、版本、权限等放事务性元数据存储；倒排或向量索引是可重建检索层；会话与缓存另行管理。小规模可以合并物理部署，不必每种职责都新建一个服务，但不能让向量库成为无法还原的唯一原文。回答要能指回文档版本与证据区段。

### 原理与继续追问（编辑扩展）

追问：删除原文后索引仍在怎么办？输出前做权威状态和权限校验，索引异步清理期间不应继续暴露。Embedding 模型升级要绑定索引版本，不能混用相同维度但语义空间不同的向量。设计双索引切换并验证撤权和回滚。

继续学习：[数据与权限链路](#/article/ai-rag-pipeline)

## 4. ES 与 MySQL 的核心差异如何影响 AI 应用？

原帖位置：八股第 4 项。

### 参考回答

MySQL 常承担事务事实与结构化关系查询，ES 围绕搜索、倒排与分布式检索分析设计，也提供向量能力。不能概括为一个只会关系、一个只会文本；要比较一致性、过滤、检索排序、更新传播、容量和运维。典型组合是数据库保留文档与权限事实，搜索索引用于候选获取，读取结果再次检查事实版本。

### 原理与继续追问（编辑扩展）

追问：如何诊断检索不到？先检查数据是否进入索引、字段和分词是否正确、权限过滤是否误排，再查召回和排序。业务证据 Recall 与 ANN 相对精确近邻的 recall 不同，换数据库不能弥补不合适的 embedding 或错误分块。

继续学习：[检索机制](#/article/ai-retrieval) · [RAG 定位](#/article/ai-rag-pipeline)
