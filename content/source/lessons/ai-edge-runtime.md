## 1. 能导出模型，不代表手机能高效执行

推理引擎是把模型计算实际运行起来的软件，不是模型参数本身。模型图是带依赖的运算网络，算子是矩阵乘、归一化等计算节点，kernel 是在某类硬件执行算子的具体实现；backend/delegate/Execution Provider 等术语则表示把计算交给特定执行后端的机制，名称随引擎不同。理解这几层后，才知道“支持模型”究竟指哪一步。

训练框架中模型正常，转成部署格式后可能遇到不支持的算子、动态形状、精度差异或预处理不一致。引擎选型应从“模型图 + 输入形状 + 目标硬件 + 质量预算”开始，而不是先选一个流行名字。

```text
训练模型 → 导出/转换 → 图优化与后端划分
 → 部署制品 → 加载/内存计划 → 实际算子执行
```

每一步都可能改变数值或资源行为。先用固定小输入比较原模型与部署输出，再做真实任务质量评估；仅能创建 session 不是转换成功的充分证据。

## 2. 图划分解释了为什么加速器可能更慢

教学模型有 A→B→C 三段，其中 A/C 支持加速器，B 只能在 CPU。执行可能变成：

```text
设备 A → 同步/拷贝 → CPU B → 同步/拷贝 → 设备 C
```

若 B 很小但两次传输很贵，整图可能不如 CPU 路径。后端委派不仅要看覆盖比例，还要看断点位置、张量大小、布局和同步。某些后端会拒绝不支持的整图，某些支持部分回退，必须查实际配置。以 [ONNX Runtime QNN EP](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html) 为例，算子、精度和平台约束都有明确文档，不能把“有 NPU”直接换成“所有图都上 NPU”。

## 3. 六类引擎先按入口与边界比较

下表依据官方文档/仓库在本轮核对的公开能力，属于选型入口，不是跨设备性能排名：

|引擎|适合先验证的入口|必须继续核对|
|---|---|---|
|[LiteRT](https://developers.google.com/edge/litert)|Google AI Edge 的转换与端侧执行生态|模型格式、算子、具体加速后端与 API 路径|
|[ONNX Runtime](https://onnxruntime.ai/docs/tutorials/mobile/)|已有 ONNX 图与 Execution Provider 路线|opset、EP 覆盖、裁剪构建与回退|
|[ExecuTorch](https://docs.pytorch.org/executorch/stable/intro-how-it-works.html)|PyTorch 导出、lowering 与端侧 runtime|导出约束、后端委派、内存计划|
|[MNN](https://github.com/alibaba/MNN)|移动推理及其公开模型/LLM 工具链|转换、模型适配与目标后端支持|
|[ncnn](https://github.com/Tencent/ncnn)|面向移动平台的轻量推理|算子、Vulkan/CPU 路径与模型转换|
|[llama.cpp](https://github.com/ggml-org/llama.cpp)|支持模型架构的本地 LLM 与 GGUF 生态|具体模型、量化格式、后端和集成接口|

不同名字可能覆盖重叠任务，但模型格式不能任意互换。GGUF 是生态中的文件格式，不意味着任何 Transformer 都能无改动运行；ONNX 也不保证所有 EP 支持全部算子。

## 4. 转换验证从张量语义开始

同一张图片若训练端按 RGB、部署端按 BGR，或者归一化范围不同，模型可能运行很快却结果错。文本模型还需 tokenizer、特殊 token、chat template、位置与停止条件匹配。

```text
固定输入 → 比较预处理张量
 → 比较可用的中间/最终数值（按容差）
 → 比较任务级输出与失败样本
```

浮点与量化结果不必逐 bit 相同，容差应与任务相关；但也不能见到差异就一律归为正常量化。先排除布局、掩码、长度和缓存更新错误。量化误差方法见 [量化第 2–5 节](#/article/ai-quantization?section=2)。

## 5. session 与缓冲需要明确所有权

创建 session、加载权重、编译图和分配工作区可能很昂贵。复用能减少重复成本，却增加常驻内存；多个并发 session 还可能各自持有权重或缓存。线程安全与并发执行能力依引擎/API 契约，不能把一个 session 当任意共享的无状态函数。

关闭页面时区分终止该请求、清理 KV 与销毁整个引擎。模型热切换要考虑新旧同时存在的峰值，mmap 文件也要保持有效。JNI/资源边界与普通 Android 原理相通，见 [ART 内存](#/article/memory-art?section=6)。

## 6. 用同一任务做技术试验

固定模型结构、精度、输入输出和质量目标，在每个引擎分别记录转换成功、后端落点、加载、首结果、持续速度、峰值与错误。若某引擎只能跑不同模型，比较时应注明模型差异，不能把它全算成引擎优势。

保留引擎 tag/commit、转换命令、设备/驱动和模型校验和。官方 stable 文档会移动，生产接入应固定自己的版本。本文未运行六引擎基准，也不声称某引擎在某 App 当前全量使用；实际发布见 [端侧性能](#/article/ai-edge-performance)。
