## 1. RAG 与幻觉边界

检索增强生成先从知识源找到相关片段，再将上下文交给模型回答。检索可能漏掉关键证据，也可能找到过期、冲突或无权限内容；模型还可能误解甚至编造引用。因而应把检索质量、回答忠实度和最终任务成功分开评测。

一个技术知识库应保留文档版本、来源和更新时间。检索到 Android 某旧版实现时，回答必须识别适用版本，不能把它拼接成“当前所有版本都这样”。这也是本项目把面经与原理依据分开的原因：面经证明问过什么，官方资料帮助判断答案是否成立。

## 2. 资料分块与索引

仅按固定字符数切块可能把结论与限制分开。可沿标题与语义边界切分，并保留父标题、来源、版本和前后文；必要时组合关键词与向量检索，再重排。更大的上下文不一定更好，重复或无关内容会增加成本并干扰判断。

权限过滤必须在检索与输出链路中生效。只在 UI 隐藏文档标题，而索引仍把正文返回给模型，无法保护数据。删除、撤权和更新也需要传导到缓存与索引，不能无限保留旧副本。

## 3. 评测集和数据泄漏

收集真实任务与已知失败案例，包含有答案、资料冲突、版本差异、信息不足和越权请求。为每题定义可核验标准与允许的不确定回答；不要只用一个模型给另一个模型打总体印象分。人工抽样应覆盖高风险与边界样本。

检索指标可观察命中与排序，回答指标看事实支持与引用准确，产品指标看任务完成、延迟与成本。提示词、模型、索引或分块变化后，用同一评测集回归，再分析具体失败类型，而不是只看平均分升了多少。

## 4. 生成代码的独立验证

生成代码可以加速探索，但评审应检查 API 真实性、版本兼容、权限、线程、取消、资源释放与测试覆盖。编译成功只验证一部分契约，AI 生成的测试也可能和实现犯同样错误。关键行为应有独立规格和反例。

使用 AI 阅读事故日志时先脱敏，避免上传密钥、用户信息或公司受限代码。让模型列出假设和需要的证据，比要求它仅凭一段栈“确定根因”更有价值。最后结论由实际 trace、复现和代码分析支撑。

## 5. 资料冲突与权限验证

建立一组含旧版 Compose、缺失来源与矛盾资料的问题，检查系统能否指出版本与不足；再加入要求读取无权限文档的任务。评测应允许“证据不足”，因为错误而自信的答案不是合格输出。
