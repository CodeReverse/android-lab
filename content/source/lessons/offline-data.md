## 1. 收藏成功后断网，界面应该信哪份数据

用户点击收藏，UI 立即显示成功；进程随后被回收，重新打开却恢复未收藏。若变化只保存在内存，乐观反馈没有留下可恢复事实。离线优先首先要确定读取入口，让界面观察本地持久状态，同时明确它与服务端同步到哪一步。

```text
UI 观察本地数据库
用户修改 → 本地事务 → UI 立即观察到 pending 状态
同步成功 → 本地状态变为 confirmed
```

pending 不是已经获得服务端承诺。离线可编辑的收藏与必须在线确认的支付，产品语义不同，不能一律乐观成功。基础设计可参考 [Android offline-first](https://developer.android.com/topic/architecture/data-layer/offline-first)。

## 2. 先给业务操作稳定身份

每次网络重试都生成新 ID，会让服务端把同一用户意图当成多个操作。应在创建业务意图时产生 operationId，并和账号、目标资源、期望值一起持久保存。

```text
operationId = K17
account = U8
item = P3
desiredFavorite = true
state = pending
```

这只是教学记录。设置为 true 通常比“翻转一次”更容易表达重试语义，但仍要考虑版本与后来的操作。稳定 ID 解决关联和去重的前提，不等于客户端自己就能保证服务端恰好执行一次。

## 3. 用同一个本地事务保存变化和待发送记录

若先更新收藏再写队列，进程可能死在两步之间，界面变了却永远没有待同步操作；反过来先写队列，界面状态也可能丢失。Outbox 思路把两份本地记录放进同一事务：

```text
transaction:
  update favorite(P3, selected=true, sync=pending)
  insert outbox(K17, U8, P3, selected=true)
commit
```

本地原子提交保证二者一起出现或一起不出现。后台 worker 读取 Outbox 发送，收到可确认结果后再用本地事务更新状态并标记完成。它不把数据库外的网络副作用纳入同一个事务。

```text
服务已处理 K17 → 响应丢失 → Outbox 仍 pending
worker 重试 K17 → 服务去重/查询既有结果 → 本地确认
```

因此端到端通常依靠至少一次尝试、幂等处理与结果查询构造可恢复效果，而非凭空得到“传输恰好一次”。重试与幂等的 HTTP 边界见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) 和 [弱网可靠性](#/article/network-reliability?section=3)。

## 4. 新意图不能被旧响应覆盖

用户先收藏 K17，再取消收藏 K18。K18 先完成、K17 响应后到时，若每个成功响应都无条件覆盖本地 selected，就会倒退到旧状态。

可以按资源序列化写入，或给操作/资源版本并只确认相应代次。即使 K17 成功，也只更新它的同步记录，不覆盖已经属于 K18 的当前意图。具体方案取决于服务端并发契约，不能只在 UI 上丢弃旧响应却让数据库继续被污染。

多设备同时编辑时还需要冲突规则。最后写入获胜简单，但客户端墙钟不可靠，也可能丢失用户修改；基于服务端版本的条件写入能发现冲突，再由领域决定合并或提示。CRDT 适合特定可合并数据，不是任意业务都能自动合并。

## 5. 删除与账号切换也要进入同步协议

如果离线删除后直接移除所有记录，下一次拉取旧服务端数据可能把它复活。需要在适当同步窗口内保留删除标记或版本信息，待确认其他副本不会重放旧值后再清理；具体回收策略依协议而定。

Outbox 必须按账号隔离。退出 U8 后，不能拿 U9 的 token 发送 U8 的记录；可暂停、明确清除或按产品规则恢复，但必须显式选择。权限撤销和服务端拒绝不能永久无限重试，应转成可解释的失败状态。

## 6. 重放故障比只测成功更有价值

教学测试在本地事务前后、网络发送前后、服务提交后响应前、本地确认前分别终止流程，再恢复 worker。检查本地意图不丢、同一业务操作不重复生效、旧响应不覆盖新操作。

还要限制重试频率、队列容量和保留时间。持久调度工具可以帮助任务恢复，但不能替代上面的幂等与冲突协议。本文是原创协议演算，没有声称已运行故障注入；测试组织见 [测试策略](#/article/testing-strategy)。

## 面试提炼

1. pending 与 confirmed 为什么不能都叫“成功”？（第 1 节）
2. operationId 应在哪一步产生，为什么重试不该换？（第 2 节）
3. Outbox 本地事务保证了什么、保证不了什么？（第 3 节）
4. 旧响应、多设备冲突与删除复活怎样处理？（第 4、5 节）
5. 哪些终止点最能暴露同步协议缺陷？（第 6 节）
