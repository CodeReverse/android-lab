## 1. 怎样讲清 RAG 从入库到回答的全过程？

原帖位置：第 4 项。

### 参考回答

先描述离线解析、结构清洗、权限与版本提取、分块、embedding 和索引；在线再讲查询理解、权限过滤、多路召回、重排、上下文组装、生成与引用校验。把原始数据和派生索引分开，给每次回答留下模型与文档版本。只说向量库 top-k 会漏掉权限、时效和证据支持。

### 原理与继续追问（编辑扩展）

追问：资料查到了还答错是什么原因？候选中的证据可能被重排丢掉或截断，也可能已经进入上下文但模型误读。用人工证据的 oracle context 对照把检索与生成分开，避免所有问题都靠增加 top-k。

继续学习：[RAG 全链路](#/article/ai-rag-pipeline)

## 2. 如何提升检索证据的覆盖率？

原帖位置：第 5 项。

### 参考回答

先标注正确证据并测当前 Recall@K。按失败原因修复解析和分块，保留原意做查询改写，针对专名和语义错配使用关键词与向量混合召回，必要时调整 ANN 探索预算。精排改善候选内次序，但不能找回候选池之外的证据；需要明确说的是候选召回还是最终上下文覆盖。

### 原理与继续追问（编辑扩展）

追问：混合分数直接相加可以吗？两路分数尺度不一致，应校准或采用 RRF 等排名融合。增大候选后记录重排成本、去重与上下文预算，对比质量和尾延迟，不把所有改动同时上线而无法归因。

继续学习：[混合召回与 RRF](#/article/ai-retrieval)

## 3. Chunk 应怎样切分与验证？

原帖位置：第 6 项。

### 参考回答

先按文档结构保留标题、段落、表格列名与代码边界，再依据 tokenizer 设置长度预算。太小丢上下文，太大混入噪声；overlap 会增加重复和成本。父子块可用小块定位、大块补上下文，但展开后仍要权限验证、去重和截断。业务材料差异很大，没有固定 token 数能一概最优。

### 原理与继续追问（编辑扩展）

追问：如何证明新切法更好？固定 query 与标注证据，对比候选召回、最终证据覆盖、答案正确与索引大小。切分改变后重建索引并保留版本，避免新旧块混用；测试表格、定义和跨段落条件，不能只测短 FAQ。

继续学习：[分块与实验](#/article/ai-rag-pipeline)

## 4. Function Calling 到底由谁执行？

原帖位置：第 12 项；原帖写作 Functional calling，此处按常用术语解释。

### 参考回答

模型基于工具描述给出结构化调用建议，实际由宿主解析、校验并调用代码或服务。必须核对工具名、schema、当前身份、资源权限和业务条件，返回标准化结果给模型。结构合法与业务授权不同，不能把符合 JSON schema 当成安全证明。

### 原理与继续追问（编辑扩展）

追问：参数错误后能否让模型一直修？应给结构化可恢复错误并设置修正预算；资源无权限不该通过反复猜 ID 解决。写工具超时先查询业务状态，幂等与对账由系统保障。

继续学习：[工具执行链](#/article/ai-tools-context)

## 5. Function Calling 与 RAG 分别解决什么问题？

原帖位置：第 13 项。

### 参考回答

RAG 主要为回答提供外部知识证据；Function Calling 为模型表达结构化动作请求提供接口机制。Agent 可以通过工具调用做检索，再用检索结果回答，也可以调用计算、查询订单或创建工单等非检索工具。二者可组合，不是可互相替换的两个模型。

### 原理与继续追问（编辑扩展）

追问：仅把所有知识库都暴露成工具够吗？还需要检索质量、权限、上下文预算、引用与拒答。工具调用成功只证明接口执行，不能证明返回片段足以支持答案。

继续学习：[知识路径](#/article/ai-rag-pipeline) · [动作路径](#/article/ai-tools-context)

## 6. 资深工程师怎样看待 AI 对研发工作的影响？

原帖位置：第 16 项。

### 参考回答

可讨论判断框架而不伪造项目：生成成本下降后，需求规格、验证、集成与长期维护仍决定交付质量。先识别可标准化且有明确验收的任务，用基线比较总交付周期、返工和缺陷，而不是把生成行数作为收益。新能力也带来依赖、权限与质量漂移的工程成本。

### 原理与继续追问（编辑扩展）

追问：如何决定先落哪个场景？优先边界明确、失败可发现、回滚容易、价值可测的任务；列出当前人工成本与验收方式。不能只因为其他公司在做 Agent 就引入开放循环。没有个人实测时明确是方案推演。

继续学习：[研发价值与责任](#/article/ai-coding)

## 7. 如何评估 AI 代码审查是否可靠？

原帖位置：第 17 项。

### 参考回答

无法保证每条评论永远正确。建立包含真实缺陷和无缺陷变更的独立集合，由人工按明确规则标注，再测缺陷级 precision、recall、严重漏报和误报。对可执行结论用测试、构建或复现验证，开放判断再用人工审查；不要用同模型自评代替外部证据。

### 原理与继续追问（编辑扩展）

追问：评论数量翻倍意味着更好吗？不意味着，泛泛意见可能降低有效发现比例。还要看定位、修复可行性、时间成本和用户采纳后的真实效果。数据按仓库和时间隔离，避免答案泄漏。

继续学习：[审查评测](#/article/ai-coding) · [质量体系](#/article/ai-quality)

## 8. AI Coding 出过问题时应该怎样复盘？

原帖位置：第 18 项。

### 参考回答

只使用自己的真实案例。可以按目标约束、模型产生的错误、发现证据、缺失上下文和验证器改进组织。常见候选方向是不存在的 API、旧版本调用、测试与实现共享错误假设、取消遗漏或误改用户代码；这些是本知识库列举的风险，不是声称原帖作者或读者经历过。

### 原理与继续追问（编辑扩展）

追问：如何防止重复发生？把版本边界、接口契约和复现用例加入可检索上下文与独立测试；高风险变更设置真实运行检查和可回滚 diff。复盘产物应是能拦住同类故障的机制，而非只记一句“下次仔细检查”。

继续学习：[上下文与验证链](#/article/ai-coding)
