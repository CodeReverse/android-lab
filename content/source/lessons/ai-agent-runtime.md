## 1. 从查状态到代办任务，控制权发生变化

Agent 在这里指围绕模型运行的任务执行系统：模型根据输入和观察提议下一步，宿主程序执行允许的动作，再把结果交回模型。它不是模型里自动长出的操作系统，也不是必须多个模型协作。可以先跟着 [从普通函数到 Agent](#/article/ai-agent-workshop) 运行一个离线小例子，再读本篇的生产状态与恢复问题。

用户问“这笔报销到哪一步了”，一个固定查询工具就能回答；用户说“检查缺失材料，补齐草稿并提交审批”，系统需要根据观察选择下一步，处理失败并决定何时停止。Agent 的工程核心是受控执行循环，不是把 prompt 写得更像角色扮演。

固定步骤明确时，工作流更容易测试：查状态→检查材料→生成草稿→等待适当授权。路径需要根据环境动态变化时，才考虑让模型选择动作。设计原则可参考 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)，本文流程是原创教学案例。

## 2. ReAct 把行动结果反馈给下一次决策

```text
观察当前状态
 → 提议一个动作及参数
 → 宿主验证并执行
 → 取得真实结果
 → 更新任务状态
 → 决定继续、结束或请求缺失信息
```

ReAct 研究把推理与行动交替组织，见 [原论文](https://arxiv.org/abs/2210.03629)。工程中需要保留的是可审计的动作、结果和决策摘要，不应把模型生成的一长段解释当作动作已经成功的证据。

如果工具返回“文档不存在”，下一步可以请求用户补充或找允许的替代来源；不能在上下文中自行补出一个“已找到”的结果。环境反馈让计划修正，也让错误有明确来源。

## 3. 状态机防止循环失去边界

只写 `while not done: ask model` 容易反复查询、重复提交或耗尽预算。把任务状态和动作执行分开：

```text
Planning → Running(toolCallId)
Running → Observed(result) → Planning
Planning → NeedsInput / Completed / Failed
任意运行态 → Cancelling → Cancelled（按实际可取消范围）
```

持久状态至少关联任务 ID、当前步骤、已完成副作用、证据引用和剩余预算。限制轮次、时间、token/费用与连续失败，避免模型一句“还需要再试试”无限延长。结束条件应由可检查结果支持，例如审批系统返回真实编号，而不只是模型说“完成了”。

## 4. 崩溃恢复不能重复执行副作用

假设宿主提交成功后、写 checkpoint 前崩溃。恢复后只看本地“未完成”就重发，可能提交两次。需要稳定 operationId、服务端幂等与结果查询；checkpoint 记录的不是自然语言总结，而是能判断动作状态的结构化信息。

```text
计划提交 K → 持久记录意图 → 发请求 K
 → 结果可确认 → 持久记录结果
恢复遇到结果未知 → 查询/同键重试，不新建业务意图
```

同一问题在客户端同步中也存在，见 [Outbox](#/article/offline-data?section=3)。不能因为执行者换成模型就跳过分布式系统基础。长任务的上下文交接与环境管理可参考 [Agent harness 实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。

## 5. 多 Agent 只在拆分收益超过协调成本时成立

把独立资料检索拆成多个执行者，可能缩短等待；把强共享状态、顺序依赖的修改同时交出去，则容易冲突。多 Agent 增加重复上下文、消息、合并与结果核验成本，不保证答案更可靠。

教学拆分可按互不重叠的文档源分工，每个结果附证据与未确认点，由单一所有者合并。涉及同一代码文件或同一业务副作用时，需要明确锁、所有权或串行提交。不要用“再加一个审查 Agent”替代确定性测试和真实授权。

## 6. 用失败路径评估自主程度

为任务注入工具超时、空结果、权限不足、格式错误、已成功但响应丢失和上下文压缩。观察系统能否停止、恢复、说明不确定性，并保持副作用次数正确。

指标至少区分任务成功、工具选择/参数正确、重复副作用、人工接管与成本。一个回答很漂亮却没完成提交的 Agent，不能按文本质量判成功。本文给出设计与验证方法，没有实际运行自主代理或报告成功率；工具协议继续见 [工具与上下文](#/article/ai-tools-context)。
