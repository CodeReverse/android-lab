## 阅读方式

按定义、结构、运行过程、实现细节、故障与验证逐层阅读。问题顺序由本站编写；文末面经映射只证明相应主题被问过，不代表原帖出现了本篇全部追问。每问下方即为对应讲解。

## 第 1 问：Agent、工作流与 ReAct 分别是什么？

工作流通常由代码预先确定主要步骤和转移，模型可作为其中一个节点；Agent 把部分下一步选择交给模型，依据观察动态调用工具。二者是控制权分配方式，不是互斥产品类别。固定的报销审核步骤更适合显式规则，可变的信息调查可能受益于动态规划，混合设计很常见。

ReAct 指模型在推理与行动、观察之间迭代的一类模式，本身不是“多 Agent 架构”。多 Agent 的组织还可以是协调者分派、分层委托、流水线、并行独立分析或评审循环。架构选择取决于任务是否可拆、状态是否共享、结果如何验证；多一层模型不自动产生更可靠的判断。

## 第 2 问：一次 Agent 循环怎样落成可观察状态机？

一次任务可表示为：接收目标 → 装配上下文 → 请求模型 → 校验决策 → 执行工具或给出结果 → 保存观察 → 判断继续／终止。运行时保存 run ID、step ID、模型与提示版本、预算、待执行动作、工具结果引用和检查点。模型生成 JSON 只是建议，宿主程序才是执行者。

工具调用前做 schema、资源身份、权限和业务约束验证；调用后将成功、失败、超时或未知结果标准化。验证器不能只看“模型说已完成”，应检查目标是否真实实现，比如工单是否存在、文件是否可编译、证据是否覆盖必要断言。

## 第 3 问：怎样判断任务完成、无进展或应终止？

循环至少受最大步数、总时长、token／费用预算约束；还要检测无进展、重复动作、不可恢复错误和目标完成。相同参数可能用于合法轮询，不能一刀切；可给轮询独立间隔、次数和状态变化规则。步骤上限触发时应返回部分结果和未完成原因，而不是假装成功。

模型反复改写计划可能没有业务进展，因此进度指标应基于已确认事实、已完成子目标和新证据。上下文越长不代表积累越有效，历史错误结论也会被带入下一轮；原始工具证据与摘要要分开存放。

## 第 4 问：工具重试与 checkpoint 为什么不等于 exactly once？

纯查询失败可以按错误类型退避重试；写入工具需要幂等键与状态查询。支付或创建工单超时可能表示操作已完成但响应丢失，直接重试会重复执行。持久化动作意图，执行后记录外部操作标识；恢复时先对账，再决定重发或补偿。

“保存了 checkpoint”并不等于 exactly once。若外部写入发生在检查点提交前，崩溃恢复仍有双写窗口。可以借助事务 outbox、目标端幂等或补偿流程缩小影响，但必须说清哪个系统提供什么保证。模型调用本身还可能返回不同决策，恢复时优先复用已确认动作，而不是无条件重新规划。

## 第 5 问：什么时候应拆多 Agent，怎样管理共享状态？

把可以独立验证的子任务并行化，可能降低长任务时延或隔离上下文；强耦合共享状态则可能引入竞态、重复工具调用和观点相互污染。协调者应传递明确输入、权限、预算、输出 schema 和完成标准；子任务只能获得所需上下文，汇总时检查证据冲突。

总成本包含所有子任务和协调开销。评估应对比“单 Agent + 同等 token 预算”，否则只是多花钱换结果。多数投票并非独立证据：同一模型、相同检索和相同偏见可能产生相关错误。

## 第 6 问：如何选择编排框架，并验证故障恢复？

**如何选择 LangGraph 一类图运行时？** 需要显式状态、循环、检查点、暂停恢复时图模型可能有帮助；简单固定三步流程用普通代码更容易维护。框架的 checkpoint 语义、并发冲突和升级迁移必须实测，不能把框架名称当可靠性证明。

**如何评测 Agent？** 看任务是否完成、非法调用率、副作用重复率、恢复成功率和成本；同时保留轨迹定位错误出在哪一步。单次最终答案评分无法发现中途越权读取。

**建议怎样练习？** 设计“建工单后网络断开”的故障注入，用相同 run ID 恢复，检查是否只创建一张工单；设计不可达目标测试预算终止。这里是待执行的实验方案。
