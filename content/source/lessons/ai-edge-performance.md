## 1. 端侧任务的耗时分解

端侧模型通常共享应用内存、CPU、GPU、存储与电池预算。总时延包含资源加载、预处理、模型执行、后处理、跨语言调用与界面呈现。首 token 快不代表整段回答快，纯推理平均值也可能掩盖预处理复制和 UI 竞争。

一次请求应使用关联 ID 记录冷加载、编译／初始化、prefill、decode、后处理和渲染。设备型号、系统、引擎、模型、线程数、温度状态与电量条件同时保存，才能比较两次实验。不要用不同机型或已热机与冷机的结果直接得出优化结论。

## 2. 运行内存与峰值

预算包含权重驻留、KV、激活、临时工作区、输入输出 buffer、运行时与应用自身对象。mmap 让文件映射到地址空间，实际页面访问仍会进入驻留内存；共享页面、PSS、RSS、native heap 和驱动内存的口径不同，不能简单相加重复计数。

模型热切换同时加载新旧权重可能接近双份峰值，正常运行不 OOM 不代表更新安全。可先下载校验到磁盘，再在空闲时卸载旧实例、加载新实例；若需要无缝切换，必须为重叠内存留预算，并保留失败回退路径。

## 3. 算力、带宽与瓶颈

对某一计算阶段，粗略下界可比较 `max(运算量/有效算力, 访存字节/有效带宽)`，实际还会受同步与调度影响。若某 decode 步主要需要读取约 2 GB 权重，有效带宽假设为 20 GB/s，则单次读取约 0.1 秒；这是带假设的下界估算，不能直接当成 10 token/s 的设备实测。

batch、缓存复用、权重分片、压缩读取和硬件内核会改变实际流量。提高线程数可能先快后慢，因为内存带宽已饱和、调度竞争或温度上升。先确定算术强度和流量，再决定优化内核、减少复制还是改变模型大小。

## 4. 持续运行的温升和能耗

持续负载产生热量，系统可降低频率或限制资源；同时后台任务、UI 渲染、充电与环境温度都影响表现。Benchmark 需要冷启动、暖启动、连续多轮和冷却后复测，展示随时间变化的曲线，至少报告 P50/P95 与最差设备组。

能耗可用可靠功率测量积分获得，使用系统估计时必须标明口径和误差。tokens/s 提升不代表每次成功任务耗电降低：回答更长、失败重试更多或持续占用加速器都会影响能耗。应同时报告任务完成率、耗时和能量。

## 5. 模型发布与热切换

模型包的 manifest 绑定 hash、签名／可信来源、引擎兼容、tokenizer、模板与配置。下载到临时文件，校验后原子切换；断点续传要防止混入不同版本分片。设置磁盘预留和下载策略，清理旧版本时保留必要回滚能力。

新模型上线不仅回归文本效果，还要回归加载失败、设备覆盖、峰值内存、热稳定、崩溃和取消。按设备与模型版本灰度，失败时回退旧模型或停止功能，不应该反复重载造成崩溃循环。运行时与模型分别升级时需维护兼容矩阵。

## 6. 取消和持续性能验证

**界面退出后推理还占资源？** 检查取消是否只取消 UI 等待，native session 是否真正停止，buffer 与回调是否被释放；对不能中断的单次算子，可以停止后续步骤并拒绝旧结果。生命周期和资源所有权需贯穿跨语言边界。

**如何证明降温策略有效？** 在同输入与环境条件下比较持续性能、质量与能耗；降低帧率或输出长度会改变任务质量，必须一起报告。不能只拿短时峰值改善作结论。

**交付哪些证据？** 机型矩阵、模型／引擎 hash、测试条件、原始 trace、分层耗时、热曲线和失败清单。本文只提供实验方案，带宽数字是假设计算，未在用户设备上运行模型压测。
