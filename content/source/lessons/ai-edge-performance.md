## 1. 首次能跑与持续可用之间还差一轮测量

先区分三个单位：延迟按毫秒/秒衡量一次等待，吞吐按每秒 token 或任务数衡量工作量，内存按字节衡量同时持有的数据。能耗与瞬时功率也不同，不能只因跑得快就推断更省电。下面沿同一次推理记录这些量，先不依赖设备宣传参数。

端侧助手第一次生成很快，连续问十轮却明显变慢。可能是上下文越来越长、缓存增长、温度限制、资源争用或泄漏；不能把所有下降都归为“手机发热”。先拆开模型加载、首结果等待、持续输出与整个任务完成。

```text
下载/校验 → 加载/编译 → Prefill → Decode → 清理/保留会话
```

冷加载可能包含读盘与后端准备，第二次复用 session 的结果不能与冷加载直接比较。长上下文的正常工作量增长也应与热降频分开控制，基础见 [推理原理](#/article/ai-inference)。

## 2. 内存账要包括切换时的重叠

设旧模型权重驻留 1.5 GiB，新模型也要 1.5 GiB；为了无缝切换先加载新模型，会短时叠加两套资源，另外还有 KV 和工作区。即使稳定态每套都能运行，更新瞬间也可能失败。

```text
运行旧版 → 下载到临时文件 → 校验
 → 选择切换窗口 → 释放/保留旧 session 的明确策略
 → 加载新版本 → 验证 → 原子切换活动清单
```

数字为教学设定。mmap 降低某些复制并支持按页访问，不等于零驻留或没有峰值；PSS、RSS 和映射口径见 [ART 第 4 节](#/article/memory-art?section=4)。模型、tokenizer、模板与配置要作为兼容组合切换，不能只替换权重文件。

## 3. 小批量生成可能被带宽而非算力限制

每步 Decode 需要访问权重和历史缓存。理想下界可粗看为 `需读取字节 / 有效带宽`，但缓存、量化解包、kernel、并行与访存模式都会改变实际值。设备宣传的峰值算力或带宽不是应用可持续达到的数值。

若权重压缩后数据读取减少，可能加速；若新格式解包很贵或后端不支持，收益可能消失。只有 trace/算子 profile 和实际输入形状才能确认瓶颈。引擎落点与回退见 [端侧引擎](#/article/ai-edge-runtime?section=2)。

## 4. 温度策略要在质量和交互允许范围内调整

持续计算会影响热状态，系统可能限制性能。可观察 Android Thermal API 提供的状态/预测信息，但可用性与行为依设备/API，不能把某个状态直接换算成统一温度或固定降频比例。官方说明见 [Thermal API](https://developer.android.com/games/optimize/adpf/thermal)。

可选策略包括减少并发、降低相机处理频率、暂停非必要后台任务或选择更小模型。每种策略都影响体验/质量，需要有明确恢复条件，避免在阈值附近反复切换。静默上传到云并不是无条件安全降级，仍要遵守数据策略。

## 5. Benchmark 使用代表性矩阵

|维度|至少区分|原因|
|---|---|---|
|运行状态|冷加载/已加载/持续运行|初始化和热稳定性不同|
|请求|短/长输入，不同输出上限|KV 与计算负载不同|
|设备|芯片、内存、系统、后端|支持与资源差异|
|质量|原精度/量化/降级模型|速度收益可能来自能力退化|
|生命周期|前后台、取消、切换|资源释放与恢复不同|

固定任务，记录首结果、token 间隔/吞吐、总时间、峰值、失败与热状态；相同设备做可重复对照。测试持续足够暴露稳定阶段，同时避免把不受控环境变化混入结论。没有实际测量时只写预算与实验设计，不给虚构跑分。

## 6. 模型发布是兼容性发布

制品清单关联模型 hash、tokenizer、量化、引擎最低兼容版本与必要配置，下载后校验完整性和来源。加载失败应能保留旧版本或回退到清晰降级路径；清理旧文件不能抢在仍有会话引用它之前。

按设备层级灰度并记录具体制品身份，才能将崩溃、质量退化或回退算子聚类到原因。引擎升级可能改变支持与数值，参见 [ONNX Runtime Mobile](https://onnxruntime.ai/docs/tutorials/mobile/) 和 [ExecuTorch 执行机制](https://docs.pytorch.org/executorch/stable/intro-how-it-works.html)。这些文档说明能力，实际发布矩阵仍由项目验证。

本文未执行模型下载、设备基准或灰度发布；方法与性能证据篇一致，见 [性能证据](#/article/performance-proof)。
