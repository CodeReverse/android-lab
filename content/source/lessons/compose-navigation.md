## 阅读方式与讨论边界

阶段 10 的状态架构与导航正文。重点是所有权、返回栈、恢复和窗口适配，避免把具体导航库版本当成永恒架构。Navigation 2 的 NavController/NavBackStackEntry 与 Navigation 3 的返回栈、条目管理接口应分别查证，不混写示例；资料核验：2026-10-25。

## 第 1 问：页面、状态持有者、ViewModel 和领域层如何分工？

纯 UI 渲染输入并发送事件；页面状态持有者组织与 UI 行为相关的状态和操作；ViewModel 可承接屏幕级业务状态与生命周期；领域和仓储处理业务规则及数据真相。不是所有组件都需要 ViewModel，也不是把所有状态放入一个 ViewModel 就等于分层。

搜索词和筛选条件影响请求，由屏幕状态层协调；展开菜单可以局部持有；收藏结果以仓储为准；离线下载若需离开页面继续，不应挂在组合协程作用域。先画持有与销毁关系，再选择 API。[状态提升](https://developer.android.com/develop/ui/compose/state-hoisting)。

## 第 2 问：导航参数为什么宜传 ID，而不是整个数据对象？

ID 表达目的地身份，目标页面从可靠来源加载当前数据；完整对象可能过大、过期或无法恢复，并把上下游绑到同一模型版本。深链接还可能直接进入详情，没有上一个页面为你准备对象，因此详情需要独立解析参数和处理不存在/无权限状态。

原创推演：用户从通知打开已被删除的文章，不能因数据库查不到就无限 loading。明确无效 ID 的错误态、返回目标和权限判断；链接能抵达路由不等于用户有权限访问业务数据。参数可序列化与业务合法性是两层校验。

## 第 3 问：返回栈、组合生命周期和 ViewModel 生命周期相同吗？

不同。条目可能仍在返回栈中，但内容暂时不在可见组合；ViewModel 的存续取决于其 ViewModelStoreOwner，不能只依据页面是否当前可见推断。弹出条目后是否释放，以选定导航实现和 owner 作用域为准。把全局 owner 错当页面 owner 会让状态跨页面残留。

返回栈还决定重复进入同一 ID 是复用、添加新条目还是恢复旧条目。切换账号时，要同时处理数据缓存与受身份约束的返回栈，避免返回到旧账号界面。导航正文入口：[官方导航指南](https://developer.android.com/guide/navigation)。

## 第 4 问：一次性导航与弹窗事件怎样避免重复和丢失？

先定义交付语义。支付成功后“展示已支付状态”可以由持久业务结果重建；一个轻量 Snackbar 可能允许页面离开后丢弃。不要用同一种 replay 配置处理所有事件，也不要认为任意 Channel 都能跨进程保证恰好一次。

对需要确认的动作，设计事件 ID、已处理状态或状态机转换，使重入可安全处理；导航触发处校验当前目的地与目标状态，避免重组时反复 navigate。真正的提交幂等性在业务层实现，Effect 的 key 只管理 UI 生命周期中的执行身份。详见[副作用正文](#/article/compose-effects)。

## 第 5 问：多窗口和大屏为什么是架构问题，而非简单放大？

同一窗口内可以同时展示列表和详情，状态所有权应允许两个面板共享选择与数据；窄窗口只显示其中一个时，仍需保持用户任务连续性。按当前窗口约束与布局策略选择展示，不使用“这是平板”这样的永久布尔值。

如果详情 ViewModel 每次切换单/双栏都无意重建，会导致重复请求或草稿丢失。若把它无条件提升到整个应用，又可能使不同窗口互相污染。需要明确任务、窗口、页面和组件四层身份，并验证缩放、折叠与外接显示变化。[自适应布局](https://developer.android.com/develop/ui/compose/layouts/adaptive)。

## 第 6 问：设计系统和模块化怎样避免形成另一套大泥球？

设计系统模块提供主题、组件契约、语义和测试，不依赖具体搜索业务；feature 模块组织屏幕与业务输入输出；导航集成层连接目的地。公共组件优先输出意图回调，避免对外暴露某个具体导航控制器，使测试和替换更容易。

建立组件变更的兼容策略：哪些参数可新增默认值、哪些状态语义改变需迁移、哪些视觉变化需要通知消费方。升级编译器、UI 库和设计系统分别记录，避免一次“大升级”使回归无法归因。资深面试要说明边界为何如此划分、代价是什么，而不只说用了 MVI。
