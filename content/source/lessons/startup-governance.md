## 阅读方式

按定义、结构、运行过程、实现细节、故障与验证逐层阅读。问题顺序由本站编写；文末面经映射只证明相应主题被问过，不代表原帖出现了本篇全部追问。每问下方即为对应讲解。

## 第 1 问：启动过程的关键路径怎样找？

应用启动涉及进程创建、类与资源加载、Application、组件初始化、首个页面以及数据准备。所有任务耗时总和不是首屏延迟，决定完成时间的是依赖关系中的关键路径。并行执行只有在存在可并行任务、资源可用且依赖正确时才减少端到端耗时。

先列初始化 DAG：每个任务的依赖、线程约束、首屏是否必需、失败策略和幂等性。初始化 SDK 不是凭经验全部丢到线程池；某些库要求主线程，某些任务隐藏依赖，过多并发又会争抢 CPU 与磁盘。

## 第 2 问：延迟初始化为什么可能只把卡顿挪到首屏之后？

将任务移到首帧后可能改善 TTID，却使用户第一次点击卡顿。对低进入概率功能可以按需加载，对高概率且低成本功能可适度预热，但需要测首次使用延迟和内存。预热条件应与设备资源及用户路径匹配，而不是让所有用户承担所有功能的预付成本。

首屏数据还涉及缓存与网络。先显示本地数据需要明确陈旧策略；为了速度省略权限或账号校验会引入正确性风险。首帧、内容可用和可交互应分别记录，不能靠提前调用 reportFullyDrawn 美化数据。

## 第 3 问：Baseline Profile 改善什么，又不能解决什么？

Baseline Profile 帮助运行时对重要代码路径进行引导优化，可能改善启动和交互执行成本；它不能消除网络等待、磁盘阻塞或不合理依赖。Startup Profile 还涉及启动相关代码布局，概念与作用点不应混为一谈。

生成 Profile 需要覆盖真实旅程，并验证打包、分发和安装后生效情况。只添加依赖或生成文件不足以证明用户已受益。比较时固定编译模式与安装条件，避免把不同预编译状态当作代码优化。

## 第 4 问：如何把一次启动优化变成持续治理？

每个初始化任务应有 owner、预算与可观测标签；新 SDK 接入需说明首屏必要性和回退方式。基准场景覆盖高频入口、深链和必要恢复路径。门禁应考虑设备噪声与复测策略，避免一次抖动阻塞所有发布，也避免长期以“偶发”忽略真实退化。

线上分群尤其重要：低端设备 CPU 与存储更敏感，网络初始化又可能在不同运营商表现不同。整体平均改善但低端 P95 恶化，不应直接宣称治理成功。

### 逐层追问与回答支点

- DAG 排好就一定线程安全吗？不一定，任务内部共享状态与库线程要求仍需验证。
- Application 工作很少为何仍慢？检查更早组件、类加载、资源、系统调度与首屏后续等待。
- Profile 与手工优化冲突吗？不冲突，但必须分别测量边际收益，避免重复归因。

## 第 5 问：怎样验证冷暖启动、回归与长期稳定性？

记录每个任务的排队、执行与完成时间，选出关键路径；一次只移动或拆分一类任务。用相同旅程比较无 Profile/有 Profile 的构建，再灰度观察首屏、首次交互、稳定性和内存，保留能一键关闭的新增预热策略。
