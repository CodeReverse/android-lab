## 1. 从一条订单请求区分三种保证

用户点击下单，客户端显示超时。服务端是否已经创建订单？回答这个问题前，要把字节传输、对端身份和业务提交分开：TCP 管有序可靠字节流，TLS 管通信的认证与保护，HTTP 表达请求与响应语义，数据库才保存订单事实。

```text
订单操作 → HTTP 消息 → TLS 记录 → TCP 字节流 → IP 数据包
```

一次 TCP ACK 只确认相应数据到达对端 TCP 的接收处理范围，不证明 HTTP handler 已执行，更不证明事务已提交。TLS 握手成功也只建立相应安全上下文，不代表用户具有下单权限。把不同层的成功混用，是重复订单和错误重试的常见来源。

可以不使用 TCP 而在 UDP 上自行实现应用协议，但那意味着自己处理丢失、顺序、拥塞和安全；QUIC 就是一套有明确规范的方案，后文再比较。不是给 UDP 加个序号就等价于可靠生产协议。

## 2. 从丢失一段数据推导序号、确认与窗口

把发送字节编号，简化为三段：`[0,100)`、`[100,200)`、`[200,300)`。中间一段丢失，最后一段到达。接收端不能把 200 后的字节直接拼到 99 后交给期望有序流的应用，否则 JSON 会变成另一份数据。

```text
收到 [0,100) → 连续前缀到 100
收到 [200,300) → 可以保留，但中间仍缺 [100,200)
重传补齐 → 连续前缀到 300 → 应用可按序读取
```

真实 TCP 使用字节序号、确认与重传等机制，上面省略 SYN 占用序号和回绕。选择性确认可以告诉发送方哪些非连续块已到达，减少不必要重传；具体恢复还依赖拥塞算法和实现。规范基线见 [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293)。

为什么不能一直发到网卡满？接收方处理能力和网络承载能力是两个上限。接收窗口约束接收方还能接受多少，拥塞窗口限制当前网络中允许飞行的数据。粗略理解，未确认数据受两者较小值约束；加大应用 buffer 不会自动突破拥塞限制。

三次握手建立双方序号与连接状态，不是为了保证“网络永远可靠”。FIN 结束某个方向的发送，另一方向仍可有数据；RST 表示不同的异常终止语义。连接可用与一个请求是否成功仍然要回到更高层判断。

## 3. TLS 为什么还需要认证而不只是加密

攻击者若能把自己的公钥放到客户端面前，再把流量转发给真服务端，两段通信都可以加密，用户却仍在和中间人交流。所以客户端不仅要协商密钥，还要确认密钥交换对应预期服务身份。

以典型 TLS 1.3 完整握手作职责示意，不包括 HelloRetryRequest、客户端认证等分支：

```text
ClientHello：支持的参数、密钥份额、服务名等
ServerHello：选定参数、服务端密钥份额
后续受握手密钥保护的消息：证书、签名证明、Finished
客户端验证身份与握手完整性，发送自身 Finished
双方使用相应应用流量密钥保护数据
```

证书链建立到受信任根的关系，主机名验证确认访问的域名匹配身份，握手签名与 Finished 把身份、协商参数和握手内容联系起来。ECDHE 等密钥协商不是“客户端拿证书公钥直接加密所有 HTTP 数据”。具体保证见 [TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446)。

如果自定义 TrustManager 接受所有证书，加密可能仍在，但身份验证被破坏。证书固定可以缩小信任集合，也会引入轮换和故障恢复成本；不能只写死一张即将过期的证书而没有更新策略。

会话恢复可以减少握手成本，0-RTT 还需要考虑重放风险。能提前发送不等于适合提前执行扣款；不可安全重放的操作必须由协议与服务端政策约束。连接变快与业务幂等是两个设计问题。

## 4. HTTP/2 多路复用为何仍受 TCP 丢包影响

HTTP/1.1 的连接使用模式容易让多个请求相互等待。HTTP/2 把消息拆成带 stream 身份的帧，多个 stream 可在同一连接交错传输，减少对“一条请求独占一条连接”的依赖。

但是这些帧仍装在同一个 TCP 字节流里。假设 TCP 中间一段丢失，即使后面的字节属于另一个 HTTP/2 stream，它们也不能绕过 TCP 的有序交付缺口。这就是需要区分的传输层队头阻塞。

QUIC 在 UDP 上实现受保护的连接和独立 stream 交付，某条流丢数据不要求其他流等待补齐它的字节。它仍共享连接级拥塞资源，也仍可能受流控、应用依赖、CPU 和链路影响，不能说“HTTP/3 没有任何阻塞”。参见 [HTTP/2](https://www.rfc-editor.org/rfc/rfc9113)、[QUIC](https://www.rfc-editor.org/rfc/rfc9000)。

| 方案 | 主要复用单位 | 仍需评估的成本 |
| --- | --- | --- |
| 多条 HTTP/1.1 连接 | 连接 | 握手、socket、拥塞竞争 |
| HTTP/2 | 单 TCP 上多个 stream | TCP 丢包对流交付的影响 |
| HTTP/3 | QUIC stream | UDP 可达性、CPU、协议部署与回退 |

这是一组结构差异，不是跨网络环境的速度排名。弱网下收益必须通过同设备、同路径与同内容实验验证。

## 5. 连接结束前后都可能出现未知业务结果

回到订单：客户端已写完请求，服务端提交订单，但响应丢失。这时关闭连接、收到异常或用户取消，都不能让已提交事务自动撤销。

```text
客户端             服务端
发送 create(K) →   事务提交订单 O
等待响应       ←   响应在链路中丢失
超时：结果未知      O 仍然存在
```

正确下一步是使用稳定业务操作 ID 查询或重试同一逻辑操作，由服务端去重与恢复结果，而不是把所有网络异常解释为“未下单”。设计细节在 [幂等与未知结果](#/article/network-reliability?section=3)。

做协议 Spike 时可分别在握手前、请求体中、服务端提交后和响应中断开。记录异常阶段、发送进度、服务端事务与最终结果。只有协议抓包而没有业务记录，仍无法证明订单未执行；只有 HTTP 200 统计也看不到重试制造的重复副作用。本文的时序是教学推演，未声明实测协议性能。
