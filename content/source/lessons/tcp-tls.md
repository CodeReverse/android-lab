## 1. TCP 可靠字节流的边界

TCP 向应用提供有序字节流，通过序号、确认、重传等机制应对丢包与乱序。它不保留应用消息边界：一次 write 不对应接收方的一次 read，业务协议需要自己定义长度或分隔。发送调用成功通常只意味着数据被本地协议栈接受，不意味着服务端已提交订单。

三次握手用于同步双方初始序号、建立连接状态并确认双向通信条件。分析连接建立需要同时考虑旧重复报文和双方的状态转换，不能只依赖报文数量。连接关闭涉及双向独立的发送结束，实际报文可能合并，因此“四次挥手”不是每次抓包都必须恰好四个包。

## 2. 流量控制与拥塞控制

流量控制保护接收方的处理与缓冲能力；拥塞控制适应网络路径容量。窗口受二者共同约束。扩大线程池或同时启动更多请求，不能突破链路容量，还可能增加排队与丢包。移动网络上的高 RTT 会放大握手、重传与细碎串行请求成本，复用与减少往返常比单纯压缩几字节更有效。

TIME_WAIT 与主动关闭端、旧报文隔离等机制相关，不能以“浪费资源”为由笼统绕过。应用通常应使用成熟连接池，关注连接生命周期与服务端配置，而不是自己修改 TCP 参数追求表面连接数下降。

## 3. TLS 加密与身份验证

TLS 握手协商协议参数、建立密钥并验证对端身份。证书链可信不等于主机名匹配，两项都必须满足。只检查证书有没有过期、或接受所有证书，都会破坏认证。证书固定还引入轮换与灾难恢复成本，应设计备用信任与可更新策略，而不是硬编码一张永不过期的证书。

TLS 1.3 常规握手和会话恢复的往返成本不同；0-RTT 数据具有重放风险，不能把支付等非幂等操作随意放入早期数据。加密能保护链路，却无法阻止合法服务器返回错误业务状态，也不能修复客户端泄露凭据。

## 4. HTTP/2 与 HTTP/3 的队头阻塞

HTTP/2 在同一连接上承载多个流，缓解 HTTP/1.1 某些应用层排队；底层仍是有序 TCP 字节流，丢失的字节可能延迟后续数据交付，影响多个流。HTTP/3 基于 QUIC，让不同流不必共享同一有序字节流的交付阻塞，但仍共享带宽、拥塞和服务端处理能力。不能据此说 HTTP/3 没有任何队头阻塞或一定更快。

## 5. 业务超时到传输证据

把“协议可靠”转化为客户端设计：设置总超时、限制并发、区分错误层次、为副作用请求提供幂等键。至于具体拥塞算法、握手报文和客户端协议支持，必须绑定部署版本与抓包证据。
