## 1. 从最后一张票找出需要保护的整体动作

库存只有 1，两个线程同时判断大于零，各减一次，最后卖出两张票。给 stock 加 volatile 只能处理相应可见性，不会把判断和扣减合成一个不可分割操作。

```java
synchronized (inventoryLock) {
    if (stock > 0) {
        stock--;
        issuedTickets.add(ticket);
    }
}
```

锁保护的是“库存与票据满足同一个不变量”的临界区，不是给变量贴标签。读取库存和票据的一方也需遵守协议；如果两个入口各自使用不同 lock，仍没有共同互斥。保护范围太小会破坏一致性，太大则扩大等待，这是锁设计的第一项取舍。

## 2. 监视器同时提供互斥与内存语义

线程进入 synchronized 需要取得对应对象的监视器，退出时释放；同一线程可以重入。释放与后续对同一监视器的获取建立规定的 happens-before，使前面的相关写对后续读可见。

```text
A 获取 L → 改库存和票据 → 释放 L
                                  ↓ 同步关系
B 获取 L → 同时检查库存和票据 → 释放 L
```

异常离开 synchronized 也会按语言语义释放，不需要业务手工 unlock。它不保证公平先到先得，也不允许用 timeout 参数尝试进入。规范契约看 [JLS 17](https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html)，对象头、轻量机制和膨胀策略则属于具体 JVM/ART 版本，不能把某代 HotSpot 的偏向锁图当通用规范。

## 3. 显式锁增加了控制能力也增加了责任

若售票请求有等待期限或需要响应中断，可评估 ReentrantLock。显式获取与释放要求使用同一控制结构：

```java
if (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    return Busy;
}
try {
    return issueIfAvailable();
} finally {
    lock.unlock();
}
```

这是方法体片段，Busy 与 issueIfAvailable 是业务占位。没有成功获取就不能 unlock；异常路径也必须释放。公平配置有助于按相应规则限制插队，但不提供操作系统调度的严格时间保证，不同获取方法还有各自契约。

synchronized 已满足简单临界区时，不必为“可配置”换成显式锁。增加超时能力也要求定义 Busy 对用户意味着重试、排队还是失败。API 依据见 [ReentrantLock](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html)。

## 4. CAS 把一次条件更新做成原子操作

只有一个计数，没有其他共同不变量，可以用 AtomicInteger。简化 CAS 循环是：

```text
读取 old
计算 next
compareAndSet(old, next)
  成功：返回
  失败：别人已经改过，重新读取并计算
```

两个线程都读到 0，其中一方把它改成 1，另一方的 CAS 就不能按旧期望覆盖，需重算成 2。计算函数可能执行多次，所以不能把扣款、发通知放在“计算 next”里，除非另有幂等协议。

CAS 不等于没有成本：竞争会重试，缓存一致性也有开销。若值先从 A 变 B 再变 A，单纯比较当前值看不出中间历史，这就是 ABA 类问题；是否需要版本戳取决于算法是否依赖历史。纯计数加一与无锁链表节点回收面临的风险不同，不能只背一个词。

## 5. AQS 把等待排队与同步状态语义分开

既然 CAS 竞争会反复失败，能否让失败者暂时休眠，释放时再叫醒？AQS 为这类同步器提供排队、阻塞与唤醒框架，子类定义状态代表什么以及怎样获取/释放。

```text
快速尝试获取 state
  成功 → 执行
  失败 → 进入等待队列 → 按条件 park
释放 state → 使合适等待者有机会重新尝试
被唤醒 → 重新竞争，不是直接被授予锁
```

对可重入独占锁，状态可表达重入次数并关联拥有者；对信号量，则可表达剩余许可。独占与共享取得成功后的传播规则不同。AQS 自身不是万能锁，也不保证所有同步器都公平。

伪代码省略了入队/取消竞争和节点状态处理，不能照抄实现锁。关键接口与约束见 [AbstractQueuedSynchronizer](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/AbstractQueuedSynchronizer.html)。锁实现为何复杂，主要在“准备休眠与释放恰好同时发生”也不能丢掉进展，而不是一个队列名字。

## 6. Condition 等待的是谓词而不是通知次数

库存不足时等待补货，如果持着锁 sleep，补货者拿不到锁，等待没有意义。Condition.await 会按契约释放相关锁并等待，返回前重新取得锁：

```java
lock.lock();
try {
    while (stock == 0) {
        notEmpty.await();
    }
    stock--;
} finally {
    lock.unlock();
}
```

补货者在持同一锁时更新 stock，再 signal/signalAll。通知表示条件可能改变，不是为某个等待者预留一张票；还存在虚假唤醒或别人先消费，因此必须 while 重查。

Condition 的等待队列与竞争锁的队列有不同职责：被 signal 后还需重新竞争锁。Object.wait/notify 也需要匹配的监视器协议；sleep 不释放监视器，不能当 await 替代。多条件队列可减少无关唤醒，但让协议更复杂。

## 7. 从两个账户转账画出死锁环

线程 A 先锁账户 X 再锁 Y，线程 B 反过来，便可能形成：

```text
A 持有 X → 等 Y
B 持有 Y → 等 X
```

最直接的修复是统一全序，例如按稳定账户 ID 获取锁，并处理相同 ID/同账户情形。tryLock 加超时允许退出，但双方总在同一时间重试还可能活锁；需要退避、顺序或更高层协调。

不要持锁调用不受控回调、网络或同步 Binder：外部代码可能重入并获取其他锁，使等待图超出当前类。锁内只保留必须保护的状态转换，慢操作先后如何安排则需重新检查不变量，不能机械地把所有语句搬出临界区。

## 8. 读多写少也不自动意味着读写锁更好

读写锁允许符合条件的读者并发，但它有额外状态与竞争管理成本，写者可能受长期读操作影响。非常短的读取，用简单锁或不可变快照可能更便宜；多字段一致读取则必须保证拿到同一视图。

乐观读允许先读、再验证期间有无写入。验证失败需要重读，读取动作本身不能依赖已经被破坏的中间状态安全执行。它不是“去掉锁然后最后比较一下”就能套任意对象图。

评审时比较临界区长度、竞争分布、读写比例与尾延迟。公平锁可能减少某些饥饿却降低吞吐，CAS 可能省阻塞却烧 CPU。没有脱离负载的锁排名。

## 9. 用等待链和反例检验同步协议

测试先验证不变量，再验证取消与进展：库存不能负数，票据数与扣减对应；等待者中断能退出；异常后锁可继续取得；两账户交叉转账不形成环。压力测试未出现错误不能代替协议推理。

诊断记录线程、拥有者、锁对象和等待资源，重复采样看有无推进。主线程阻塞时还需追到持锁者为何慢，详见 [ANR](#/article/anr-diagnosis)。本文未运行同步压力实验，AQS 图为职责模型，不冒充特定版本节点源码。
