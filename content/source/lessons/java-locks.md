## 1. 锁与共享不变量

锁用于协调并发访问，使同一不变量涉及的多步操作在约定边界内完成，并建立相应内存可见性。锁不是自动冻结一个对象的所有字段；只有遵守同一协议的访问才受保护。两个线程各锁自己的对象，再操作同一份共享数据，仍可能竞争。

例如转账需要同时维护两个余额和总量约束，分别把单次读写变成原子操作并不足够。先找共享状态、不变量和操作边界，再讨论具体锁的性能。

## 2. synchronized 的锁对象

实例同步方法关联接收者对象的监视器，静态同步方法关联声明类的 Class 对象，代码块关联括号中的对象。锁 A 实例不保护 B 实例；锁 this 也不等于锁某个静态共享集合。监视器是可重入的，同一线程再次进入按相应次数退出。

同步块通常可在字节码中看到 monitorenter/monitorexit，同步方法使用方法标志表达同步语义。异常退出也需要释放监视器。不要把编译器安排的正确退出语义误当成手工 Lock 的自动 unlock。

## 3. 互斥与可见性

同一监视器的解锁 happens-before 后续成功加锁。线程 A 在释放前完成的写入，通过这条关系对线程 B 随后的受保护读取可见。关键是同一个监视器和正确的同步顺序，不是任意两个 synchronized 都相互同步。

锁外读写同一个可变字段，不能仅凭另一路代码加了锁就认为安全。锁的实现可能使用原子指令、屏障、排队和系统等待等机制，但语言保证不等同于简单一句“全部刷到主内存”。

## 4. 锁实现与版本差异

不是，它们描述特定实现和版本中的优化策略。对象头如何表示锁、是否自旋、何时膨胀或消除，都受 HotSpot 版本、配置与优化影响；Android ART 有自己的 monitor 实现。不能把某张旧版 HotSpot 锁升级图当作 Java 的永久契约。

面试应先讲互斥、重入、等待与可见性，再声明讨论哪个运行时版本的源码。如果没有核验某版本对象头布局，明确边界比背出已经变更的位图更准确。

## 5. CAS 与复合操作

CAS 以原子方式比较当前位置是否等于期望值，符合时更新；i++ 则涉及读、算、写，多个线程可能基于同一旧值覆盖。原子类可通过 CAS 循环等机制实现复合原子操作，具体实现与内存访问模式需按 API 理解。

CAS 只能直接保护所针对的状态，多个变量之间的不变量仍需锁、不可变快照或更完整协议。高竞争下重试带来 CPU 与缓存一致性开销；无锁不代表无等待、一定更快或更容易证明。

## 6. ABA 与版本标记

线程看到值 A，期间其他线程把它改成 B 再改回 A，普通 CAS 可能仍成功，却忽略了中间状态变化。如果算法关心对象生命周期或链表节点是否被复用，仅比较值不够。

可用版本号、带戳引用或合适的内存回收协议表达状态变化；版本也要考虑回绕和覆盖范围。不是每个“值回到 A”的场景都错误，要先证明算法不变量是否依赖历史身份。

## 7. AQS 的状态和等待队列

AQS 提供原子 state 操作、等待队列、获取／释放流程和条件队列支持，子类定义 state 的含义及 tryAcquire/tryRelease 等规则。它不是“自带公平性的锁”，也不直接实现所有同步器接口。ReentrantLock 用它表达独占与重入；信号量等可用共享获取语义。

竞争失败时进入队列并按规则重试或挂起，释放后促使等待者继续竞争。队列用于协调，不意味着唤醒即获得锁。具体 Node 字段与取消清理算法随 JDK 演进，本文以 JDK 21 API 契约为边界。

## 8. park 与 unpark

LockSupport 的许可机制允许先 unpark 后 park 而不一定丢失这次许可；许可不无限累计，park 也可能因中断或其他原因返回。等待者必须重新验证锁状态，不能把返回当作获得锁。

线程并不应在所有竞争阶段一直自旋，长等待时挂起减少无用 CPU 消耗，但切换也有成本。正确同步器需要处理入队、准备等待、释放唤醒之间的竞态，单独拼几次 CAS 和 park 很容易遗漏唤醒或破坏队列。

## 9. 公平策略与调度

公平策略通常偏向已排队的等待者，但线程调度仍不保证全局时间顺序。非公平路径可以抢占空闲锁，可能提高吞吐，也增加个别线程的等待风险。ReentrantLock 的无参 tryLock 还有不遵循公平排队策略的契约细节。

用业务需要定义公平：尾等待、饥饿和吞吐分别测量，不以“公平”二字直接推导性能更差或用户体验更好。

## 10. Condition 的等待循环

await 需要持有相应锁，它在等待时释放锁，之后返回前重新获取；signal 把符合条件的等待者推进后续竞争，不立即把锁转交给它。唤醒后条件可能被其他线程改变，也可能有非预期唤醒，所以在 while 中检查业务条件。

不同 Condition 可表达非空、非满等不同等待集合。signal 不是一条可随意缓存的业务事件，必须与受锁保护的状态一起设计；信号发出后若状态不满足，等待者仍应继续等待。

## 11. 显式锁选择与死锁预防

需要可中断获取、超时尝试、多条件队列或明确公平策略时可考虑显式锁；普通互斥场景 synchronized 往往更简洁。显式锁成功获取后在 finally 解锁，避免异常路径遗留；不要在未获取时无条件 unlock。

死锁定位画等待图：谁持有哪把锁，等谁，是否有环。固定锁顺序、缩短临界区、避免锁内外部调用、可中断或超时恢复都有价值。超时不是自动修复，退出前须保持状态一致；锁内同步 Binder 调用还可能出现跨进程等待链。

## 12. 并发正确性的验证

先明确线性化点或受保护不变量，列出允许与禁止的交错，检查所有读写路径是否遵守协议。再使用受控并发测试、压力与故障注入测争用和尾等待；测试没复现不能代替内存模型证明。

性能对照需相同语义和负载，不能拿不保证原子性的普通自增与 AtomicInteger 比速度后说原子操作没必要。本文没有执行锁微基准，源码布局也不宣称适用于所有 JVM/ART 版本。
