## 1. 如何按状态理解 Activity 回调？

原帖位置：Android 1。

### 参考回答

onCreate 建立实例与恢复状态，onStart 进入可见，onResume 进入可交互的 resumed 状态；失去前台主导时通常 onPause，不可见时 onStop，实例结束时可能 onDestroy。暂停不一定不可见，停止也不代表已被销毁；进程被杀不保证收到 onDestroy。

### 原理与继续追问（编辑扩展）

资深回答还应解释窗口焦点与生命周期不等价，多窗口可有多个 resumed Activity。数据保存不能赌 onDestroy，一次业务提交也不能无条件放在每次 onCreate。追问进程恢复时，用可保存少量状态重建入口，以持久数据恢复业务事实。

继续学习：[状态恢复](#/article/state-restoration)

## 2. A 打开 B 时常见回调怎样交错？

原帖位置：Android 2。

### 参考回答

限定普通全屏 Activity、A 已 resumed、B 新建且没有特殊窗口模式：常见顺序是 A.onPause → B.onCreate → B.onStart → B.onResume → A.onStop。A 停止的前提是被完全遮挡；透明 B、配置变化与多窗口不能机械套用这一序列。

### 原理与继续追问（编辑扩展）

系统协调前台与可见状态，不是 A 所有回调全部完成后 B 才开始。onPause 要快速返回，不能在这里同步落盘大文件或等待网络，否则 B 的展示也可能受影响。验证时记录实例 ID、任务和窗口条件，而不是只打印方法名。

继续学习：[生命周期边界](#/article/state-restoration)

## 3. B 结束后 A 如何恢复？

原帖位置：Android 3。

### 参考回答

限定 A 的实例仍在、处于 stopped，B 正常 finish：常见路径为 B.onPause，A.onRestart/onStart/onResume，随后 B.onStop/onDestroy。若 A 进程或实例已不存在，则是重建路径，需要 onCreate 与恢复数据，不能期待旧 ViewModel 一定在。

### 原理与继续追问（编辑扩展）

不要把“返回上一页”直接等同于读取内存中旧对象。通过系统保存的标识与持久库恢复页面；若 A 正在进行的业务已经完成，返回时应读当前业务事实而不是重放原点击事件。

继续学习：[恢复设计](#/article/state-restoration)

## 4. 怎样定义并识别常见泄漏？

原帖位置：Android 4。

### 参考回答

对象已经不再被业务需要，却仍被存活对象强引用而无法回收。Android 常见是单例持 Activity、监听未注销、延迟任务捕获页面、Fragment 销毁 View 后仍保留 binding。泄漏不同于合理缓存或一次内存尖峰。

### 原理与继续追问（编辑扩展）

GC 依据可达性而非业务语义。应从异常存活对象追到 GC Root，确认保留者寿命为何更长；弱引用只改变可达性，不解决过期任务和资源关闭。大对象分配失败只是结果，未必是增长源。

继续学习：[内存原理](#/article/memory-art) · [泄漏定位](#/article/oom-diagnosis)

## 5. 延迟消息怎样留住页面？

原帖位置：Android 5。

### 参考回答

存活线程持有 Looper/队列，队列消息持 Handler 或 Runnable，它们又可能捕获 Activity。即使 Handler 是静态类，Runnable 闭包仍可能保留页面。应取消页面归属回调并避免不必要捕获，长期工作由更合适的 owner 管理。

### 原理与继续追问（编辑扩展）

追问时画出真实引用链，不回答“Handler 天生泄漏”。专用 token 比共享 Handler 上删除全部消息更安全；取消与回调执行可能竞争，结果还需校验页面是否仍有效。队列中的预期延迟也不保证准点执行。

继续学习：[消息执行与引用链](#/article/handler)

## 6. 用什么证据确认泄漏已修复？

原帖位置：Android 6。

### 参考回答

可用泄漏检测工具发现疑似保留，再用 heap dump 的引用路径和 retained size 分析。固定操作脚本反复进入退出页面，比较实例数量和内存增长平台；只看一次 GC 后没回收不足以证明长期泄漏。

### 原理与继续追问（编辑扩展）

如果 Java 堆稳定而 PSS 上涨，需要检查 Native、线程栈、映射和图形资源。修复后既要看保留链消失，也要看是否以频繁重新加载换来卡顿。线上 OOM 归因需结合设备与实际场景。

继续学习：[证据闭环](#/article/oom-diagnosis)

## 7. Activity 和 Fragment 的责任与生命周期差在哪？

原帖位置：Android 7。

### 参考回答

Activity 是系统管理的应用组件和窗口宿主；Fragment 是受宿主管理的 UI/逻辑单元，不是独立系统组件。Fragment 自身生命周期与其 View 生命周期不同，View 可在 Fragment 仍存活时销毁并重建。

### 原理与继续追问（编辑扩展）

最常见错误是用 Fragment 的较长生命周期观察数据并更新已经销毁的 View。绑定 viewLifecycleOwner，及时清除 binding；嵌入 Compose 时也让 Composition 的释放策略匹配 View 生命周期。

继续学习：[双生命周期](#/article/state-restoration) · [互操作](#/article/compose-effects)

## 8. Activity 与 Fragment 如何共享状态和返回结果？

原帖位置：Android 8。

### 参考回答

按语义选择：持续共享页面状态可使用明确作用域的 ViewModel；一次性可保存小结果可用 Fragment Result API；跨 Activity 使用 Activity Result API 或稳定标识参数。直接强转宿主并调用其内部方法会增加耦合，传整棵大对象图也不适合重建。

### 原理与继续追问（编辑扩展）

先问数据所有者是谁、需活多久、是否跨进程恢复。返回“订单 ID”通常比传可变订单实例稳妥，接收方读取权威状态。作用域过大会串页面，过小则无法共享；不要用全局事件总线掩盖所有权问题。

继续学习：[状态归属](#/article/state-restoration)

## 9. 散列表查找与扩容如何工作？

原帖位置：Java 1。

### 参考回答

HashMap 根据 hash 定位桶，再用相等比较确认 key。容量和负载控制冲突与空间开销，达到条件后扩大存储并重新分布条目。某些 JDK 实现使用链表/树化桶，但必须声明版本；Android 与其他平台不保证逐字采用同一实现。

### 原理与继续追问（编辑扩展）

以常见二次幂容量实现为例，扩容加倍后可利用新增的一位 hash 判断条目留原桶还是移到旧容量偏移处。该解释属于实现细节，不能泛化所有 map。可变 key 改变 hash 后查找失败，比背阈值更能体现理解。

继续学习：[集合与键稳定性](#/article/collections)

## 10. 并发修改 HashMap 会发生什么？

原帖位置：Java 2。

### 参考回答

它不提供无同步并发修改保证。竞争可能丢更新、观察不一致状态或破坏结构；具体表现依实现与交错而异。迭代器的 fail-fast 是尽力检测错误，不是同步协议，也不能说所有 JDK 都必然出现同一种死循环。

### 原理与继续追问（编辑扩展）

即使单次 get 看起来正常，也不代表 get-判断-put 这一复合操作原子。需要用 JMM 的同步关系解释可见性，再用不变量解释原子性。日志和 sleep 可能改变竞态，却不能建立正确性证明。

继续学习：[JMM](#/article/jmm-concurrency) · [集合边界](#/article/collections)

## 11. 怎样选择并发 map 的保护方式？

原帖位置：Java 3。

### 参考回答

可用外部锁保护整个不变量、合适同步包装，或用 ConcurrentHashMap 等并发容器。若涉及多步关联更新，多个线程安全方法仍未必组成事务；按需求使用 putIfAbsent/compute 等原子操作，或更高层锁。

### 原理与继续追问（编辑扩展）

ConcurrentHashMap 迭代不等于某个时点的严格全量快照，不能把它直接作为财务结算一致视图。compute 回调应短小并遵守重入约束；高竞争时应测吞吐、尾延迟与锁等待，而非相信“并发类一定最快”。

继续学习：[复合不变量](#/article/jmm-concurrency)

## 13. 怎样回答项目使用的网络框架？

原帖位置：项目与网络 2。

### 参考回答

需要按真实项目回答。若使用 Retrofit + OkHttp，可说明 Retrofit 负责声明式接口与适配/转换，OkHttp 承担 HTTP 调用、连接、缓存等；业务 Repository 再负责数据来源与错误语义。库的职责与业务层分开讲。

## 14. 如何理解使用拦截器和内部职责链？

原帖位置：项目与网络 3。

### 参考回答

请求交给 Call，拦截器围绕 chain.proceed 组织前后处理。典型内部职责是重试/后续请求、Bridge、缓存、连接与最终网络交换。应用拦截器围绕逻辑调用，网络拦截器围绕网络交换，所以缓存命中和重定向时执行次数可能不同。

### 原理与继续追问（编辑扩展）

读完或丢弃响应体要关闭；多次 proceed 需遵守层级契约，网络拦截器不能任意多次调用。鉴权刷新要防并发风暴和递归拦截；一次性上传体不能无条件重试。内部类名与顺序应按锁定版本核对。

继续学习：[完整拦截链](#/article/okhttp-chain)

## 15. 缓存响应怎样决定使用还是验证？

原帖位置：项目与网络 4。

### 参考回答

先判断允许存储与请求匹配，再判断新鲜度。新鲜且规则允许则直接复用；陈旧可带 ETag/If-None-Match 验证，304 时组合已有实体与更新元信息。no-cache 要验证，no-store 不存储，不能混用。

### 原理与继续追问（编辑扩展）

Vary 参与匹配，授权和共享缓存有额外约束。协议缓存与业务数据库不同，账号隔离和过期展示应由业务进一步设计。不能强改所有服务端缓存头来刷高命中率。

继续学习：[缓存细节](#/article/http-cache)

## 16. 文件传输需要哪些接口请求之外的设计？

原帖位置：项目与网络 5。

### 参考回答

下载通常需要流式写盘、进度、容量检查、取消、失败恢复与完整性校验，不能将大 body 全读进内存。先写临时文件，完成校验后按文件系统条件安全切换，避免用户看到半成品。

### 原理与继续追问（编辑扩展）

续传用 Range 等协议时验证响应状态与 Content-Range，并确认资源版本未改变；服务端若返回完整 200，不能直接追加到旧文件。上传重试同样要确认服务端已接收偏移和业务幂等，关闭连接不等于未上传。

继续学习：[续传与幂等](#/article/network-reliability)

## 17. HTTP 的可靠性应该在哪一层讨论？

原帖位置：网络 1。

### 参考回答

HTTP 定义请求响应语义；HTTP/1.1、HTTP/2 常运行于 TCP，HTTP/3 基于 QUIC。传输可靠有序不等于业务恰好执行一次，客户端超时后服务端仍可能已提交。回答时分开传输交付、协议响应和业务成功。

### 原理与继续追问（编辑扩展）

支付请求结果未知时查询请求 ID 或使用幂等协议，而不是凭 TCP 没报错就显示成功。服务端返回 200 也还要按业务契约解释，HTTP 状态并不自动证明业务数据一致。

继续学习：[协议分层](#/article/tcp-tls) · [业务确认](#/article/network-reliability)

## 18. TCP 怎样处理丢包与乱序？

原帖位置：网络 2。

### 参考回答

通过序号、确认和重传等机制实现有序字节流，流量控制保护接收方，拥塞控制适应网络容量。接收端可以重组与去重，但 TCP 不保留应用消息边界，read 次数不对应 write 次数。

### 原理与继续追问（编辑扩展）

应用必须定义消息帧。即使字节到达对端协议栈，业务仍可能未读取或未提交。抓包确认与业务日志需要对应；高 RTT 和丢包会放大重传尾延迟，更多并发未必有利。

继续学习：[传输原理](#/article/tcp-tls)

## 19. 连接建立与双向关闭为何需要这些交互？

原帖位置：网络 3。

### 参考回答

三次握手同步双方初始序号等状态并确认双向通信；只发两次时服务端缺少客户端对其建立信息的确认，也难正确处理旧重复请求等情况。关闭是两个方向各自结束发送，因此常见 FIN/ACK 往返，但 ACK 与 FIN 可合并，抓包未必固定四个报文。

### 原理与继续追问（编辑扩展）

TIME_WAIT 与旧报文隔离、连接关闭可靠性等相关；RST 是另一种终止，不是优雅关闭的替代词。半关闭时一端可不再发送却继续接收。进一步应能把协议状态与连接池陈旧连接问题联系起来。

继续学习：[握手与关闭](#/article/tcp-tls)

## 20. 如何原地反转链表的指定区间？

原帖位置：算法。

### 参考回答

原帖题名对应 [LeetCode 92：反转链表 II](https://leetcode.cn/problems/reverse-linked-list-ii/)。用 dummy 统一处理从头反转，先走到 left 前驱 pre，cur 指向区间首节点。重复 right-left 次：摘下 cur.next，把它插到 pre 后。cur 一直是已反转部分的尾，因此外部链路可以保持连接。

### 原理与继续追问（编辑扩展）

不变量是 pre 前的链不变，pre 后是已反转区间，cur 后是未处理区间。每次先保存待移动节点，更新 cur.next，再连接待移动节点到 pre.next，最后更新 pre.next，避免丢链或成环。时间 O(n)、额外空间 O(1)。测试 left=right、从头到尾、单节点与尾区间；现场约束不保证合法时需单独校验。
