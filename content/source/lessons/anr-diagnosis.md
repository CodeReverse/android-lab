## 1. 先确认谁在等待应用响应

用户点击刷新后界面无响应，报告里出现 ANR。第一步不是搜索“主线程五秒”，而是确认具体触发类型：输入分发、广播、服务等有不同的监测对象和条件，超时策略还受系统版本、前后台状态等影响。ANR 是系统认为某项响应责任没有及时完成，不等于所有情况都是某个 Java 方法运行超过固定秒数。

保留触发原因、时间、进程/线程、设备版本、前后台状态与相邻业务事件。若只拿到一份很晚采集的主线程栈，可能已经错过真正的阻塞。类型与边界先核对 [Android ANR 指南](https://developer.android.com/topic/performance/issues/anr)。

## 2. 用等待链把“卡在 synchronized”展开

教学案例：刷新需要读取缓存状态，主线程进入 synchronized 后阻塞；后台同步线程持有同一把锁，同时执行远程调用。

```text
main → 等 cacheLock
worker 持 cacheLock → 等 Binder 回复
remote worker → 等数据库事务
```

只把主线程这行改成后台调用，可能隐藏表面卡顿，却没修正持锁区过长和远端资源瓶颈。应查锁由谁持有、持锁者在做什么，再查它依赖的下游。若形成 A 等 B、B 又等 A 的环，才有死锁证据；只有长等待不能直接叫死锁。

修复可以在锁内取快照，锁外做 I/O，再按版本条件写回。这样缩短等待，但需要处理快照变旧；如果无条件覆盖新状态，就用并发正确性换了流畅度。锁语义见 [Java 锁](#/article/java-locks?section=7)，跨进程重入见 [Binder](#/article/binder?section=4)。

## 3. 线程在栈上“运行”不等于一直拿到 CPU

面对相同的用户卡顿，trace 可能显示三种路径：

|证据|更接近的假设|下一步|
|持续在 CPU 上执行解析|计算过多或重复工作|采样热点、输入规模、重复次数|
|等待 monitor / Binder / I/O|依赖没有完成|追持有者与下游等待链|
|可运行却长时间没被调度|CPU 竞争或调度压力|看其他线程/进程、优先级与负载|

这张表是诊断分支，不是仅凭一帧栈就能下的结论。Java RUNNABLE 与系统调度轨迹也不是完全相同口径。把 GC、磁盘、Binder 和业务 trace 标记放在共同时间轴上，才能判断哪段真的占据了响应窗口。

若主线程栈停在 nativePollOnce，可能正在正常等待，也可能故障过去后才采样。官方诊断文档同样强调采样时机与不同 ANR 类型，见 [诊断和修复 ANR](https://developer.android.com/topic/performance/anrs/diagnose-and-fix-anrs)。

## 4. 把工作移到后台后仍要控制排队

设每次刷新创建十个 CPU 任务，用户连续操作五次。即使主线程不直接计算，后台线程竞争 CPU、持锁回传或一次性大量发布结果，也会影响界面。后台化只改变执行位置，不减少总工作，也不提供背压。

可先合并重复请求、取消失去业务意义的任务，再按资源设置并发上限。主线程只接收必要的状态变化；对不可取消任务加结果代次校验。不要在主线程 `Future.get` 等待“已经移到后台”的工作，那又把等待接了回来。线程池路径见 [线程第 4–6 节](#/article/java-threads?section=4)。

## 5. 证明修复的是因果链

教学验证先固定触发动作与数据规模，再人为控制远端延迟或锁持有时间。修复前应能观察主线程等待链；修复后应看到主线程不再依赖该长等待，同时业务结果没有旧值覆盖或重复提交。

线上比较要保留 ANR 分母、版本、设备与触发类型，避免“报告数量下降”只是活跃人数变少。灰度阶段还要看失败率和数据一致性，不能用静默吞错换低 ANR。本文未声称运行实验或取得下降百分比；如何整理证据见 [项目成果证据](#/article/project-evidence)。
