## 1. 把“要不要跨端”改写成可回答的问题

教学场景：两端各维护一套优惠规则，经常出现结果不一致。有人建议整个交易页迁到 Flutter，也有人主张 KMP，还有人认为保持原生即可。框架名是候选方案，问题却是规则一致性与交付成本。

先写清约束：UI 已成熟，支付接入平台差异大，规则变化频繁，团队需要能独立回退。这些是本例设定，不是行业统计。若只为共用规则，全量 UI 重写可能扩大了变更面；如果真正痛点是两端交互长期不同步，只共享逻辑又可能不够。技术决策从目标和约束出发，才能避免拿自己最熟悉的工具替问题定形。

## 2. 基线方案也应进入比较

至少比较“保留原生并共用契约测试”“共享领域逻辑”“共享整个页面”。第一种不酷，却可能以最小风险消除大部分规则偏差。比较表不先打分，而先写作用机制：

|方案|怎样解决当前问题|新成本|
|---|---|---|
|双端实现 + 共用用例|以相同输入输出检测规则偏差|规则仍写两份，修复需协调|
|共享领域模块|同一规则实现服务两端|跨语言构建、异步与平台适配|
|共享页面|进一步统一交互实现|渲染、插件、导航、迁移与回退|

权重可以帮助讨论，但不能把未经测量的“性能 9 分”伪装成事实。对不确定项标记待验证，比算出漂亮总分更有用。技术机制分别见 [KMP](#/article/kmp-boundaries)、[Flutter](#/article/flutter-runtime) 和 [RN](#/article/rn-architecture)。

## 3. Tech spike 只验证最危险的假设

本例最大的未知可能不是代码能否编译，而是 iOS 取消订阅时能否停止共享层任务，以及团队能否稳定调试线上异常。一个只展示 Hello World 的 demo 不能回答这些问题。

可以选择一条“加载规则—本地缓存—取消—错误恢复”的窄流程，固定成功条件：两端规则输出一致，取消后资源释放，异常能定位到共享代码，旧实现可接回。再测构建、包体和响应时间。阈值应由产品预算与现状决定，而不是抄行业数字。

```text
假设：共享逻辑可减少规则漂移
证据：相同契约用例在两端运行；确认失败是实现差异还是输入差异
反例：平台时间/舍入/序列化让相同规则得到不同输入
继续条件：关键反例可控，且维护成本在团队预算内
```

以上是试验设计，不是已取得结果。试验的价值在缩小不确定性；“暂不采用”同样可以是有效产出。

## 4. ADR 记录选择发生的条件

决策记录应该让半年后的同事知道：当时为什么选它，哪些代价是主动接受的，什么变化会要求重新评估。结构可参考 [Architecture Decision Records](https://adr.github.io/)，本例可写成：

```text
状态：待验证
范围：优惠规则模块；不包含支付 UI
备选：双端原生 + 契约测试 / 共享领域模块 / 共享页面
决定：在试验满足退出条件后，先迁移纯规则
接受的代价：增加共享构建与版本协调
复审触发：平台能力大量渗入共享层，或调试成本超出预算
```

这里“待验证”不能在汇报里变成“已落地”。决定与证据状态分开，才不会用目标描述冒充成果。来源提供记录方法；具体选择是针对本教学约束的推理，不代表框架作者或某公司的统一结论。

## 5. 把可逆性写进实施路径

用接口隔开新旧实现，在无副作用的规则计算阶段可双跑比较结果，再让部分流量使用新实现。双跑不能无脑用于支付、发送消息等副作用操作，否则一次业务被执行两遍。

回退应说明切回旧实现后数据是否仍兼容、配置何时生效、未完成任务由谁接管。若新格式旧代码不认识，开关并不构成真正退出路径。架构迁移细节见 [架构演进](#/article/architecture-evolution)。

最终评审回答的不是“我选了哪个框架”，而是“这个选择如何满足当前目标，证据到什么程度，失败时怎样收敛影响”。这也让面试追问能落到具体约束，而不是技术偏好。
