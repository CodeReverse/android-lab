## 1. 单请求很快，服务却可能很慢

这里的 serving 指把模型包装成可同时服务多用户的系统：接请求、安排设备计算、返回结果并释放资源。batch 是一次共同组织计算的一组输入；吞吐量是单位时间完成多少工作，延迟是一个请求等待多久。TTFT 是 time to first token，即首 token 时间。它们像线程池吞吐与单任务等待一样相关，但不能互相替代。

本地模型生成很快，上线后用户等待很久。端到端延迟包含排队、输入处理、Prefill、逐步 Decode 和网络交付；增加 GPU 利用率不一定降低每个人的等待。

```text
请求进入 → 准入/排队 → Prefill → Decode 多步 → 完成/取消
```

先分别记录 TTFT、token 间隔、总完成时间、成功率和吞吐。短问答与长文总结的输入/输出分布不同，不能只用一个平均 tokens/s 排名。缓存与计算基础见 [推理原理](#/article/ai-inference)。

## 2. 连续批处理让完成的空位及时复用

教学例子：A 还需 2 个 token，B 还需 5 个。静态批次若等整批结束再接受 C，A 完成后的容量可能闲置；连续批处理在迭代边界调整活跃请求，让 C 有机会进入。

```text
步 1：A B
步 2：A B   A 完成
步 3：B C
步 4：B C
```

实际还需安排 C 的 Prefill，不能把它当成零成本插队。长 Prefill 可能干扰已有请求的 token 间隔，分块 Prefill 等策略用于权衡；不同框架/版本实现不同。连续调度与 KV 管理相关但不是同一机制，背景见 [PagedAttention 系统论文](https://arxiv.org/abs/2309.06180)。

## 3. 排队限制比无限接受更能保护服务

活跃请求越多，KV 越大，显存不够时可能抢占、重算或失败；即使没 OOM，排队也可能早已超出用户预算。准入需要按输入长度、最大输出、可用缓存与优先级判断，而非仅按请求数。

```text
若预计工作量超过预算：拒绝/降级/延后
若用户取消：停止后续计算并回收对应资源
若超出截止时间：终止无价值的继续生成
```

这是工程策略伪代码。长请求可能需要公平调度，避免短请求优先导致长期饥饿；高优先级也不能无限抢占其他租户。限流、重试退避和服务端准入要配合，否则客户端重试会把拥塞放大。

## 4. 投机解码用便宜的草稿换目标模型并行验证

小模型先提出多个候选 token，大模型对这些候选计算验证信息，接受合适前缀并在必要处修正。直观收益是减少目标模型串行迭代次数；代价是草稿计算、验证与被拒绝的无效工作。

精确采样版本不是“只要大模型觉得差不多就接受”。它需要按目标/草稿概率进行接受拒绝和校正，才能在相应假设下保持目标分布；贪心验证和近似变体又有各自条件。依据 [Speculative Decoding](https://arxiv.org/abs/2211.17192)。

若草稿很慢、接受率低，或者当前负载下批处理已充分利用硬件，收益可能消失。不能直接承诺固定倍数加速，应同时报告接受率、输出质量契约和端到端延迟。

## 5. 成本要按成功完成的任务算

每 token 价格/成本便于计量，却可能奖励冗长输出。一个便宜模型重试三次仍失败，可能比贵模型一次完成更浪费；相反简单任务无需总用最大模型。

按任务定义成功后，可估算“总计算与服务成本 / 成功任务数”，同时保留失败、重试和人工接管成本。模型路由需有校准数据，不能只让模型自报置信度决定风险。前缀缓存可降低重复输入处理，但缓存命中由请求结构和隔离规则决定，固定实现见 [vLLM 0.8.4](https://docs.vllm.ai/en/v0.8.4/design/automatic_prefix_caching.html)。

## 6. 负载测试应重放真实分布

构造长短输入、不同输出长度、到达突发与取消，逐步提高负载，观察排队何时快速增长、尾延迟何时失控、内存何时接近上限。只用同一短 prompt 循环测试，会高估缓存命中并低估真实波动。

保存硬件、模型精度、服务版本、调度参数与质量基线。本文时间线是教学推演，没有报告真实服务吞吐；评估数据与线上实验见 [AI 质量工程](#/article/ai-quality)。
