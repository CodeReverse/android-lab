## 1. 体验与成本指标

一个知识问答服务的总耗时可拆为准入排队、检索重排、输入处理、首轮生成、后续生成和网络输出。某环节慢，不意味着都应该换模型。用请求 trace 将队列等待与模型执行分开，记录输入／输出 token、缓存命中、模型 revision、工具耗时和取消状态，才能比较方案。

至少定义 TTFT、token 间隔、完整任务时延、成功率和单次成功任务成本。吞吐以 tokens/s 和完成任务数分别观察；把短回答改成长回答会提高 token 吞吐，却未必创造更多用户价值。

## 2. 静态批次与连续批处理

静态 batching 将一组请求绑定执行，短请求完成后可能等待长请求，资源利用不充分。连续批处理在生成迭代边界移出完成请求，加入等待请求，使运行中的序列动态变化。它不是无限增大 batch：KV 内存、计算吞吐与单请求 token 间隔都会成为约束。

长 prefill 可能挤压已有 decode；可考虑分块 prefill、优先级和每轮 token 预算。策略之间存在吞吐与尾延迟取舍。单独把 prefill 和 decode 部署到不同资源池可以按瓶颈扩容，但会增加 KV 传输、路由和容量配比复杂性，小流量场景未必值得。

## 3. 投机解码的收益条件

小模型或其他草稿机制先提出一串 token，目标模型并行验证。经典严格采样算法通过接受／拒绝与校正，使最终分布与目标采样分布相符；不能把“目标模型觉得差不多就全部接受”当成该保证。

收益取决于接受率、草稿成本、验证并行性和额外内存。任务风格与草稿模型不匹配，反复拒绝会变慢。确定性贪心场景和随机采样场景也需分别对齐算法。测试不能只展示一个短 prompt 的最佳速度，应按实际输入长度和任务类别分层报告。

## 4. 容量、排队与准入

稳定系统的平均在途数量可用 Little 定律 L=λW 检查。例如到达率 20 请求/秒，平均在途时间 5 秒，平均约 100 个请求同时处于系统中；这不是 GPU batch 必须等于 100，因为其中一部分在检索或等待。该关系要求稳定平均，不应用来推导极端突发流量的 P99。

按预计 token 预算而非只按请求数准入，避免少数长上下文把 KV 吃光。队列必须有长度和等待上限，过载时可以拒绝、切小模型或降低上下文预算；每种降级都要明确用户可接受的质量损失。盲目重试超时请求会把过载放大。

## 5. 缓存与模型路由

单次成功任务成本应包含推理、向量化、重排、工具、重试及失败成本。小模型便宜但频繁失败，端到端未必便宜。路由以任务复杂度、数据敏感性、所需工具、延迟预算为依据，离线评测后灰度验证；不能仅听模型自报“我能处理”。

共享前缀适合 KV 缓存；稳定且权限一致的问答可以评估最终答案缓存。缓存键要覆盖模型、知识版本、权限和影响结果的参数，不能把不同账号的个性化上下文复用。采用语义缓存还需测误命中，语义相近的“允许”和“不允许”不是相同请求。

## 6. 吞吐和时延的权衡验证

**GPU 利用率高，用户仍然慢？** 利用率只表明某些计算资源忙，不能区分排队、内存带宽、长 prefill 阻塞、低效内核和工具等待。要看阶段耗时、显存、带宽、请求长度分布及 token 间隔。

**该怎样证明连续批处理有效？** 固定模型和到达过程，用包含长短请求混合的回放，对比吞吐、TTFT、TPOT、P99 和峰值内存，包含低载与过载区间。只用无限并发压榨峰值吞吐无法证明交互体验。

**生产怎么回滚？** 将调度参数、模型、模板、量化格式分别版本化，保留原资源池与冷启动容量，使用相同请求标识防止重试重复调用业务工具。本文是设计推演，未执行服务压测。
