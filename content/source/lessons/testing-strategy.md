## 阅读方式

按定义、结构、运行过程、实现细节、故障与验证逐层阅读。问题顺序由本站编写；文末面经映射只证明相应主题被问过，不代表原帖出现了本篇全部追问。每问下方即为对应讲解。

## 第 1 问：测试策略怎样围绕最昂贵的失败建立？

测试策略不是追求某个统一覆盖率数字。支付重复提交、账号串数据、进程恢复丢草稿，与按钮颜色偏差有不同风险。先列关键业务不变量，再选择在哪一层以最低成本验证：纯业务规则适合本地单元测试，存储迁移需要真实数据库，平台生命周期需要设备或相应环境，关键旅程需要端到端验证。

每个测试应能说明防止什么回归。大量 mock 后只验证某方法调用一次，可能只是镜像当前实现，重构时全碎却没有保护用户行为。

## 第 2 问：状态机为什么比零散布尔值更易验证？

登录流程可能有 idle、loading、authenticated、error；并发请求与取消会引入过期响应。把合法转换和结果接受规则写清，测试“取消后旧成功到达”“新请求失败但旧请求成功更晚到达”等交错，比只测 happy path 更有价值。

协程测试调度器可控制虚拟时间，适合验证超时、退避和流操作，但它不等价真实线程竞争。锁、阻塞 I/O 和 native 调用需要另外的并发或设备验证。使用虚拟时间后不能以测试运行快为理由省略真实平台路径。

## 第 3 问：契约测试怎样保护跨模块与跨进程边界？

Repository 的契约应说明错误、取消、缓存与一致性语义。新旧实现都跑同一组行为测试，有助于架构迁移；网络协议测试可模拟超时、异常响应和重定向。测试替身应忠于关键行为，不能把真实可能失败的操作永远写成即时成功。

数据库迁移测试需要从受支持旧版本的 schema 与数据升级，检查约束、索引与业务可读性；只从空库创建最新版不能覆盖升级用户。发布回滚若涉及旧代码读取新数据，也应有明确兼容测试或禁止回退的条件。

## 第 4 问：UI 测试应该验证哪些真实用户结果？

Compose 的语义树适合按可访问语义查找与断言，减少依赖内部布局实现。仍需少量真实设备旅程验证输入法、返回导航、权限和跨 View/Compose 边界。把所有情况都放进昂贵 UI 测试会让反馈慢且易抖动，应将可下沉的规则下沉。

截图测试能发现视觉变化，但不能证明业务正确或无障碍可用。固定字体、密度和环境减少噪声；允许更新基线时应审查变化，而非每次失败自动接受新图。

### 逐层追问与回答支点

- 覆盖率很高为什么仍出事故？覆盖执行不代表断言正确，更不代表覆盖关键交错与真实平台限制。
- flaky 测试怎么办？先查隐含等待与共享状态，使用确定性同步；简单扩大 sleep 会拖慢并掩盖根因。
- 哪些测试进发布门禁？优先稳定、高风险、高信号用例，其余安排合适频率与失败处理。

## 第 5 问：怎样判断测试真的能拦住历史故障？

选一个离线提交流程，写出五个不变量，分别映射到规则测试、真实数据库测试、协议测试和一条端到端旅程。检查是否有重复且低价值的用例，并记录每个失败应该由谁处理。
