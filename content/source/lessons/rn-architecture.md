## 1. Bridge 到 JSI、Fabric 与 TurboModules

旧架构常以异步序列化 Bridge 连接 JS 与原生。新架构引入 JSI、Fabric 与 TurboModules 等机制，减少部分旧边界限制，并改变模块和渲染协作方式。面试若只回答“RN 就是 JSON Bridge”，会忽略已演进的执行模型；但也不能据此说跨语言调用成本已消失。

JSI 提供 JS 与 C++ 交互能力，具体模块可以据此实现同步或异步接口。同步调用会占用调用线程，因此“可以同步”不意味着“应该把耗时原生工作同步执行”。CPU、内存、线程亲和与错误处理仍要显式设计。

## 2. JS 与原生 UI 的更新链

React 根据状态生成描述，Fabric 的渲染体系围绕 Shadow Tree 等结构计算与提交，再挂载到宿主视图。布局和挂载有各自阶段与线程约束。不能假定所有新架构工作都在 JS 线程，也不能把它理解成完全摆脱主线程的渲染器。

TurboModules 改善原生模块加载和类型接口等问题，Codegen 为跨边界接口提供生成支持。JS 包、生成接口与 Android/iOS 实现需要版本兼容；仅 TypeScript 编译通过并不证明 native 方法已存在且语义一致。

## 3. 跨边界后的性能成本

一个 JS 侧昂贵的列表处理仍会占用 JS 执行时间，大量 UI 更新仍需布局与挂载，图片解码和原生控件仍有平台成本。若每帧把海量对象在边界间创建和传递，移除旧序列化瓶颈后还会暴露新的分配与调度瓶颈。

应分别看 JS 工作、React render/commit、原生挂载、UI 线程与 GPU。将任务全部包进 memo 不一定有效；props 不断创建新对象、长列表身份不稳定、组件职责过大等都可能抵消收益。

## 4. 依赖、团队与发布约束

RN 对有 React/JS 经验的团队具有复用优势，也便于与原生控件能力结合。但依赖生态、原生模块新架构兼容、版本升级与双平台调试构成长期成本。动态代码更新的能力还受渠道规则、包兼容和回滚协议限制，不能承诺绕过平台分发约束。

混合应用需要建立 bundle 与 native 能力版本协商，确保新 JS 不调用旧安装包尚未实现的接口。灰度时按宿主版本筛选，回滚时确认本地数据结构与服务端协议仍兼容。只回退 bundle 未必能回退数据副作用。

## 5. 兼容性与性能验证

锁定 RN 版本和架构模式，盘点每个 native module 的支持状态。对高频交互、复杂列表和跨边界批量调用进行 trace，并对 JS/native 版本不匹配、模块加载失败和回滚做故障演练。
