## 阅读方式

按定义、结构、运行过程、实现细节、故障与验证逐层阅读。问题顺序由本站编写；文末面经映射只证明相应主题被问过，不代表原帖出现了本篇全部追问。每问下方即为对应讲解。

## 第 1 问：Function Calling、MCP、Skill、Memory、Harness 有何区别？

|概念|负责什么|不能据此推断什么|
|---|---|---|
|Function Calling|模型输出结构化的工具名与参数建议|不代表参数合法或已获得业务授权|
|MCP|宿主与外部服务之间约定发现、交互等协议|不是模型，不自动替代应用权限判断|
|Skill|可复用的任务说明、流程或资源组织方式，具体约定随产品不同|不是统一的模型能力保证，也不是任意代码的通行证|
|Memory|跨步骤或跨会话保留的状态／事实|不是越多越好，不等于真实且永久有效|
|Harness|围绕模型的运行环境、控制循环、工具、验证与恢复等工程支撑|不是单独的提示词模板|

RAG 负责给生成提供外部证据；Function Calling 负责提出结构化动作，两者可以组合：调用检索工具是一种动作，返回的证据进入后续生成。一个术语描述知识路径，另一个描述动作接口，不能简单比较谁“更高级”。

## 第 2 问：模型提出工具调用后谁校验、授权和执行？

将工具描述与参数 schema 提供给模型 → 解析调用建议 → 验证工具名和参数结构 → 解析当前用户与资源权限 → 执行业务约束 → 调用后端 → 标准化结果 → 回送模型或直接渲染。schema 只能约束形状；一个格式正确的他人订单 ID 仍可能越权。

校验失败时给模型可操作的错误，例如字段缺失或范围限制，并限制纠错次数。认证错误、资源不存在、冲突、可重试故障应分别处理，不把所有错误转成“再试一次”。工具结果属于外部数据，其中的自然语言不应获得新的指令权限。

## 第 3 问：MCP 怎样分配宿主、客户端与服务端职责？

以本文固定引用的 2025-11-25 架构规范为基础，宿主负责用户交互与协调，客户端与服务端建立协议连接，服务端提供相应能力。协议协商与能力发现解决互操作问题；工具能否针对某个账号、某个对象执行，仍由应用策略和后端校验。

认证身份不是无限授权；读工具与写工具、测试环境与生产环境的能力应分开。发现工具时不能仅按名称信任描述，工具更新和服务端身份变化应进入配置审核。协议版本持续演进，项目必须锁定双方兼容版本，本篇不宣称所引用版本是最新版本。

## 第 4 问：上下文预算怎样分配，压缩会丢失什么？

上下文是有限预算：系统约束、用户目标、当前计划、已确认事实、工具定义、检索证据、历史观察之间需要分配。优先保留当前任务不可丢的约束和原始事实定位，减少重复日志、过期观察与大段无关文档。摘要必须标明是派生信息，并能回查原始证据。

长会话压缩不应把“计划做”改写成“已经做”，也不能丢失否定、单位、时间或权限边界。工具返回大型文件时先存对象和索引，按需读取片段；不要让所有子 Agent 共用整个对话堆栈。

## 第 5 问：长期 Memory 怎样避免越权、过期和错误污染？

短期状态可保存在 run 的 checkpoint，长期偏好或事实放在带用户 ID、来源、时间、有效期和置信状态的存储。读取前按用户与任务过滤，更新时区分新事实、纠正与推测，支持删除及失效。把模型推测直接写成长期事实，会让错误在后续对话中自我强化。

例如用户说“出差时可能去上海”，不能永久记录为“居住上海”。内容即使被向量化，也仍是用户数据，不因为变成 embedding 就天然匿名。安全边界需覆盖日志、缓存、备份和删除链路。

## 第 6 问：怎样验证注入防护、Skill 粒度与 Harness 作用？

**恶意文档让 Agent 忽略规则怎么办？** 标记检索结果为不可信数据，服务端坚持权限与参数校验，写操作采用受控动作集合。提示词只是一层辅助，不能替代执行器边界。构造包含假指令的文档并检查是否触发不应发生的调用。

**Skill 粒度怎么定？** 围绕可独立验收的任务封装输入、输出、适用条件、错误处理和示例；太大难组合，太碎增加选择与维护成本。用任务完成率、误调用率和总开销评估，不按说明字数评分。

**为什么已经有框架还需要 Harness？** 框架可能提供基础节点与存储，但预算、环境隔离、业务验证、审批边界和恢复语义仍要由项目实现。能展示失败轨迹与恢复结果，比罗列名词更有说服力。
