## 1. JMM 与内存区域

Java Memory Model 规定多线程执行中哪些读写观察是允许的，以及同步如何约束这些观察。JVM 运行时分区讨论堆、栈、方法区等结构，两者不在同一层。对象位于共享堆，不代表对其字段的并发读写天然安全。

用“线程私有缓存刷回主内存”可以粗略帮助入门，但不能把它当成 JMM 的完整定义；编译器优化、处理器排序和运行时都必须满足规范可观察行为。

## 2. 可见性、原子性与有序性

可见性关心一个线程的写何时能够按规则被另一个线程观察；原子性关心操作是否会被观察为可交错的多个步骤；有序性关心允许的执行与观察顺序。线程安全通常还要维护业务层跨字段不变量。

即使读取一个计数值总能看到最新内容，两个线程同时“读旧值、加一、写回”仍可丢更新。可见性不能替代复合操作的原子性。

## 3. happens-before 关系

它是规范中的顺序关系，约束可见结果，不是拿时间戳比较墙上时钟。常用边包括线程内程序顺序、同一监视器解锁到后续加锁、volatile 写到后续相应读、线程启动与终止相关规则，以及传递性。

证明时画出发布者写数据 → 发布信号 → 消费者读信号 → 读数据的边。如果中间信号是普通字段，或者消费者根本没经过同步读取，不能靠“通常先执行”补出关系。

## 4. volatile 的保证范围

volatile 对变量访问提供规定的可见性与排序语义，但 count++ 包含读取、计算和写入，两个线程可以读到同一旧值，随后各自写入相同新值。需要原子增量时使用对应原子类或共同锁。

一种发布协议是生产者先写普通数据再写 volatile ready，消费者观察到对应发布后读取数据；必须确保之后没有不受同步保护的修改。单个发布信号不能自动保护整个生命周期的可变对象。

## 5. 互斥与发布协议

volatile 适合表达简单发布和独立状态变量等符合其语义的协议；锁可把多个操作与多个字段组成临界区，并通过解锁／加锁建立顺序。两者解决的约束不同，不应仅按“哪个更快”选择。

如果不变量是余额不能为负，检查再扣款要形成一个原子边界；分别把余额字段设为 volatile，并不能防止两个线程都通过余额检查。

## 6. final 与构造期间逸出

final 字段有专门的初始化安全语义，正确构造、没有让 this 提前逃逸时，可支持安全地观察初始化状态。但 final 引用不表示它指向的集合不能修改，也不替代对象整体的线程安全设计。

构造过程中注册回调或启动能访问 this 的工作，可能让其他线程看到未完成构造的状态。更清楚的方式是在构造完成后通过明确同步边界发布，不在构造器中承担隐式并发启动。

## 7. 单例的安全发布

典型双重检查需要对共享引用使用正确发布语义，例如 volatile，并在锁内再次检查。只在内层加锁但外层无同步地读取普通引用，无法简单证明安全发布。解释重点是构造、发布和读取之间的顺序，不只是背“指令重排三步”。

也可用类初始化持有者等语言机制简化发布；但若初始化依赖慢 IO 或外部锁，仍会导致等待。单例对象中的后续可变字段也需自己的并发协议。

## 8. CAS 的适用边界

CAS 可用于原子更新特定位置，配合循环实现某些并发算法；它不自动保护多个对象间的不变量，也不消除 ABA、活锁或高竞争重试开销。不同原子访问模式的内存语义应按 API 确认。

选择锁或无锁方案要考虑证明成本、竞争特征、取消与等待策略。继续读 [锁与 AQS](#/article/java-locks)，不能用一次微基准代表所有并发负载。

## 9. 并发结果的验证

不能。调试器、日志和测试环境可能改变交错与时序，低概率合法坏结果未发生不等于被规范禁止。先明确共享变量、同步边和线性化点，推演允许交错，再用专门并发测试与不同运行环境寻找反例。

若插入日志后问题消失，需要怀疑时序或额外同步，而不是将日志当作修复。本文没有运行并发压力测试；上述小场景是用于建立规范推理的例子。
