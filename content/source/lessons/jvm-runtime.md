## 1. JVM、JDK 与 ART

JVM 是执行 class 文件所描述程序的抽象机器规范，也常用于指符合规范的具体实现。Java 是语言；javac 等工具把源码编译为字节码；JDK 包含编译、运行和诊断工具。HotSpot 是一种 JVM 实现，规范不要求所有实现使用相同对象布局、GC 或 JIT。

Android 通常把 Java/Kotlin 产物经 D8/R8 转为 DEX，再由 ART 执行。语言层很多语义相通，但 ART 不是把桌面 HotSpot 整套搬到手机。本文规范基线为 Java SE 21，HotSpot 与 ART 的实现细节另行标注。

## 2. 运行时数据区域

可按规范运行时区域组织，而不是背固定数量：线程各有 pc 和 JVM 栈，pc 跟踪执行位置，执行 native 方法时该值未定义；栈保存调用帧。堆用于类实例和数组，线程共享。方法区保存类结构、方法代码和运行时常量池等逻辑信息，也共享。实现可提供 native 方法栈。运行时常量池是每个类／接口的结构，不应当成和方法区无关的额外“大仓库”。

这些是逻辑职责，规范没有要求一定物理连续，也没有规定堆必须分新生代、老年代。直接内存、线程栈、JIT 代码、GC 元数据等也会消耗进程资源，所以 −Xmx 从来不等于整个进程内存上限。

## 3. 方法区与 Metaspace

方法区是规范概念；Metaspace 是现代 HotSpot 存放类元数据的实现组成，二者不能无条件画等号。类的静态字段描述、静态字段的值、字段指向的对象、类镜像以及字符串对象要分开看。不要从“static”推导对象脱离 Java 堆。

现代 HotSpot 的字符串对象和相关 Java 对象仍在堆中；具体元数据、运行时常量池、字符串驻留表实现应按目标版本核对。排查 Metaspace 增长时看类与类加载器存活和动态生成类，而不是只找最大的业务数组。

## 4. 一次方法调用的执行

启动运行时后定位入口类并按需完成加载、链接与初始化，开始执行入口方法。方法调用建立逻辑栈帧，参数进入局部变量槽，字节码把值加载到操作数栈，计算后把返回值交给调用者。实例方法局部变量通常还包含 this。

以静态 add(a,b) 返回 a+b 为例，典型字节码可由 iload_0、iload_1、iadd、ireturn 组成：先压入两个 int，再弹出求和、压入结果，最后返回。JIT 可能内联或常量折叠，所以这描述语义执行模型，不保证优化后的机器代码保留同样帧结构。

## 5. 栈帧与递归深度

规范栈帧包含局部变量数组、操作数栈以及访问当前方法所属类运行时常量池的引用等执行信息。调用嵌套使逻辑帧增长；递归没有正确终止，或深度超过可用栈容量，可能产生 StackOverflowError。

局部变量槽中放引用，不等于所引用的大对象本体在栈上。增大线程栈可能缓解合法深递归，却增加每线程资源，进而降低可创建线程数。应先检查算法深度和循环依赖，再考虑配置，不把调大栈作为普遍修复。

## 6. 对象分配与构造

从语义上需要解析目标类型，必要时触发类初始化，为实例取得存储并建立默认值，再执行构造过程。引用赋值和对象初始化是不同动作；把尚未完成构造的 this 交给别的线程或回调，会破坏安全发布。

在典型 HotSpot 中，对象分配可能使用线程本地分配缓冲 TLAB 以减少共享分配竞争，慢路径可能触发 GC 或失败；对象头、对齐、压缩引用依版本和配置而定。逃逸分析可促成标量替换甚至消除实际分配，不能断言源代码每次 new 都必然产生一个可在堆 dump 中找到的对象。

## 7. 类的加载到初始化

加载取得类的二进制表示并建立运行时结构；验证检查其满足约束；准备为静态字段等建立必要状态并设置规定初值；解析把符号引用关联到运行时实体，可按规范允许的时机延迟。初始化执行相应初始化逻辑。

不能把“读取字节码”与“执行 static 代码块”混为一谈。编译期常量的使用可能被内联，不必触发声明类初始化；普通主动使用则遵守初始化规则。解析出错可能表现为链接错误，初始化失败则有另外的异常传播与后续状态。

## 8. 类加载器与类型身份

类身份不仅是二进制名称，还与定义它的类加载器有关。两个加载器分别定义相同名称的类，可以是不同运行时类型；因此“类名一样”不保证强转成立。插件边界最好通过共同父加载器定义的接口或明确数据协议通信。

常见委派模型先询问父加载器，有利于复用与核心类一致性；但 JVM 规范并不要求所有自定义加载器只能采用同一委派策略。改变加载策略仍必须遵守类加载约束和安全边界，不能简单说“打破双亲委派就能任意替换系统类”。

## 9. 类初始化与安全发布

运行时协调类初始化，其他线程按规则等待初始化完成，正确完成的静态初始化可用于安全发布。初始化不是“所有业务对象永远线程安全”的保证：随后可变状态仍需要自己的同步。

如果 static 初始化执行慢 IO、复杂锁等待或触发互相依赖的类，可能造成启动长等待甚至死锁。定位时画出“线程—初始化锁—外部锁”的等待关系；不要把全部耗时工作藏在单例 static 初始化中。

## 10. 解释执行、JIT 与预热

解释器按字节码语义执行，JIT 根据运行信息编译热点为机器码；具体分层、阈值和策略依实现。编译、类加载、缓存建立和资源初始化都会影响预热。JIT 可以基于假设内联、消除检查，假设失效时需去优化并恢复正确执行状态。

基准测试应区分冷启动与稳态，避免常量折叠、死代码消除和循环混入 IO。不能用一次毫秒计时证明锁或集合快几倍；微基准还要说明输入、预热与测量误差，最终回到真实业务链路。

## 11. 运行时区域、JMM 与 GC

运行时区域讨论程序数据由什么结构承载；JMM 讨论多线程读写可观察结果与 happens-before 约束；GC 讨论识别和回收不再需要的对象。对象在共享堆，不代表其他线程立即看到最新写入；有内存可回收，也不代表 GC 无暂停。

继续读 [JMM](#/article/jmm-concurrency)、[GC](#/article/gc-runtime) 与 [ART](#/article/memory-art)。把这三个层次混成“线程把栈刷新到堆”会在进一步追问时失去解释力。

## 12. 字节码与运行证据

对固定 JDK 的小程序使用 javap -c -v 查看指令与常量池；构造不同类加载器加载同名类观察类型身份；用受控递归与线程数对照观察不同资源失败；用类加载和 GC 诊断日志定位初始化或回收。实验只在隔离环境执行，避免把内存耗尽带到真实应用。

能展示字节码、调用时序、运行配置和异常资源类型，说明你理解模型与实现的区别。本文给出的是实验方案与手工字节码推演，未声称实际运行了这些 JVM 实验。
