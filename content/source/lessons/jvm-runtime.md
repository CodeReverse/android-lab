## 1. 从一段加法程序区分语言、格式与执行者

写下 `add(1, 2)`，处理器并不认识 Java 源码。编译器先产生 class 文件中的字节码与类型信息，运行时再按规定执行。JVM 是描述这台抽象机器的规范，也常用于指它的具体实现；Java 是语言，JDK 提供编译、运行和诊断工具，HotSpot 是一种实现。

```java
class Demo {
    static int add(int a, int b) { return a + b; }
    public static void main(String[] args) {
        System.out.println(add(1, 2));
    }
}
```

为什么要有中间格式？它让语言编译与目标平台执行解耦，也给类型检查、动态加载和运行优化提供统一输入。代价是加载、验证、编译或解释等运行时工作。直接编译机器码也是可行路线，取舍在部署、优化信息与运行能力，而不是谁天然更高级。

本篇以 Java SE 21 规范和明确标出的 HotSpot 实现概念为边界。Android 的 D8/R8 将相关产物转为 DEX，由 ART 执行，不能拿桌面 JVM 的所有参数和对象布局套到 Android。对应区别见 [ART](#/article/memory-art)。

## 2. 用一次方法调用找到局部变量与操作数栈

先不背内存区域，跟踪 add 所需数据。静态方法参数 a、b 进入当前帧的局部变量槽；计算指令在操作数栈取值、产生结果；返回时把结果交回调用者。

```text
局部变量：slot0=1，slot1=2
iload_0：操作数栈 [] → [1]
iload_1：            [1] → [1,2]
iadd：              [1,2] → [3]
ireturn：           将 3 返回调用者，结束当前逻辑调用
```

这是典型字节码语义的手算，不是声称运行时机器代码一定保留这个指令序列。实例方法还要处理 this，long/double 的槽位规则与 int 不同。帧还需要关联运行时常量池以解析符号引用；调用返回时调用者继续，而不是所有方法共享一个随意覆盖的局部数组。

如果 a 是对象引用，槽中保存的是引用语义，不是把整个对象复制进栈。这个区别会影响后面判断“大对象是不是跟方法返回一起销毁”。帧与运行时区域的规范依据见 [JVMS 第 2 章](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html)。

## 3. 再把数据放回完整的运行时地图

有了帧，区域划分就有了理由：各线程需要独立的调用进度与帧；多个线程又可能访问同一个对象和类型。

| 逻辑区域 | 本例中承载什么 | 不能误推的结论 |
| --- | --- | --- |
| pc | 当前执行位置的相关状态 | native 方法执行时 pc 值未定义 |
| JVM 栈 | main、add 的逻辑帧 | 引用在帧中不等于对象本体在栈中 |
| 堆 | 类实例和数组 | 规范不要求固定分代方案 |
| 方法区/运行时常量池 | 类型、方法及符号等结构 | 不等于某个实现名或单一物理内存块 |
| native 方法栈等实现资源 | 平台调用需要的执行支持 | 不受 Java 堆上限完全覆盖 |

如果只给 Java 堆设上限，线程栈、元数据、JIT 代码和 native 分配仍会占进程资源。于是“堆还有空闲却创建不了线程”并不矛盾。内存地图回答存储职责，JMM 回答并发可见性，两者不是同一种“内存模型”。

## 4. 用 new 的语义区分分配、默认值与构造

再写 `Box b = new Box(7)`。从语义上看，需要取得对应类型、为实例建立存储与默认字段值，再执行构造逻辑，最后让变量 b 指向得到的实例。构造器是初始化步骤，不是把一片不存在的内存凭空变出来。

```java
final class Box {
    final int value;
    Box(int value) { this.value = value; }
}
```

若构造过程中把 this 注册到外部监听，其他线程可能在构造完成前访问它。`final` 字段的初始化安全保证也有正确构造等前提，不能用一次“看起来正常”的运行证明发布安全。完整并发推理见 [JMM](#/article/jmm-concurrency?section=4)。

典型 HotSpot 可以用 TLAB 降低分配竞争，也可能经逃逸分析做标量替换，消除某些实际对象分配。语义上的 new 不保证每次都能在堆 dump 里找到一个独立实体。TLAB 是堆分配的实现技巧，不是“对象被放进线程栈”的同义词。

## 5. 从首次访问区分类加载与初始化

类型的字节从哪里来，static 代码又何时执行？把它们合成“加载类时全部执行”会解释不了下面的对照：

```java
class Config {
    static final int LIMIT = 10; // 编译期常量
    static int count = init();
    static int init() { System.out.println("init"); return 1; }
}
// 使用 Config.LIMIT 与使用 Config.count，触发初始化的语义不同。
```

加载建立类型表示；验证检查字节码满足约束；准备建立规定的初始状态；解析关联符号引用与运行实体，允许在规定边界内延迟；初始化执行相应静态初始化逻辑。编译期常量可被内联，使用 LIMIT 不应据此推断一定执行 init。

初始化失败也不等同于类文件找不到。首次失败与后来再次主动使用已失败类型会有不同异常路径，排障要记录根异常，而不只看到最后的 NoClassDefFoundError 就认为缺了 jar。触发条件、顺序和错误以 [JVMS 第 5 章](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html) 为准。

## 6. 两个同名类为什么仍可能不能强转

插件 P 和 Q 各自定义 `example.Model`，日志类名一样，强转却失败。类型身份还包含定义它的类加载器，名字相同不是充分条件。

```text
加载器 L1 定义 example.Model → 类型 T1
加载器 L2 定义 example.Model → 类型 T2
T1 与 T2 不自动成为同一类型
```

共同父加载器定义接口，插件通过该接口或数据协议通信，可以把共享契约与插件私有实现分开。常见父优先委派帮助复用类型与核心类一致性，但并不是所有自定义加载器必须采用同一算法；改变策略仍受加载约束等规则限制。

这也解释类加载器泄漏：若长寿命线程、静态注册表或回调仍引用插件对象，加载器和相关类型可能一起无法回收。只删除插件文件不会解除运行中的引用链。

## 7. 方法区概念怎样连接到 Metaspace 故障

现代 HotSpot 用 Metaspace 管理类元数据相关存储，但规范方法区与某个实现区域不能无条件画等号。静态字段描述、静态字段的值、它引用的 Java 对象和类镜像也要分开，不能看到 static 就把整个对象排除在堆外。

假设每次刷新脚本都创建一个加载器，再把脚本回调加入全局表却不注销：加载器数增加，类数量增加，元数据可能持续增长。堆里最大的数组未必是根因，反而应检查是谁留住加载器。解决方向是结束旧版本的使用关系，而不是只增加某个元空间上限。

HotSpot 元数据实现演进可看 [JEP 387](https://openjdk.org/jeps/387)；它说明具体实现改进，不改变“规范不固定物理布局”的边界。Android 元数据与内存统计要回到 ART 工具链。

## 8. 解释执行与 JIT 改变成本但不能改变语义

add 被频繁调用以后，JIT 可能内联它，甚至把常量结果折叠。于是字节码中存在一个调用，不代表优化机器码中仍存在一个相同物理栈帧。

```text
冷路径：加载、验证、解释/初期执行、收集运行信息
热路径：按实现策略编译优化，利用类型等运行假设
假设失效：按需要去优化，恢复能维持正确语义的执行
```

为什么不始终立刻做最重优化？编译本身消耗时间和内存，很多方法不够热；基于实际运行信息优化也可能比完全静态判断更有机会。反过来，启动路径不应被稳态跑分代表。

微基准若只调用 `add(1,2)` 却不消费结果，可能测到被优化掉的工作。需要合理基准工具、输入与结果消费，并记录预热、编译与环境；实际用户延迟还要回到完整链路。

## 9. 让异常资源与证据一一对应

无限递归增加调用深度，可能触发 StackOverflowError；持续持有数组压迫堆；大量线程消耗栈与系统资源；动态加载类压迫元数据。它们都可能表现为运行失败，却不能统一用“加大堆”修复。

对 Demo 可用固定 JDK 的 `javap -c -v Demo` 对照字节码和常量池；对类型问题记录类名与 defining loader；对分配问题结合 GC 日志、堆和 native 证据。本文给出预期与诊断设计，没有宣称执行过这些实验。

接下来按问题进入 [线程](#/article/java-threads)、[锁](#/article/java-locks)、[GC](#/article/gc-runtime)，而不是把所有源码细节挤进运行时地图。能把一个变量、一个调用、一个对象和一个类型放到正确机制里，才有继续分析复杂故障的基础。
