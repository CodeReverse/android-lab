## 1. 进程、线程与任务

进程提供地址空间与资源隔离边界；线程是运行时与系统调度执行的载体，拥有执行栈等状态；任务是一段待执行工作，可被排队、取消或分配给线程。多个线程通常共享进程内对象和资源，因此能方便通信，也会发生竞争。

在 Java/Kotlin 中创建 Runnable 不等于启动新线程，直接调用 run() 仍在当前线程执行。Thread.start() 启动线程执行过程，不能把同一 Thread 实例反复 start 当成复用；线程池复用的是工作线程，让它执行多个任务。

## 2. Java 与操作系统线程状态

Java 层有 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。它们是抽象观测，不是一张精确 CPU 调度状态表：RUNNABLE 可能正在执行，也可能等待获得 CPU；BLOCKED 特指等待监视器进入等相应状态，不能用来概括全部阻塞 IO。

排查时结合线程栈、CPU 时间、调度 trace 和等待对象。同一栈反复停留在某处既可能是计算热点，也可能是等待；单次截图不足以判断长期行为。

## 3. sleep、wait、park 与 yield

sleep 暂停当前线程一段时间，不释放已经持有的监视器；wait 必须持有对象监视器，进入等待时释放该监视器，返回前重新竞争；park 基于许可机制等待，不替你释放普通锁；yield 只是调度提示。

wait/park 可出现非预期唤醒或中断返回，因此等待业务条件应循环检查 predicate。notify 或 unpark 是让线程具备继续的可能，不保证立刻执行，也不保证业务条件仍为真。错误地在持锁时 sleep，常把短暂等待放大成整个临界区拥堵。

## 4. 线程池的任务执行

以 ThreadPoolExecutor 为基线：工作线程少于 corePoolSize 时尝试增加；否则尝试入队；队列不能接收时再尝试增长至 maximumPoolSize；仍无法接收则拒绝，具体过程还要重检运行状态。无界队列通常使 maximumPoolSize 很难起到你期待的扩容作用。

core、max、队列、keepAlive、线程工厂与拒绝策略共同定义系统。一个问题如果只答七个参数而不能推演“第 N 个任务到来时去哪”，说明还没有理解执行模型。

## 5. 线程数与队列容量

CPU 密集任务受核数与带宽约束，增加线程带来上下文切换、缓存失效和竞争。阻塞任务可提高并发隐藏等待，但下游连接池、磁盘和服务容量仍有限。队列吸收突发的代价是保留任务对象与增加等待时间，无界积压会导致延迟雪崩与内存问题。

先定义完成时限、下游并发上限和最大积压，测量到达率、服务时间与队列长度。线程数经验公式只能作为实验起点，不能脱离真实阻塞比例直接套用。

## 6. 拒绝、超时和取消

拒绝表示执行器不能接受，超时表示调用方等待超过预算，取消是停止后续工作的请求；它们都不自动撤销已经发生的业务副作用。CallerRuns 可形成背压，但若提交方是 UI 或事件循环，会把耗时工作挪到最不该阻塞的线程。

Future.cancel(true) 可以尝试中断执行线程，中断是协作信号，不是安全地强杀代码。任务要在循环、阻塞 API 和资源处理处支持终止，finally 中关闭资源；吞掉 InterruptedException 后继续执行可能破坏上层取消契约。

## 7. ThreadLocal 的生命周期

任务结束不等于线程结束。与线程绑定的值可能被后续任务读到，形成账号串用或长期保留。典型 ThreadLocalMap 的弱 key 并不意味着 value 同时变弱，过期条目的清理也不保证恰好发生在任务结束时。

将任务级上下文的 set/remove 放在配对的 try/finally 中，传播跨线程上下文时显式捕获和恢复。不能把 InheritableThreadLocal 当作通用线程池任务上下文传播机制，因为线程可能早已创建并被反复使用。

## 8. 任务依赖与线程池饥饿

若池中所有工作线程都执行父任务，父任务同步等待提交到同一池的子任务，子任务排队却没有线程可执行，形成线程饥饿死锁。资源依赖图不只包含监视器，还可能包含线程池容量、连接池和配额。

修复可采用异步组合、消除池内同步依赖或隔离有阻塞依赖的工作，不能一律用增大池掩盖。故障证据是活跃线程都在等待某类结果、子任务持续排队且没有可运行工作线程。

## 9. 虚拟线程与协程的资源边界

JDK 21 虚拟线程通过运行时调度到载体线程，适合大量等待型任务，但不会增加 CPU 算力，也不移除数据库连接、内存和外部服务限制。Kotlin 协程的 suspend 状态机与 Dispatcher 是另一层模型，不能简单视为同一个 API。Android ART 是否提供某个桌面 JDK 能力，需要单独核验，不能直接照搬。

版本也重要：JDK 21 的 synchronized 相关 pinning 讨论，不能原封不动用于 JDK 24；后者改进了监视器场景下释放载体线程的能力。native 等边界仍需按版本分析，不说“虚拟线程从不阻塞”。

## 10. 线程池配置的验证

展示固定负载下的吞吐、排队等待、执行时长、拒绝、取消、下游容量和内存，分正常与突发场景。注入慢依赖和中断，检查任务能否停止、队列能否恢复、上下文是否串用。尤其测 CallerRuns 是否把工作压回主线程。

对 Android 再观察主线程调度和耗电；对服务端观察尾延迟与过载保护。本文给的是诊断与实验设计，尚未在用户环境执行线程压测。
