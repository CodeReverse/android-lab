## 1. 从一句成果声明开始追问证据

“我优化了启动速度 30%”听起来明确，却缺少场景、口径和归因。是冷启动还是热启动，TTID 还是内容就绪，哪类设备，样本多少，团队同期是否换了接口？没有这些信息，数字无法帮助面试官判断技术能力。

本篇用教学项目组织证据，不替读者编造经历或收益。若没有可靠原始数据，应说已经完成哪些实现和验证，不能给估计值加上“线上实测”。资深材料的可信度来自结论与证据范围一致。

## 2. 一张证据表把事实与推理分开

|内容|教学示例|证明范围|
|---|---|---|
|事实|某版本 trace 显示主线程等待索引读取|该时间窗存在等待|
|假设|索引读取是内容就绪的关键依赖|需要改变该因素验证|
|决策|首屏使用轻量摘要，详细索引延后|说明选择与代价|
|验证|同条件对照，并检查首屏正确性|支持限定场景下的效果|
|限制|尚无全量线上 A/B|不能宣称所有用户获益|

这些行是模板，并非真实已采集记录。事实、假设、决定和结果混写，容易把“计划达到”变成“已经达到”。性能证据的测量方法见 [性能证据](#/article/performance-proof)。

## 3. 个人贡献要落在具体动作上

跨团队项目中，客户端发现等待链，服务端修改接口，测试团队覆盖回归，平台团队提供监控。最终指标属于共同结果；个人说明应写自己完成的诊断、方案、实现、协调和验证范围。

可以把“负责启动优化”展开为：“我对齐内容就绪定义，定位索引读取依赖，提出两种替代方案并用 spike 排除其中一种，负责客户端迁移与灰度验证。”只有实际做过才能这样写；没有参与的服务端设计不要占为己有。

面试追问方案为什么被否决时，最好有当时的约束和试验记录，而不是事后编造一个显然更差的替代方案。记录结构可参考 [ADR](https://adr.github.io/)。

## 4. 从根因到修复保持可追溯

```text
现象与影响
 → 原始日志/trace/复现
 → 可检验的机制假设
 → 最小改动或试验
 → 对照结果与反例
 → 灰度/回退/后续治理
```

每个箭头都应能解释。例如从“线程阻塞”到“锁粒度过大”，需要持有者和等待链；从“内存下降”到“泄漏修复”，需要旧对象不再被保留的根路径或计数。单次截图不能独立证明全部因果。

记录版本、设备、时间、操作、数据规模和测试脚本，使同事能复查。敏感信息需要脱敏或只展示可公开的结构；不要把公司私有日志直接带到公开面试材料。

## 5. 没有线上指标时仍能诚实展示深度

如果外企环境不允许带出数据，可以准备脱敏的架构关系、简化复现、测试设计、决策边界和自己能解释的机制。明确说“下面用教学数值演算”，就能展示分析能力，而不伪装为真实收益。

尚未完成的验证也有价值：写出预期信号、可能反例和下一步。如果无法区分缓存影响与代码收益，就承认当前结论有限，说明怎样控制变量。这通常比一个无法追溯的漂亮百分比更可靠。

## 6. 将证据转成不同长度的项目说明

短说明讲问题、自己的关键决定和已证实结果；深入说明再展开约束、机制、替代方案、失败路径与验证。两种长度应共享同一事实底稿，不能短版说全量收益、长版才承认只是实验室结果。

准备一页索引指向可展示的 ADR、最小例子、对照记录和遗留风险，按提问展开。项目不是背诵稿，而是一组能够承受“为什么、如何证明、还有没有别的办法”的证据。本文属于编辑方法，不代表某公司统一面试标准。

## 面试提炼

1. 一条性能成果缺少哪些条件就无法判断？（第 1、2 节）
2. 怎样区分事实、假设、决策和结果？（第 2 节）
3. 团队成果如何准确说明个人贡献？（第 3 节）
4. 什么证据把根因、修复与收益连接起来？（第 4 节）
5. 无法提供线上数据时怎样展示真实技术深度？（第 5、6 节）
