## 1. 先把失败分成未开始、已失败与结果未知

用户点击付款，转圈后提示超时。若立刻重新创建一笔付款，可能重复扣款；若永久禁止重试，又可能让一次根本没发出的请求无法恢复。难点不是选择三次还是五次重试，而是辨认客户端究竟知道什么。

```text
本地校验拒绝：知道请求未被发送
服务端明确拒绝且协议保证未提交：知道本次没有成功
请求可能到达，响应没收到：通常只能判断结果未知
```

最后一种可以由服务端提交后响应丢失产生，也可以由请求根本没到达产生。客户端观察到同一个 timeout，并不能区分两种世界。这是跨网络通信的信息边界，不是换一个 HTTP 库就能消除。

因此状态模型至少应允许 Pending/Unknown，而不是所有异常都赋值 Failed。UI 应告诉用户正在确认，并提供查询恢复路径。TCP 与业务提交之间的区别见 [传输协议](#/article/tcp-tls?section=5)。

## 2. 用总截止时间约束所有尝试

假设用户愿意等 3 秒，每次请求都设置 3 秒超时，再重试三次，整体可能远超 9 秒，还不含排队与退避。不同层的独立计时器没有自动组成用户预算。

定义一个单调时钟截止时间，所有排队、连接、读取、退避和尝试都从剩余时间扣除。以下是策略伪代码，不是某网络库的完整实现：

```text
deadline = monotonicNow + 3s
for attempt in permittedAttempts:
  remaining = deadline - monotonicNow
  如果 remaining <= 0：结束本次等待
  尝试请求，阶段超时不得超过 remaining
  成功或明确不可重试：返回
  若业务不允许安全重试：进入结果确认
  delay = 有上限的退避 + 抖动
  如果 delay >= 剩余时间：停止
  可取消地等待 delay
```

连接超时管建连等待，读取超时常针对相应读取停滞，调用级超时覆盖范围由具体客户端定义。不要假定一个 readTimeout 就是整个请求从排队开始的总期限。页面离开时取消等待，也不代表服务端操作被撤回。

退避减少持续冲击，抖动避免大量客户端在同一时刻一起重试。把次数加大虽然可能提升个别成功率，也可能放大故障期间的负载；需要结合失败类型、Retry-After、服务端限流和业务预算。HTTP 的幂等与重试规则见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-9.2.2)。

## 3. 让业务操作 ID 跨越网络尝试

现在给一次逻辑付款分配 K。用户点一次生成 K，后续网络重试继续使用 K；若每次尝试生成新 K，服务端看到的仍是多笔独立付款。

服务端去重不能只有“先查 K，不存在就扣款”：两个请求可以同时查不到，然后都执行。需要把去重记录与业务效果放在能保证原子性或可靠协调的边界内。一个简化数据库事务方案为：

```text
事务开始
  尝试以唯一键(account, K)创建操作记录，附请求摘要
  已存在：核对摘要；返回既有结果或处理中状态
  新记录：执行同事务可覆盖的业务修改
          保存结果引用与状态
事务提交
```

这里的唯一约束解决并发竞争，请求摘要阻止同一 K 被复用为另一笔金额。响应丢失后，再发 K 或查询 K，可以恢复原结果。记录保存期还要覆盖客户端允许的重试窗口；过早删除后再次收到 K，就可能重复执行。

如果扣款实际调用另一个外部系统，本地事务无法自动包住它。还需要对方支持的幂等键、Outbox、补偿或状态查询，不能宣称一张本地表实现跨系统 exactly-once。更多存储时序见 [离线与 Outbox](#/article/offline-data?section=3)。

## 4. 搜索可以丢旧结果，付款不能随意丢事实

搜索 A 后输入 AB，希望页面展示 AB。即使取消 A，旧回调仍可能已排队，因此提交前检查查询版本：

```kotlin
// 伪代码：接受输入和提交结果在同一串行状态拥有者内执行。
val requestId = ++generation
val result = search(query)
if (requestId == generation && account == currentAccount) {
    state = Result(query, result)
}
```

校验与更新必须在同一受控边界，不能校验后让其他线程改账号，再无条件赋值。它保护的是当前展示不被过期工作覆盖，取消则尽量减少资源消耗。

付款的成功事实不能因为页面已换而静默丢掉：可以不再更新旧 UI，却仍需在业务层记录并恢复结果。先区分“这份结果还适合当前画面吗”与“这项操作是否需要最终确认”，再决定生命周期与持久化。

## 5. 用故障注入审查重试协议

准备一个可控服务，在事务前、事务后响应前、响应中途分别断开。对同一个 K 并发发送两次，改变其中一次金额，再把客户端进程结束后恢复查询。验收是最终业务效果与请求摘要符合契约，不是仅看 HTTP 成功率。

记录逻辑操作数、网络尝试数、未知结果占比、最终确认延迟和重复副作用。尝试成功率上升却导致逻辑付款重复，优化应判失败；重试次数下降却让未知结果永远挂起，也不算完成。

这些是未执行的验证设计。方案的适用范围取决于服务端支持和业务可补偿性，不承诺所有接口都能靠客户端修复。把请求阶段、幂等边界、恢复与用户提示写成同一份协议，才能经受“响应没回来怎么办”的继续追问。
