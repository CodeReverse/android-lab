## 1. 从一次改文案却全量重编译开始

改一行页面文案后构建仍很慢，先别把问题归为“Gradle 太慢”。一次构建包含配置项目、计算任务关系、执行必要任务及打包等工作。若慢在配置，缓存编译产物未必解决；若某个输入每次变动，执行缓存也可能始终失效。

```text
请求 assembleRelease
 → 配置项目/确定任务图
 → 检查任务输入输出
 → 执行或复用任务结果
 → 产出签名与分发需要的制品
```

这是一张概念图，不是所有 AGP 版本的完整任务名清单。要记录 Gradle、AGP、JDK、Kotlin 和插件版本，才能把现象对应到实现。先比较无改动构建、单文件改动和干净构建，三者回答不同问题。

## 2. 三种“缓存”为什么不能混为一谈

UP-TO-DATE 判断本地输出与已知输入是否仍匹配；build cache 可复用相同任务输入对应的输出，包括合适配置下的远程缓存；configuration cache 复用配置阶段形成的任务执行配置。它们省下的阶段不同。

假设一个代码生成任务只声明 schema，却偷偷读取当前时间。相同声明输入产生不同输出，缓存就不再可靠。反过来，若把整个仓库都声明为输入，改 README 也可能令生成任务失效。缓存优化首先是把真实输入、输出和环境依赖声明准确，而不是打开开关。

依据 [Gradle Build Cache](https://docs.gradle.org/current/userguide/build_cache.html) 和 [Configuration Cache](https://docs.gradle.org/current/userguide/configuration_cache.html)；具体插件是否兼容需在项目版本验证。教学检查可先故意改变一个声明输入、一个无关文件，观察是否只有前者令任务失效。

## 3. Debug 正常，Release 为什么找不到类

R8 根据可见的程序关系分析可达代码，并进行收缩、优化与重命名。直接调用容易进入分析图；通过字符串反射加载的类，使用关系可能不完整。例如：

```kotlin
val type = Class.forName("com.example.codec.LegacyCodec")
val codec = type.getDeclaredConstructor().newInstance()
```

若这里确实依赖类名和无参构造器，可用与实际契约匹配的窄规则，示意如下：

```proguard
-keep class com.example.codec.LegacyCodec {
    public <init>();
}
```

这只是保留该类和指定构造器的示例。反射调用的其他成员、序列化注解或 JNI 入口还需按真实使用补充；不能照搬后宣称所有反射安全。为什么不 `-keep class ** { *; }`？它掩盖缺失规则，也放弃很多优化。优先使用静态可见代码和库提供的 consumer rules，必要时才精确补规则。见 [R8 保留规则](https://developer.android.com/topic/performance/app-optimization/keep-rules-overview)。

## 4. 可发布制品还需要可诊断性

线上栈经过重命名后，需要与**同一次制品**匹配的 mapping 才能还原；native 崩溃还需要对应符号。只保存源代码 tag 不保证以后重新构建出完全相同映射，依赖解析、工具版本和环境也可能变化。

发布记录应关联提交、依赖锁定信息、工具链、签名身份、制品校验和、mapping/符号和配置。敏感签名材料不能放进仓库或日志；保存的是关联和受控存储位置。验证 release 的关键路径要覆盖反射、序列化、动态加载与 ABI，不能只跑 debug 测试。还原工具参见 [Retrace](https://developer.android.com/tools/retrace)。

## 5. 回滚版本不一定能回滚数据

设新版把本地数据库字段从 A 拆成 B、C，并删除 A。即使旧 APK 能重新部署，旧代码也可能读不懂新数据；“保留旧包”不是完整回滚策略。更安全的演进常先兼容读写，再迁移，最后在确认旧版本退出后清理，但具体窗口依产品而定。

灰度需要定义扩大、停止和回退的条件，例如崩溃、启动、关键业务成功率和数据迁移失败率；按设备/API/ABI 分层，避免总体平均掩盖特定机型故障。开关只能关闭被设计为可关闭的功能，不能逆转已执行的不可逆数据变更。

## 6. 把构建优化做成可复现的小实验

教学实验可选一项任务，保存三轮不同场景的任务原因、缓存命中与耗时；修正输入声明后重新运行相同场景。发布验证则安装真正的 release 制品，运行关键反射入口，再用对应 mapping 还原一份受控异常栈。

这里没有声称构建提速或线上收益。最终需要同时证明“该省的工作省了”和“产物仍正确”，否则速度提升可能只是漏掉了应执行的任务。架构模块拆分与构建收益的关系见 [架构演进](#/article/architecture-evolution)。
