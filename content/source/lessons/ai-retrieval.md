## 1. 关键词与向量相关性

关键词检索根据词项出现、稀有程度、文档长度等判断匹配，BM25 是经典例子，适合精确型号、错误码、专有名词。向量检索把 query 与文档映射到语义空间，用相似度找近邻，适合表达不同但语义相近的请求。向量并不天然理解最新缩写、数字条件或否定关系，关键词也可能因分词和术语变化漏掉正确文档。

Embedding 的输入模板、归一化和距离度量必须与模型训练方式兼容。单位归一化后余弦与内积排序等价，但未归一化时不是；不同模型产生的向量即使维度相同也不能直接比较。召回质量首先是表示质量问题，再是索引效率问题。

## 2. HNSW 近似检索

暴力精确检索对每个向量算距离，容易理解但库大时成本高。HNSW 用多层近邻图，上层稀疏地快速导航，下层进行更细的候选探索。它是近似搜索，速度与内存换取可能的漏召回，不保证任何参数下都达到精确 top-k。

建图连接数 M、构建搜索宽度和查询搜索宽度影响内存、构建时间、延迟和召回。提高 efSearch 通常增加探索，可改善 ANN recall，同时增加成本；不能许诺所有数据分布严格单调或固定倍数收益。高选择性的权限过滤也可能让有效候选不足，需要评估过滤顺序、扩大探索或对小子集精确检索。

面试里应主动区别两种“召回率”：ANN recall 是相对精确向量近邻的重现比例；业务 Recall@K 是相对人工相关证据的覆盖。前者 99% 不代表后者 99%，因为向量空间本身可能就不把正确证据排前面。

## 3. 混合召回与 RRF

BM25 分数与向量相似度不在同一尺度，直接各乘 0.5 相加未必合理。可以用验证集校准分数，或者用排名融合。RRF 的典型形式为 `score(d)=Σ 1/(k+rank_i(d))`，不在某候选列表的文档通常对该列表贡献为零。k 为平滑常数，具体窗口、重复文档和 rank 约定依实现。

示例：文档 A 在两路分别排 1、10；B 排 3、3。取 k=60，A≈1/61+1/70=0.03068，B≈2/63=0.03175，B 得分更高。这是手算说明一致性如何影响融合，不是推荐所有项目固定 k=60。

融合之后按文档身份去重，保留命中来源用于诊断。多路查询与 query rewrite 会增加候选覆盖，也可能改变问题意图；查询扩展需要保存原始约束，尤其是否定、时间、单位和权限。

## 4. Cross-Encoder 重排

双塔分别编码 query 与文档，文档向量可预计算，适合大规模召回。Cross-Encoder 联合输入 query 和文档，在交互表示上评分，通常更适合较小候选集的精排；每个候选都要重新计算，成本更高。它并非任何语料都必胜，应对困难集、领域错配和多语言分别评测。

reranker 只重排已有候选，不能纠正不存在的证据。候选池从 50 增到 200 可能提升覆盖但增加重排耗时，最终给模型的证据数却不必同比增加。记录召回 K、精排 k、上下文 token 三个预算，而不是只有一个 top-k 参数。

## 5. ANN 召回与证据覆盖

**ES 和 MySQL 能否简单二选一？** MySQL 常作为事务性元数据或事实源，ES 擅长倒排与搜索分析，也支持向量能力；MySQL 也有全文和生态扩展。选型看事务约束、过滤、检索质量、写入与一致性需求，不以“一个能存向量一个不能”做绝对判断。

**怎么证明要用向量数据库？** 小数据量先用精确检索建立质量上界，再对 ANN 做规模压测和成本比较；如果内存和延迟已达标，不必引入分布式系统。离线记录证据召回、MRR/nDCG、权限过滤后覆盖，在线验证任务完成率与延迟。本文示例仅为理论计算。
