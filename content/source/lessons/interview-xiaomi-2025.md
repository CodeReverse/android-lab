## 2. 已有 Activity 接收到新 Intent 时如何处理？

原帖位置：一面 2。

### 参考回答

某些启动模式或 Intent flag 组合会复用已有实例，并调用 onNewIntent，而不是重新 onCreate。新参数应在回调中解析与校验；若后续通过 getIntent 读取，需理解保存的 Intent 不会自动等同回调参数，必要时 setIntent 更新。

### 原理与继续追问（编辑扩展）

不能只为少建一个 Activity 随意选 singleTask，因为返回栈语义也会变化。把初次 Intent 与新 Intent 交给同一参数处理入口，避免重复消费副作用。深链还要校验权限与资源归属，防止新 Intent 把旧账号页面跳到未授权内容。

## 3. RecyclerView 应从哪些环节优化？

原帖位置：一面 3。

## 4. Glide 怎样协调缓存、解码和目标生命周期？

原帖位置：一面 4。

## 6. 如何实现可取消的异步结果回调？

原帖位置：一面 6。

### 参考回答

耗时工作由明确执行器或协程承载，完成后把结果投递到约定线程；接口定义成功、失败与取消的互斥完成状态。回调所属 owner 决定生命周期，结果交付前检查是否仍有效。只是 new Thread 再调用 callback 还不够。

## 8. execute 与 submit 的结果和异常处理有何区别？

原帖位置：一面 8。

### 参考回答

execute 接收 Runnable，不提供 Future 返回结果；submit 可接收 Callable 或 Runnable 并返回 Future。任务异常经 submit 包装后通常记录在 Future 中，调用 get 时以 ExecutionException 等形式观察，不能以没打印日志判断成功。

### 原理与继续追问（编辑扩展）

Future.get 会阻塞调用线程，不能在主线程等待长任务。cancel(true) 通常通过中断表达取消请求，不保证任务立即停止；失败处理要覆盖未观察 Future 的情况。execute 抛出的未捕获任务异常与线程工厂的异常处理路径不同。

继续学习：[线程与任务](#/article/jmm-concurrency) · [并发结果](#/article/coroutines)

## 9. 如何让一个线程协作停止？

原帖位置：一面 9。

### 参考回答

使用中断或其他明确取消协议，不使用强制 Thread.stop。interrupt 设置中断状态，某些阻塞方法会抛 InterruptedException；纯计算需要主动检查。底层库是否响应中断必须查契约，必要时通过关闭资源或专用取消 API 终止等待。

### 原理与继续追问（编辑扩展）

捕获 InterruptedException 后若不能完成取消处理，应按调用协议恢复中断标记或向上传播，不能吞掉后无限循环。中断标记不等于业务回滚；操作已经提交时，需要独立补偿或查询。

原帖位置：一面 11。

## 14. 最长无重复片段怎样维护不变量？

原帖位置：一面 14。

### 参考回答

题意对应 [LeetCode 3](https://leetcode.cn/problems/longest-substring-without-repeating-characters/)。滑动窗口维护当前无重复区间，记录每个字符最近位置；读到右端字符 c 时，left=max(left,last[c]+1)，更新 last 和最大长度。left 只能向右，不可因旧字符位置而倒退。

### 原理与继续追问（编辑扩展）

每个右端点处理一次，均摊 O(n)，空间取决于字符集合。测试 abba 可暴露 left 倒退错误。Kotlin/Java Char 是 UTF-16 代码单元；若业务要求完整 Unicode 码点或字素簇，需要先明确“字符”的定义，不能默认与题目约束完全相同。

## 15. 队列空闲时为何不忙轮询，如何醒来？

原帖位置：二面 1。

### 参考回答

Looper 从 MessageQueue.next 取消息，没有到期消息时进入 native 等待，经典 Android 路径通过 poll/epoll 等事件机制睡眠，被新消息或相关事件唤醒。新消息若改变最早可执行条件，队列会触发唤醒以重新计算等待。

### 原理与继续追问（编辑扩展）

epoll 关注文件描述符上的就绪事件，线程等待时不是一直执行 Java while。具体唤醒 fd 和实现需按 Android 分支核对。nativePollOnce 出现在 ANR 快照不证明此等待本身有 bug；还要看采样时刻和真正超时窗口。

## 16. Binder 的拷贝与 Parcel 应如何精确解释？

原帖位置：二面 2。

### 参考回答

应用参数经 Parcel 编解码，Proxy/Stub 协作完成 IPC。在经典 Binder 驱动路径中，目标进程映射驱动管理的接收区域，普通事务载荷可从发送方用户空间复制到该区域，避免再做一次通用接收拷贝。因此常说的一次拷贝有明确统计边界。

### 原理与继续追问（编辑扩展）

Parcel 构建、对象转换、嵌套 buffer、文件描述符处理以及服务端读取仍可能有额外工作，所以不能说所有类型从业务对象到业务对象总共只复制一次。大数据用共享内存或 fd 等方案时边界又不同；性能还受调度、线程池和同步往返影响。

继续学习：[IPC 全链路](#/article/binder)

## 17. 建连为什么不能简单少一次交互？

原帖位置：二面 3。

### 参考回答

双方需要同步初始序号和确认对方对连接建立信息的接收。两次交互后服务端尚缺客户端对其响应的确认，旧重复请求等情况也会让状态处理出现歧义。三次握手建立的是传输连接，不是应用登录或业务事务确认。

### 原理与继续追问（编辑扩展）

进一步解释 SYN 与 ACK 对状态机的影响，并区分 TCP 握手和 TLS 认证。复用现有连接可减少新握手成本，但会带来陈旧连接与网络变化的失败处理；不能简单以减少报文数为理由绕过协议。

继续学习：[TCP 与 TLS](#/article/tcp-tls)

## 18. Java 运行时区域与 JMM 是同一件事吗？

原帖位置：二面 4。

### 参考回答

不是。运行时区域讨论堆、线程栈、方法相关数据等存储职责；JMM 讨论线程间读写可见性与顺序约束。HotSpot 的 Metaspace 等具体实现不能直接当 ART 的内部布局。对象可能在堆中，不代表引用它的各线程无需同步。

### 原理与继续追问（编辑扩展）

用 volatile 发布对象说明 happens-before，再用 count++ 说明可见性不等于复合原子性。安全发布后对象的后续可变字段仍需保护；Thread.sleep 和日志顺序不构成通用同步证明。

继续学习：[Java 内存模型](#/article/jmm-concurrency) · [ART 内存](#/article/memory-art)

## 19. 让 B 在 A 完成后再工作有哪些办法？

原帖位置：二面 5。

### 参考回答

最直观是 B 调用 A.join 后继续，但要处理 InterruptedException，且等待线程不能是需要保持响应的主线程。还可按场景用 CountDownLatch、Future 或协程的结构化组合；不要用固定 sleep 猜 A 何时结束。

### 原理与继续追问（编辑扩展）

join 正常返回后具有相应完成可见性语义；如果 A 失败，B 仍需明确是否继续。若 A/B 是同一受限线程池里的任务，阻塞等待可能造成饥饿。任务依赖组合通常比占用线程盲等更易管理。

继续学习：[同步关系](#/article/jmm-concurrency) · [结构化依赖](#/article/coroutines)

## 20. 进程通信有哪些选择，管道边界是什么？

原帖位置：二面 6。

### 参考回答

可讨论管道/FIFO、socket、共享内存、消息机制与 Android Binder。普通匿名管道通常依赖继承或传递文件描述符建立关系，FIFO 可由名字打开；管道是字节流，没有应用消息边界，容量有限，写端和读端需处理阻塞、EOF 与关闭。

### 原理与继续追问（编辑扩展）

共享内存减少大块传输复制但需要自己同步与管理权限；socket 适合本地或网络通信；Binder 提供 Android 对象接口与调用身份等能力。原帖未限定数据规模和通信模式，不能断言管道一定最慢，选型应比较协议、载荷与平台需求。

继续学习：[Android IPC](#/article/binder)

## 21. 数组与链表的查找复杂度如何区分？

原帖位置：二面 7。

### 参考回答

若指已知合法下标的随机访问，数组可 O(1)，链表通常需遍历 O(n)；若按未知位置的值搜索，普通无序数组和链表都可能 O(n)。已排序数组可用二分 O(log n)，普通链表不具备同样高效的随机跳转能力。

### 原理与继续追问（编辑扩展）

链表插入删除 O(1) 的前提是已拿到需要的节点/前驱，查找位置仍可能 O(n)。数组移动元素有成本，但连续存储和缓存局部性可能让实际遍历更快。先澄清“任意元素”是按下标还是按值，比直接给单一复杂度严谨。

继续学习：[集合选型](#/article/collections)

## 22. 数组按下标 O(1) 的地址计算来自哪里？

原帖位置：二面 8。

### 参考回答

固定宽度元素或引用槽连续排列时，位置可由基址加下标乘槽宽直接计算，边界检查也是常量级。对象数组存的是引用槽，槽连续不代表每个对象本体连续；多维引用数组也未必是一整片规则内存。

### 原理与继续追问（编辑扩展）

O(1) 是渐进操作数量，不代表每次真实延迟相同：缓存、页缺失与内存层次会影响时间。变长编码字符串按“第几个字符”访问又是另一个问题，不能照搬数组槽位模型。

继续学习：[类型与存储边界](#/article/collections)

## 23. 三数和小于目标值的题如何先澄清再求解？

### 参考回答

原帖说寻找下标三元组，但未明确返回数量还是枚举全部，也未给去重规则；它不是直接等同 LeetCode 15。若只统计 i<j<k 的数量，可排序后固定 i，使用左右指针：和小于 target 时，当前 left 与 left+1..right 的组合均满足，计入 right-left 后移动 left；否则移动 right。

### 原理与继续追问（编辑扩展）

计数可 O(n²)，但若必须返回所有原始下标，要保存值与原下标映射并处理重复元素身份，输出量最坏 O(n³)，不能承诺整体 O(n²)。现场应先问计数/枚举、重复值与索引要求；本题保留为变式说明，不新增未经确认的力扣编号。
