## 1. 从退出页面后仍占内存寻找真正的问题

用户关闭图片页，Activity 不再可见，内存却没下降。GC 不认识“页面已关闭”这条产品规则，它根据引用与运行时可达性判断对象是否还能被程序使用。如果全局回调仍能到达 Activity，对象就可能继续存活。

```text
长寿命注册表 → listener → Activity → 图片列表 → Bitmap
```

这条链说明为什么手工调用 GC 不能修复泄漏：只要强引用关系仍有效，再扫描也应保留对象。第一步是解除不再需要的拥有关系，而不是要求回收器违背正确性。

本篇区分通用回收思想与 Java 21 HotSpot G1 的具体机制；Android ART 的收集器和内存统计在 [ART](#/article/memory-art) 单独说明，不混用调参。

## 2. 从根集合推导可达性

如果靠引用计数，两对象互相引用但外部已不可达，计数仍可能非零。追踪式 GC 从根集合出发，沿引用边寻找活对象，因此可以识别这种不可达环。

```text
根 R → A → B     C ↔ D
可达：A、B
不可达：C、D（即使互相引用）
```

根包括运行线程执行状态与运行时持有的相关引用等，具体枚举方式依实现。Java 局部变量在源码里还“在作用域内”，不等于每个时刻都必然被视为活引用，优化和活跃性分析会影响实际保留。

对象不可达只是满足相应回收条件，不承诺下一行马上释放，也不适合用 GC 管理必须及时关闭的文件、socket 和锁。资源释放应走明确的 close/finally 协议。

## 3. 标记之后还要决定怎样得到可用空间

标记告诉我们谁活着，回收还要解决空间组织。三种基本方向可以用一排内存理解：

```text
原来：[活A][死][活B][死死][活C]
清扫：保留 A/B/C，释放空洞
整理：把存活对象移到一起，形成连续空闲区
复制：把存活对象复制到另一可用区域，旧区域整体回收
```

清扫避免移动所有活对象，却可能产生碎片；整理改善连续空间但需要更新引用；复制对低存活率区域很高效，却需要可用目标空间。实际收集器组合这些思想，并有并发、安全点和屏障等协议，不能只凭三个算法名判断暂停时间。

对象移动后，程序引用必须仍指向正确对象；这也是 GC 与执行器要协作，而不是后台线程任意 memcpy 的原因。JNI 等跨语言引用同样要遵守运行时契约。

## 4. 分代为何能减少扫描，又增加了什么维护

很多负载中，大量临时对象很快死亡。若每次分配压力都扫描整个长寿命对象图，工作量过大，因此分代设计倾向于更频繁回收年轻对象，较少处理长寿命区域。这是经验性负载特征，不保证每个程序都符合。

但老对象可以指向年轻对象：只从年轻区内部扫描，会漏掉活引用。于是需要维护跨区域引用信息。写屏障在相关引用写入时执行额外逻辑，卡表/记忆集等结构帮助收集时找到应考虑的外部引用。

```text
oldOwner.child = youngObject
       ↓ 相应写屏障
记录“这个范围可能出现跨代引用”
年轻区回收时检查相关记录，而不是无条件扫描整个老年代
```

代价从一次完整扫描转移为写入时维护和回收时处理记录。屏障不是 JMM volatile 的同义词，两者解决不同约束。

## 5. 并发标记必须处理对象图正在变化

收集器扫描 A 时，业务线程可能把引用从 B 移到 C。若没有额外协议，收集器可能漏掉仍然活的对象。因此“边运行边标记”不只是给标记线程换个调度器。

三色模型把未发现、已发现待扫描和已扫描对象区分开；图变化可能破坏标记不变量。不同收集器用快照式记录、增量更新或其他屏障策略修复，不能把一种方案描述为所有 GC 的统一实现。

以 G1 为例，其并发标记采用 SATB 相关思想，记录必要旧引用以维持标记视图。它可能保留在本轮过程中才变成垃圾的对象到后续回收，这不必然是泄漏。具体机制见 [G1 文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)。

## 6. 并发不等于没有暂停

应用与 GC 并发执行仍需在某些阶段协调一致状态；搬迁、根处理和元数据转换的暂停策略依收集器而异。并行指多个 GC 工作线程同时做事，并发指 GC 与应用同时推进，两词不能互换。

```text
吞吐：一定时间里应用完成多少工作
延迟：单次暂停和用户请求尾部有多长
内存：为并发与复制保留多少空间
CPU：屏障、标记、迁移消耗多少执行资源
```

压短暂停可能需要更多并发 CPU 或内存余量；省内存也可能让收集更频繁。一次 GC 暂停不长，应用仍可能因分配慢路径或 CPU 竞争卡顿。不能只统计日志中最长 pause 就宣布无问题。

## 7. 用 G1 的区域模型解释失败边界

G1 将堆组织为多个 region，并在收集周期中选择相应区域进行回收与搬迁。它尝试满足暂停目标，但目标不是硬实时承诺。

假设源区域有大量活对象，搬迁需要足够目标空间；若堆过满、分配太快或存活集过大，系统就更难在有限余量内完成回收。某些大对象还有特定区域安排，不能只看“总空闲字节”就断言某次分配一定可满足。

处理顺序应先找持续保留、分配速率和峰值并发，再评估堆与收集器参数。盲目增大堆可能降低频率，却增加驻留和某些处理成本；选择低延迟收集器也不能消除业务无限保留对象。

## 8. 引用类型不是资源清理的万能开关

WeakReference 允许在只剩相应弱可达关系时回收目标，但不会自动取消监听或清理业务注册。SoftReference 的保留受实现与压力影响，不适合承诺缓存容量或命中率。PhantomReference/引用队列可参与特定清理协议，也不是让任意资源及时结束的保证。

引用可达性与通知契约可查 [Java 21 java.lang.ref](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ref/package-summary.html)。缓存更适合有明确容量、淘汰和拥有关系；文件等资源使用显式关闭。用弱引用掩盖 Activity 泄漏可能让回调悄悄丢失，根因仍是生命周期协议没有定义。

## 9. 从曲线区分泄漏、抖动与峰值

重复进入退出图片页，观察每轮静稳后的存活基线：持续抬高值得查保留链；基线稳定但每轮高频分配/回收，可能是抖动；只在解码瞬间超限，则可能是峰值。三类原因需要不同改动。

收集 GC 事件、分配速率、存活集、暂停、进程内存和具体引用路径。堆 dump 本身会改变现场，单份最大的对象也未必是最应删除的拥有者；结合对照轮次分析。进一步看 [OOM 诊断](#/article/oom-diagnosis)。本文没有运行 GC 实验，图示为机制模型，不伪造回收收益。
