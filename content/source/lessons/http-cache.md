## 1. 从一份文章详情建立缓存身份

用户反复打开同一篇文章，响应正文没有变化，每次仍下载数十 KB。最简单的本地 Map 可以省流量，但立即遇到三个问题：保存的是什么版本、还能不能直接用、不同用户是否可以共用。HTTP 缓存把这些约束放进响应元数据与验证协议，而不是只有一个“开启缓存”按钮。

先用公开文章说明，不涉及登录：

```http
HTTP/1.1 200 OK
Date: Mon, 16 Nov 2026 00:00:00 GMT
Cache-Control: max-age=60
ETag: "article-v7"
Vary: Accept-Language

{"title":"Snapshot","version":7}
```

URL 标识资源，Vary 说明选择响应还依赖哪些请求头。同一 URL 的中文和英文表示不能简单共用；ETag 是服务端给这个表示的验证器，不要求它一定是内容 MD5，也不应由客户端猜测。缓存本身还受请求方法、状态码与可存储性规则限制，不能看见 max-age 就忽略所有其他条件。

不用 HTTP 缓存也可以在数据库保存业务模型，但应用必须自己定义版本、权限、过期与同步规则。两层可以共存：HTTP 缓存复用表示，业务离线库表达用户可读取的数据事实，详见 [离线架构](#/article/offline-data)。

## 2. 新鲜度是年龄比较，不是从收到时重新计时

第一次接收后 20 秒再请求，是否可以直接用？要比较 freshness lifetime 与 current age。max-age=60 给出一个新鲜寿命，不保证每个缓存收到它时都还剩完整 60 秒。

简化算例：上游缓存返回 `Age: 40`，本地又放了 15 秒，在忽略其他时钟校正和网络延迟的前提下，当前年龄至少约 55 秒，仍在 60 秒范围内；再过 10 秒就过期。真实算法还使用 Date、请求/响应时间与 Age 修正，不能把这个简化算式当完整 RFC 算法。

```text
可直接复用的候选
 → 请求/响应允许存储与复用
 → 缓存键和 Vary 匹配
 → 当前年龄仍在新鲜寿命内
 → 没有其他要求验证的指令
```

为什么要保留年龄而不每层重置？否则响应从代理 A 到 B 再到手机，每层都重新延长一分钟，陈旧数据就可能无限续命。相关规则以 [RFC 9111 的新鲜度与年龄计算](https://www.rfc-editor.org/rfc/rfc9111#section-4.2) 为准。

`no-cache` 的意思也不是“不能存”。它要求满足相应验证条件后才能复用；`no-store` 才是禁止按该指令存储相应请求/响应。它们是协议约束，不是清除历史所有副本的魔法。

## 3. 过期后用验证器避免重传正文

过期不意味着内容必然变化。客户端已经有 v7，只需要问服务器“还是这一份吗”：

```http
GET /articles/42 HTTP/1.1
If-None-Match: "article-v7"
Accept-Language: zh-CN
```

若所选表示仍匹配，服务端可返回 304，并携带相关更新元数据。缓存把这次验证结果与已有正文结合使用，不应把 304 当成一个空文章覆盖数据库。

```text
本地 v7 + 条件请求
  ├─ 304：复用旧正文，按规则更新元数据
  └─ 200 v8：保存新正文和验证器
```

Last-Modified/If-Modified-Since 是另一组验证方式；时间精度和服务端生成策略会影响能力。ETag 也有强弱区别，弱验证器可以表达语义等价，却不满足所有要求字节一致的用途，范围请求尤其不能随便混用。条件语义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-13)。

条件请求仍要走网络，验证仍匹配时节省的是正文传输而非全部往返。若访问频繁且允许短时间陈旧，合理 freshness 可进一步省请求；若数据必须每次核验，则要接受往返成本，不能两者都无限要求。

## 4. 账号隔离不能只靠 URL

把例子换成 `/me/profile`，A 登出后 B 登录，URL 不变。若应用自制 Map 只按 URL 缓存，B 可能看见 A 的资料。HTTP 协议对共享缓存、Authorization 和 private 有相应规则，但不替应用解决所有本地账号状态归属。

首先区分共享代理缓存与用户私有缓存。`private` 限制共享缓存存储，不代表响应已经加密，也不保证应用切账号时自动清掉旧数据。业务缓存要有账号命名空间、数据权限版本和明确退出清理；不宜直接把完整 token 写进磁盘路径或日志。

```text
应用业务缓存键示意：
(accountId, permissionVersion, resourceId, locale)

HTTP 表示缓存：按客户端实现与 HTTP 规则管理
登录态变化：重新判断哪些响应允许复用，哪些业务副本需要失效
```

“统一给所有请求加一分钟缓存”会把只读公开文章和敏感账户数据混在一起。反过来，一律 no-store 可能损失离线和性能能力。评审按数据类别定义可保存性、读权限与最大可接受陈旧时间，再选择机制。

## 5. 离线旧数据必须表达陈旧性与适用条件

网络断开后，缓存过期但用户仍想看文章。可以设计允许展示旧副本的离线策略，但这不等于客户端能无条件违反响应的验证要求，也不等于旧库存可以继续作为下单依据。

把“最后同步于何时”作为 UI 数据的一部分，比把所有缓存都当最新更诚实。公开阅读内容可能接受陈旧展示；权限撤销后的文档、支付状态和交易限额可能需要更严格策略。协议允许的 stale 行为与业务离线副本是不同层，应分别记录。

验证用一个可控服务器依次返回：v7/60秒、304、新v8、语言变化、切账号、无网络。断言正文、元数据、隔离和是否发出条件请求，不只看命中率。本文未执行该实验；命中率高也可能是错误复用。客户端缓存链位置见 [OkHttp](#/article/okhttp-chain?section=2)。
