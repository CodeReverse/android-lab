## 1. 生成代码的常见失效

模型能写出语法正确的代码，不代表理解业务约束、依赖版本或并发边界。工程师仍需把目标写成可验证行为：输入输出、异常路径、兼容范围、性能预算和不可破坏的不变量。给出相邻实现、接口定义和失败用例，比粘贴整个仓库更容易提供有效上下文。

常见问题包括调用不存在的 API、用旧版本示例、绕过错误处理、扩大修改范围、修改测试以迎合错误实现、遗漏取消与资源释放。识别问题后，应记录“缺失什么上下文／验证器为什么没拦住”，而不只把原因归为“模型不够强”。

## 2. 静态检查与独立判据

静态检查与类型检查捕捉接口和类型问题；构建验证依赖与集成；单元测试覆盖局部逻辑；集成测试覆盖存储、网络与组件约定；关键路径用端到端或真实设备检查。并发、性能和安全还需要专门场景，不是所有问题都能由普通测试发现。

生成实现和生成测试如果来自同一个错误假设，二者一起通过仍可能错。应从业务规格、历史故障和独立 oracle 设计测试；必要时使用性质测试或差分测试。例如序列化往返可测不变量，但不能单靠同一实现的编码／解码互相证明符合外部协议。

## 3. 审查精度与严重漏报

审查模型通常只输出“可能有问题”，要评价其可操作性和真实缺陷命中。定义 defect 级别，构造包含真实历史缺陷、无缺陷变更与边界变更的集合，人工复核结论。precision 是报告里真缺陷比例；recall 是已知缺陷被发现比例。大量泛泛建议可能提高评论数量，却降低用户信任。

评测应统计严重缺陷漏报、误报、定位是否准确、修复建议是否可行、审查耗时和每个有效发现成本。按代码库与时间隔离，避免训练或提示中出现同一个历史 PR 的答案。只有被验证的缺陷计入命中，不能把“这行值得注意”都算正确。

## 4. 代码 Agent 的权限

Agent 需要编译、运行测试和读取项目，但不应因此获得所有网络、凭据和生产写权限。按任务创建隔离工作目录，明确可执行命令与资源，保留变更 diff 和工具日志。仓库文档、Issue 内容和测试输出可能包含恶意指令，应作为数据处理，不得自动升级为系统权限。

对安装依赖、外部发送、生产变更设置与风险相称的控制。不是每次读文件都要人工确认，也不能因为模型宣称测试通过就相信：要保存真实命令、退出状态与相关输出，区分未执行、执行失败和通过。

## 5. 长任务的进度恢复

长任务需要可恢复的进度记录、已完成的变更、失败证据和下一步验证目标。上下文摘要写“已尝试什么、得到什么证据”，不要把计划写成完成。每次继续先检查工作区真实状态，避免重复修改或把用户改动覆盖。

若并行处理子任务，需要文件边界、接口契约和集成责任人。并行数量增加不代表速度线性增加，冲突合并与重复上下文有成本。优先并行相互独立、验收明确的任务。

## 6. 提效证据与失败归因

**能保证 AI 审查绝对正确吗？** 不能。应以确定性检查、独立样本和人工责任构成验证链，说明仍可能漏掉哪些缺陷，并给出发现后的回滚与改进机制。

**被问用 AI 写代码踩过什么坑？** 只讲真实发生的案例，按输入约束、错误行为、发现证据、根因和改进组织。若没有正式上线经验，可展示小实验，但要标明实验范围，不能借原帖作者的经历当自己的成果。

**如何衡量提效？** 比较从需求到验收的总周期、返工、缺陷和维护成本，而非只比较生成耗时或代码行数。本文列出的是可执行评估方案，不是已取得的效率收益。
