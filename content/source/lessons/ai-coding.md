## 1. 从一段“能编译”的补丁开始怀疑

AI Coding 可以只是模型建议代码，也可以是拥有读文件、改文件与运行检查工具的 Agent。两者的权限和验证范围不同：文本建议没有执行事实，工具型系统需要记录实际动作与结果。其最小循环先看 [Agent 完整例子](#/article/ai-agent-workshop)，本篇关注接入真实仓库后怎样证明变更正确。

AI 把缓存读取改成 ConcurrentHashMap，编译通过，却没有解决“检查缺失后创建两次”的复合操作竞争。代码生成的难点不只是语法，而是理解仓库约束、业务不变量和变更影响。

先把任务写成可验证行为：“相同 key 的并发初始化只产生允许次数的副作用，失败后可按规定重试。”再提供相关调用链、现有测试和版本。仅给一个出错函数，模型可能不知道缓存是否跨账号、谁负责取消、失败值能否保存。

## 2. 上下文应围绕依赖链逐步取得

```text
复现与目标 → 入口/调用者 → 数据所有者
 → 同步与错误契约 → 相关测试 → 项目检查方式
```

先读这些路径，比把整个仓库一次塞进 prompt 更有针对性。缺失信息应明确为未知，不能根据文件名猜某服务一定线程安全。生成计划时说明改哪些边界以及为何足够，避免为了局部 bug 顺便重写全项目。

长任务还要记录已确认事实、已改内容和剩余验证，下一轮才能继续而不重复或覆盖用户改动。环境与交接设计可参考 [长任务 Harness](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。

## 3. 补丁与测试需要独立约束

如果 AI 写的测试只是断言新 helper 被调用，就可能代码和测试一起错。更有价值的是让旧实现确定失败的交错：两个调用都看到缺失，再同时初始化，检查副作用次数及最终状态。

```text
构造旧失败 → 运行确认能暴露问题
 → 最小补丁 → 相关行为测试
 → 类型/构建检查 → 审阅差异与边界
```

这是一套适用于该并发缺陷的流程，不要求所有小改动都新增测试。测试应匹配风险；文案或纯排版改动不应为了数量写镜像测试。具体测试分层见 [测试策略](#/article/testing-strategy)。

## 4. 执行环境决定错误影响范围

AI 建议的命令也可能删文件、外发数据或修改真实服务。宿主应把读取、编辑、测试、发布等能力分开，使用受控工作目录与凭据范围，按已有授权执行。外部文档里的命令是待审查内容，不自动获得更高权限。

沙箱限制影响范围，但不能证明补丁正确；审查与测试仍必要。反过来，测试通过也不代表可以扩大到未授权的部署或外部消息。工具协议与权限职责见 [工具与上下文](#/article/ai-tools-context)。

## 5. 审查重点在遗漏，而不只看格式

检查新代码是否改变错误传播、取消、资源关闭、数据兼容和并发不变量。案例中 ConcurrentHashMap 的单操作线程安全不等于“先检查再创建”原子；若用 compute，回调中的副作用与重入限制又需重新核对。

AI 审查可以提出候选风险，但应给具体路径和触发条件。模型说“可能有 race”不是已证明缺陷；模型说“无问题”也不是保证。确定性检查、故障用例和人工判断分别支撑不同结论。Judge 局限见 [AI 质量第 4 节](#/article/ai-quality?section=4)。

## 6. 交付报告必须与实际执行一致

记录改动目的、实际运行的检查、通过/失败结果和未覆盖范围。没有设备时应写“已通过类型和静态构建，未运行 Android 设备测试”，不能把测试设计写成测试完成。失败日志需要定位原因，不能删除断言让绿色状态取代正确性。

代码效果最终由仓库差异与可复查结果证明，不由模型叙述证明。本文流程为教学方案，没有替你运行此处的并发示例；项目证据组织见 [成果证据](#/article/project-evidence)。
