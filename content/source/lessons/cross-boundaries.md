## 1. JSBridge 协议与关联字段

JSBridge 连接 Web 内容与宿主能力。请求至少需要明确 method、requestId、协议版本、参数结构和上下文；响应需要区分成功、业务失败、协议错误与取消。对副作用操作，requestId 的关联能力不自动等于幂等能力，还需服务端或宿主实现去重规则。

协议应定义超时后回调如何处理、页面销毁时怎样清理挂起请求、重复响应是否忽略。否则新页面可能接收到旧页面回调，或者原生回调表长期持有已销毁 WebView。

## 2. 内容来源与信任边界

addJavascriptInterface 暴露的能力可被 WebView 中脚本访问，其安全边界不能只靠“我们自己的 H5 不会乱调用”。页面导航、iframe、第三方脚本和内容注入都会改变风险。对敏感能力，应限制可信来源、减少暴露面、校验参数并在宿主执行真实授权。

域名 allowlist 必须用规范解析后的 host 精确匹配或明确子域规则，不能简单 contains。file、content、自定义 scheme 和重定向也要有策略。只检查首次加载 URL，不足以覆盖后续导航。对于支持来源约束的消息通道，仍应按 API 契约验证来源，不能把任意消息当作可信命令。

## 3. 线程、取消与生命周期

桥接回调未必运行在 UI 线程。访问 View 要切到合适线程，但耗时工作又不能堵住该线程。页面离开时取消页面归属任务并移除监听；需要跨页面持续的任务应由应用级组件拥有，通过可查询状态重新关联。

可为每次页面实例生成 generation，响应返回时同时校验 requestId 和 generation。它能拒绝旧页面结果，但不能撤销已经执行的支付或上传。传输取消、界面丢弃和业务撤销必须分别定义。

## 4. 能力协商与版本兼容

新 H5 在旧 App 中可能调用不存在的方法。宿主提供能力集合和协议版本，Web 侧根据能力选择降级路径；新字段允许向后兼容，破坏性改变采用新能力或新版本。协议测试应同时覆盖新 Web/旧宿主与旧 Web/新宿主。

动态内容发布还需要灰度、异常监控和可回滚资源。回退页面代码不等于回滚本地数据库升级，因此数据变更必须考虑双版本共存。跨端框架中的 Flutter Channel、RN Module 也面临类似协议边界，只是实现工具不同。

## 5. 断连、异常与重复回调验证

覆盖非可信 iframe、跳转后调用、非法参数、超大消息、重复 requestId、超时后回调、页面销毁和版本不兼容。安全与可靠性测试应验证具体能力边界，而不只测“JS 能调用 Android 方法”。
