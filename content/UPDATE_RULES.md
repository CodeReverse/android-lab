# 面经更新、文章生成与发布

## 使用入口

网站左侧“内容更新”进入更新中心。GitHub Pages 不保存管理员凭据，实际的仓库操作在 GitHub 登录后通过 Actions 执行；网站按钮会打开工作流，不会假装在浏览器后台抓取网站。

工作流 **Research and update interviews** 的 Run workflow 参数：

| operation | 行为 |
| --- | --- |
| check_model | 独立验证模型鉴权与 JSON 输出，无需来源页面；只发出一次简短请求 |
| refresh | 检索新面经、核验来源、生成文章草稿；source_url 可指定一个原帖 |
| enable_auto | 开启每周一北京时间 10:17 的后台检索生成 |
| disable_auto | 关闭自动任务，保留手动更新 |
| publish | 核验后发布 draft_id 指定的草稿，不覆盖任何已有 ID |

自动任务默认关闭；GitHub 调度可能排队，公开仓库长期无活动时 GitHub 可能暂停计划任务，届时在 Actions 恢复。即使网页关闭，已开启的仓库任务仍会执行。更新中心另有“每 30 分钟检查已发布版本”，只负责提示刷新，与自动面经检索独立。

## 模型和搜索配置

仓库 Settings → Secrets and variables → Actions：

- Secret `ARTICLE_AI_KEY`：模型服务 API Key。默认接口 `https://api.deepseek.com/chat/completions`，模型 `deepseek-flash`。
- 可选 Variables `ARTICLE_AI_ENDPOINT` 和 `ARTICLE_AI_MODEL`：替换为兼容 Chat Completions + JSON object 输出的接口完整地址和模型名。
- 可选 Secret `SEARCH_API_KEY`：Tavily 检索 Key。缺省使用公开 Bing RSS；它可能返回无关或不完整结果，会严格按来源域名过滤，不把无结果说成“行业没有新面经”。

配置 Secret 后先运行 `check_model`，成功仅表示模型接口可用，不代表面经来源可读或文章事实已核验。DeepSeek 接口明确使用非思考模式，以保留正文输出额度；其他兼容接口不发送此专用参数。

调用模型和搜索可能计费，每次最多生成两篇草稿（配置上限为三篇）。没有模型密钥时仍可检索和提取网页；来源保留为等待配置，不编造正文。接口失败不输出密钥、完整响应或完整原帖。

更改来源域名、公司、关键词、时间范围和数量只需编辑 `content/update-config.json`，无需更改 UI。分类来自 `content/categories.json`，写作规范来自 `content/ARTICLE_TEMPLATE.md`。自定义分类需先同步到仓库，本地私人分类不用于公共文章。

## 内容规则

1. 面经只收中文互联网公司公开原帖。搜索结果仅用于发现 URL；登录墙、验证码、403、缺少正文均记录原因，不绕过。来源不能读取时不生成文章。
2. URL 去跟踪参数后去重，读取正文后再做哈希去重。已收录原帖、已生成草稿不会重复生成；等待模型和暂时失败的候选可重试。
3. 发布日期只采纳原页面明确元数据；面试日期不得用发布/采集日期替代。日期缺失显示未核验，不宣传为已确认的最新面经；有日期则限制近两年。
4. 同一原帖选择一个主题、最多三个相近问题。模型提取的短证据必须能在正文定位；对用户展示原创问题概述，不整篇转载作者面经或答案。
5. 归类依照知识点的主领域。协程归 Java/Kotlin、AI 归 AI；关联网络调用不代表主分类变成网络。算法题不走自动正文流程，仍须单独核对 LeetCode 中国编号。
6. 生成前检索并读取官方文档、规范或论文。没有可读原理来源就保留候选等待重试。引用只允许使用本次真正取到的资料 URL。
7. 自动生成的是学习文章：用 4–8 个陈述式小节讲清概念、组成、执行、实现和边界，正文控制在 900–3200 字符，避免重复与堆砌。文末附原题简答和 3–5 个复习提问，提问指向正文小节；不能把全文写成问答。真正的面经逐题详解仍保留原题对应答案。精确版本和源码细节需有依据，未知处明确标注。
8. 草稿不是技术审核完成。模型生成与结构验证不能证明事实正确；维护者核验原帖问题、分类、引文支持、版本条件和反例后，再运行 publish 收录。自动任务只产生草稿。
9. 发布生成新的稳定 ID；新增内容不覆盖旧文章或个人数据。需要合并已有主题时，维护者按原文章 ID 和版本规则编辑，不能用生成器覆盖个人收藏关联。

## 审核与修改

`content/updates/drafts/research-….md` 为可读预览；同名 JSON 中 `data` 是可修改的正文结构，`extraction` 是原题归纳，`references` 记录已读取资料。修改 JSON 后运行 publish，脚本会重新渲染 Markdown 并复查结构。修改前核对 URL 与原文，不能把失败资料补成“已验证”。

待发布清单：主题与类别正确；原题概述忠于原帖；答案逐项回应；概念到实现的讲解、反例与验证齐全，文末提炼可回溯正文；引用确实支持机制；未伪造测量、面试日期或行业频率；与现有文章重复时先合并设计。

## 运行、故障和验证

- 更新状态记录于 `content/updates/state.json`，最近 20 次运行留档；网站展示最近 100 个候选。完整候选仍保存在仓库，便于去重。
- 原帖全文与资料全文只用于本次处理，不写入公共仓库；存储 URL、哈希、短证据与原创文章。
- 任务串行执行。结构、分类、引用、目录、类型和构建检查通过后才推送；若有其他提交并发到 main，普通 push 会失败，绝不强推覆盖，重新运行任务即可。
- Actions 使用仓库自动令牌提交内容；由于该令牌的 push 不自动触发其他工作流，更新任务显式触发 Pages 部署。
- 网页渲染使用已有安全 Markdown 路径，模型不拥有工具调用、任意文件路径或脚本执行能力。
- 外网检索/模型实测与离线测试分开。离线测试验证去重、正文识别、拒绝假证据、编号与引用约束；真实生成还取决于配置的模型、搜索质量与来源可读性。

官方接口依据：[DeepSeek 接口](https://api-docs.deepseek.com/)、[JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)、[GitHub 工作流触发规则](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)。
