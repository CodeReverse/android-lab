# 技术正文写作规范：面试官逐层追问

适用：网络、Java/Kotlin、Android、Compose、跨端、AI，以及有明确技术机制的性能、架构和故障专题。路线地图、项目证据与决策说明可以保留适合其目的的结构。

每篇聚焦一个知识点。提问必须有依赖顺序，答案直接写在问题后，不能只增加问题列表。源码、公式和时序应帮助解释行为，而不是堆名词。

## 六层组织方式

1. 定义：是什么、解决什么问题、与相近概念有什么区别。
2. 结构：分为哪些部分、谁持有谁、每部分的职责和状态是什么。
3. 运行：一个具体输入从进入到完成，怎样流经这些部分。
4. 实现：数据结构、算法、同步、内存与源码入口如何支撑上述行为。
5. 边界：什么条件会失败，有哪些反例、版本差异和方案取舍。
6. 证据：怎样实验、采集什么、如何判定根因和改进，什么仍未验证。

六层可以展开成更多问题，不要求每层只有一问。机制复杂时拆成相互链接的文章，不让一篇变成无边界题库。

## 正文格式

```markdown
## 阅读方式与讨论边界

说明规范／运行时／库版本，以及原题证据和原创追问的区别。

## 第 1 问：这个技术是什么，解决什么问题？

给出直接答案和一个可解释的例子。

## 第 2 问：由哪些部分组成，怎样协作？

解释责任、持有关系、调用或数据方向。

## 第 3 问：一次具体操作怎样执行？

用时间线或状态变化回答，不用孤立术语代替过程。
```

继续按顺序写到机制、故障和验证。文章目录由这些标题自动生成，`inquiryCount` 由构建推导，不手填。构建检查编号连续、正文存在、内链有效；这些结构检查不能代替技术准确性核验。

## 深度与事实边界

- 先讲公共契约，再讲明确版本的实现；区分 JVM 规范、HotSpot 和 ART。
- 把“通常”背后的条件讲清楚；给反例，如超时不代表未提交、可见不代表原子、GC 不代表资源及时关闭。
- 原帖用于证明问过什么；论文、规范和官方源码用于核验原理；编辑设计的追问不得伪装成公司原题。
- 来源描述发布时间、面试日期与核验时间，不能用采集时间补造面试年份。
- 没有执行的实验标为设计或推演；例子中的假设数值不能作为个人项目成果。
- 路线与相关链接不改变主分类；文章更新保留稳定 ID，递增 version 并更新 updated。

## 维护入口

正文：`content/source/lessons/`；元数据：`content/articles.json`；路径：`content/learning-paths.json`。AI 原帖范围还记录在 `content/ai-research.json`。执行 `npm run content:sync`、`npm test` 和类型检查后再构建。
