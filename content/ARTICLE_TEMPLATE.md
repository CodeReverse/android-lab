# 学习文章与面经详解的写作规范

## 先区分文章用途

- **学习文章、学习路径知识点及其他非面经技术文章**：正文采用连续讲解，不用问答串、面试官口吻或“第 N 问”。面经仅提供选题线索时仍属于学习文章。
- **明确的面经详解**：保留原题概述、逐题参考答案和事实边界；不把编辑追问冒充公司原题。
- 学习路线是阅读索引，链接到具体文章和小节，不重复整篇教程。

## 学习正文的推进顺序

从一个具体场景和未解决的现象开始，按需要引入概念与职责，用例子追踪执行过程，再让新增约束引出实现机制、失效边界和验证。每一段回答前一步留下的问题，同时为下一步提供理由；用依赖关系推进深度，不以问答数量或篇幅表示深度。

## 教学节奏：场景、例子、解释、递进

先给读者一个可理解的小场景和预期行为，再引入解决它的概念。核心机制至少提供一个完整的教学过程：最小例子 → 解释关键语句与对象职责 → 改变一处写法并推演结果 → 归纳机制与成立条件 → 连接下一层问题。正文标题保持陈述式，不改回问答串。

**过渡要延续思考，而不是宣告下一个知识点。** 每次引入新概念，先让读者看见前一步还没解决的现象或新约束，再给出解决办法，解释其作用，继续检验剩余疑问。比如：普通收藏标记无法被观察 → 引入 mutableStateOf 并解释 MutableState 与 value → 创建位置重新执行会生成新对象 → 引入 remember → 两种职责弄清后再解释 by 的简写。不要一开始就把所有 API 塞进正确代码，再逐项补百科式定义。

正文允许自然的引导问题，如“既然值已经可观察，为什么还需要保留对象？”，随后用代码与推演接着说明；这不是要求恢复“第 N 问／答案”的机械问答格式。过渡可以是一句未解疑问、一个新需求或对照现象，不要每节固定插入“那么问题来了”或重复总结。来源、版本和必要条件保留，但尽量不打断主线。

优先沿同一个例子增加约束，例如收藏按钮 → 两处共享状态 → ViewModel 数据源 → 页面恢复 → Runtime 读写。不要每节换一个无关场景。代码后解释输入、执行、输出和容易误解的行为；只列 API、结论或源码名称不算讲清原理。

代码是帮助推导的内容：标出语言和上下文、必要 import/依赖、示意或可运行的性质。展示错误对照时说明错误条件与预期差异。原理小节给执行链、数据结构或关键源码入口；如果写的是简化模型，明确标为示意，不能冒充原版源码。

**不按固定字数压缩正文。** 长度由讲清当前主题所需的过程决定，不能为了 1000–2500 字或 3200 字符的旧上限删去必要解释。精简对象是重复定义、重复整套页面代码、无关铺垫和空泛总结。合理增加小节和短段落；主题出现独立学习目标时再拆篇，而不是一到字数就切断推导。

正文结束后，读者应能解释例子为何成立、改变条件为何失效、如何迁移到实际项目。文末 3–5 个面试问题用来回顾这些已讲清的机制，不用问题列表补偿缺失的正文。

写作校准参照：[用户指定的 State 范文](https://juejin.cn/post/7399530589987504128)。只参考例子递进和解释节奏，不复制正文代码，也不将其技术说法直接当事实依据；规范与源码仍需独立核验。仓库内样章：`content/source/lessons/compose-state.md`。2026-11-16 本轮实质重写了其余 15 篇 Compose 正文，保留 State 样章；其余 53 篇学习文章尚未按本轮更深入的标准重新逐篇验收，不能从结构检查通过推断已经完成。路线页连接主题与章节入口，不重复整篇教程。

```markdown
## 1. 场景与第一个问题

从具体操作、预期与实际差异出发，引入解决当前问题所需的最少概念。

## 2. 最小例子与逐步解释

承接上一节的未解问题给出代码或操作，解释关键语句与对象职责；改变一个条件，推演结果差异。

## 3. 执行过程与实现机制

沿例子追踪调用、状态或数据，再解释数据结构、算法或同步方式；区分契约与版本实现。

## 4. 边界与验证

给出一个反例以及可观察的证据。没有执行的实验标为验证设计。

## 原理资料

列出支持本文机制的资料与版本范围。

## 面试提炼

1. 一个基础概念问题。（回看第 1 节）
2. 一个执行或实现问题。（回看第 2–3 节）
3. 一个反例、取舍或验证问题。（回看第 4 节）
```

文末选 3–5 个问题覆盖基础、机制、边界和验证，不重复正文答案。问题应能从正文找到解释；有原帖选题时，可在末尾另附简短原题对应说明。文末自测不要求开启练习功能。

## 设计理由、替代方案与主题边界

讲机制时必须回答它解决的具体矛盾：不这样设计会怎样，是否能用更简单方式解决，各自付出什么成本。用技术评审或 tech spike 的视角检验必要性，而不是假设采用某个框架机制就是唯一正确答案。替代方案需给成立条件，不能虚构框架作者的历史设计动机。

当前主题必须讲透一个完整执行过程。例如 Snapshot 需要解释版本读取、隔离写入、apply、冲突与观察，不能只列 StateRecord 名称和源码链接。源码引用应固定版本；原创伪代码要标明简化范围。能帮助理解时使用数据结构图、时序、数值计算、最小代码和失败对照，并在其后解释输入、步骤、输出与边界。

后续有专篇的知识点只引入当前所需的概念和作用，再链接对应章节。例如 Recomposer 在 Snapshot 篇先说明协调组合失效，跳转刷新篇继续学习。本站章节地址采用 `#/article/<稳定ID>?section=<编号>`；不猜测不存在的章节。链接不能代替当前主题的必要解释。

## 人工验收标准

- 从首个例子往下读，新术语是否由前一步未解决的问题引出，而不是靠“接下来介绍”拼接目录。
- 读者能否手算一个执行过程，解释改变输入后的差异，而不只是复述结论。
- 设计理由、替代方案、代价、失败条件是否明确；不同机制的职责是否混淆。
- 代码是完整最小例、接入片段还是伪代码，依赖、未展示组件和预期是否说明；未运行不得写成实测。
- 链接有无越界；正文深度是否由编辑逐篇判断。字数、代码块数量、结构校验和自动评分都不能作为“已经讲透”的证明。

## 深度与事实边界

- 先讲公共契约，再讲固定版本的实现；区分 JVM 规范、HotSpot 和 ART。
- 保留成立条件和反例，如超时不代表未提交、可见不代表原子。精简不能删掉关键条件。
- 原帖证明问过什么；官方资料、规范和论文支持机制。没有确认的源码细节应标明待核验。
- 区分发布时间、面试日期和采集时间；不推断未经样本支持的行业频率。
- 没有执行的实验不能写成实测成果；技术更新保留 ID，递增 version，更新 updated。

## 构建与维护

正文在 `content/source/lessons/`，元数据在 `content/articles.json`，路径在 `content/learning-paths.json`。构建推导 `sectionCount` 和 `reviewCount`，检查小节顺序、文末自测与路径定位；结构通过不代表事实核验完成。明确面经的 `questionCount` 维持独立统计。

执行 `npm run content:sync`、`npm test`、类型检查与构建。人工核验内容后再发布。
