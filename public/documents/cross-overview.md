初始核心：WebView/H5 + JSBridge、Flutter、React Native、KMP、Compose Multiplatform。原生作为对照；Hippy、Lynx、Kuikly 等国内框架作为可扩展专题。新增技术使用同一模板，不重新设计全部目录。

## 2. 先区分比较层次

- **JSBridge 是通信机制**，应将“WebView/H5 + JSBridge”作为完整候选路线；不能把它与完整 UI 框架当作同一层级组件。
- **KMP 主要提供共享代码的基础**，UI 可以保留各端原生，也可以选择共享；**Compose Multiplatform 是共享 UI 的一种选择**，两种选型分别评估。
- **使用 React 语法不等于 React Native**；Hippy、Lynx 等的渲染、线程和原生互操作需按各自实现分析。
- **跨端、动态化、服务端驱动 UI 是不同能力**。能复用代码不自动意味着任意业务逻辑都可在线发布；开发期热重载也不等于生产热更新。

机制依据：[Android WebView 文档](https://developer.android.com/develop/ui/views/layout/webapps/webview?hl=zh-cn)、[KMP 概览](https://kotlinlang.org/docs/multiplatform/kmp-overview.html)、[React Native 架构](https://reactnative.dev/architecture/landing-page)、[Flutter 架构](https://docs.flutter.cn/resources/architectural-overview/)。

## 3. 第一层比较：优点、代价和适用场景

下表的适用场景与风险是基于机制的工程判断，不是通用性能排名；实际表现需用相同业务、版本、设备与构建条件验证。

| 路线 | 主要复用与运行方式 | 主要优势 | 主要成本/边界 | 优先评估的场景 |
| --- | --- | --- | --- | --- |
| Android/iOS 原生 | 各端 UI 与平台能力分别实现，可另共享协议或底层库 | 平台集成直接，各端体验可独立打磨 | 双端重复建设与行为一致性治理 | 平台交互密集、已有成熟原生资产、关键能力强依赖系统 |
| WebView/H5 + JSBridge | Web 内容在浏览器内核中渲染，桥接访问受控原生能力 | Web 资产复用、内容更新灵活、易跨入口投放 | 启动/资源加载、内核差异、复杂交互、桥接安全和生命周期 | 运营活动、内容展示、表单，以及已有 Web 业务的移动承载 |
| Flutter | Dart 逻辑与 UI 复用，框架及引擎负责主要 UI 绘制，平台能力经集成层接入 | 统一设计与自定义 UI 能力，逻辑和界面可一起共享 | 引擎与包体成本、启动、平台视图混合、插件与团队 Dart 能力 | 统一品牌界面、中重度自定义 UI、可以逐页引入的业务 |
| React Native | JS/TS 与 React 共享逻辑和组件描述，原生组件与平台模块参与实现 | 可利用 React 团队能力，支持渐进接入与平台扩展 | JS 计算、线程边界、原生模块、升级及双端组件差异 | React 人员和资产较多、业务页面复用、已有原生 App 的局部模块 |
| KMP 共享逻辑 + 原生 UI | 共享业务规则、数据层或 SDK，使用平台后端编译，UI 各端实现 | 逻辑复用和平台 UI 可独立选择，适合小模块渐进引入 | 仍维护多套 UI；Swift 互操作、库支持、构建调试、并发边界 | 网络/数据/规则/SDK 重复多，且要保留原生 UI 的成熟项目 |
| KMP + Compose Multiplatform | 在 KMP 上进一步共享声明式 UI；渲染与互操作按目标平台区分 | Kotlin 与 Compose 经验复用，共享范围可延伸到 UI | 各平台组件和生态成熟度、文本输入/无障碍/平台视图、迁移与性能验证 | Kotlin 团队主导、希望共享 UI、能验证目标平台体验的项目 |

技术路线依据分别见 [WebView](https://developer.android.com/develop/ui/views/layout/webapps/webview?hl=zh-cn)、[Flutter](https://docs.flutter.cn/resources/architectural-overview/)、[RN](https://reactnative.dev/architecture/landing-page)、[KMP 与 CMP 的区别](https://kotlinlang.org/multiplatform/)。RN 必须注明新旧架构，不能把旧 Bridge 的序列化模型当作所有版本现状；KMP/CMP 也不能把 Android 单端行为机械套到其他平台。

国内扩展框架另设技术卡：Hippy 关注前端开发模型和多种渲染路线；Lynx 关注运行、渲染与平台集成；Kuikly 关注 KMP 基础上的 UI/逻辑复用及动态化设计。不能因都支持跨端就假设三者与 RN 或 CMP 相同。[Hippy 官方仓库](https://github.com/Tencent/Hippy)、[Lynx 官方文档](https://lynxjs.org/next/zh/guide/start/build-with-app-framework.html)、[Kuikly 官方仓库](https://github.com/Tencent-TDS/KuiklyUI)

## 4. 第二层比较：资深面试需要展开的维度

| 维度 | 每种技术必须回答 | 应准备的证据或验证 |
| --- | --- | --- |
| 复用边界 | 共享 UI、业务逻辑、数据还是基础设施？平台差异放哪里？ | 模块依赖图、共享/平台代码的职责，不只看代码行比例 |
| 运行与渲染 | 哪个线程做计算、布局、绘制？谁持有 UI 节点？ | 一次交互到成帧的时序图 |
| 原生通信 | 编解码、调用频率、复制、调度、异步与取消是什么关系？ | 高频与大数据场景的成本拆解 |
| 生命周期 | 页面、引擎、宿主、任务、插件资源分别由谁释放？ | 页面退出、进程恢复、回调竞争的状态图 |
| 体验与系统能力 | 输入法、无障碍、手势、地图/视频、系统新特性怎样适配？ | 真机体验矩阵与平台差异清单 |
| 性能与资源 | 首次启动、首屏、帧耗时、内存、包体、功耗的成本在哪里？ | 相同负载与条件的基线，说明缓存/预热和测试开销 |
| 发布与动态化 | 改逻辑、改 UI、加原生能力分别怎样发布？ | 版本协议、灰度、失败回退、最低宿主版本；动态能力需逐项确认 |
| 工程化 | 日志和崩溃如何关联多语言栈？如何测试、调试、升级？ | 诊断链路、符号/映射文件、组件兼容矩阵 |
| 团队与长期成本 | 谁有平台与框架能力？插件和基础设施谁维护？ | 培训、招聘、排障、升级、协作与退出成本 |
| 迁移与治理 | 一次替换还是逐页迁移？失败是否可退回？ | 试点范围、质量门槛、责任人、回滚方案 |

比较页面支持只选择两三种技术，也支持只看某平台或维度；一个技术卡被多个比较引用，避免分别维护矛盾描述。未知数据直接标未知；没有同条件实验不显示“性能第一”等绝对排名。

## 5. 场景选型：从约束推出候选方案

以下是教学场景，不是某公司的真实决策记录。

| 业务约束 | 可优先比较的方案 | 决定前必须解决的问题 |
| 多入口运营活动，已有 Web 团队，快速迭代 | H5/JSBridge 与现有动态容器 | 首屏、离线资源、登录权限、桥接能力、失败降级 |
| 多端统一视觉，有较多自定义绘制和动画 | Flutter、CMP 与原生基线 | 低端机帧耗时、文本/输入/无障碍、原生视图互操作、包体与启动 |
| React 业务资产较多，向既有原生 App 接入页面 | RN 与现有前端跨端容器 | 原生模块兼容、线程瓶颈、引擎复用、升级和平台差异成本 |
| Android/iOS UI 已成熟，重复问题主要在规则和数据层 | KMP 共享逻辑与保持现状 | 可共享边界、Swift 接口、异步/错误模型、平台依赖替换 |
| 相机、音视频或系统交互是核心 | 原生关键链路 + 跨端业务外层的混合方案 | 高频跨边界成本、资源所有权、延迟预算；不等于一律不能跨端 |
| 大型 App 已有多种容器，新业务希望统一 | 复用现有平台、逐步收敛或局部新增方案 | 平台治理收益是否足以覆盖双轨维护；避免仅为技术统一而迁移 |

一次选型至少交付：约束与非目标、两三个候选方案、核心假设、最小验证、收益和全周期成本、接入边界、退出条件。量化比较只有在权重由业务约束决定且数据可追溯时才有意义；不预设一个所有场景都适用的框架总分。

## 7. 面试时如何形成更高层次的总结

### 90 秒回答结构

“我会先明确要复用的是 UI 还是业务逻辑，以及团队、平台体验和发布节奏的约束。WebView 方案利用 Web 资产；Flutter 和 RN 可以共享较多业务页面，但运行、渲染和平台集成成本不同；KMP 可以从共享逻辑开始，是否共享 UI 是进一步决策。大 App 的实际采用应落实到业务模块，成熟的跨端建设还包括容器、监控、兼容和回滚。因此我会用同一业务试点验证关键假设，再决定采用范围。”

这是表达模板，不是固定标准答案。随后选择一个资料范围准确的行业案例，再结合自己的真实经历说明取舍。

### 逐层追问

1. **概念层**：为什么 KMP 与 Flutter 不能只比较一个“性能”分数？JSBridge 在方案中负责哪一层？
2. **机制层**：同样点击一个按钮，这几种技术的逻辑、布局、绘制分别在哪执行？
3. **成本层**：消除了旧式桥接编解码，为什么仍不意味着跨语言调用零成本？
4. **诊断层**：列表卡顿到底来自 JS/Dart/Kotlin 计算、布局、图像还是平台互操作，如何区分？
5. **决策层**：已有原生双端团队为何仍要迁移？如果不迁移，还有什么办法解决重复劳动？
6. **演进层**：怎样选择试点、定义停止条件、避免长期维护多个容器却没有收益？
7. **证据层**：复用率提高是否等于研发效率提高？如何纳入测试、适配、排障和基础设施投入？
8. **组织层**：框架团队与业务团队如何分工？谁承担长期升级和兼容成本？
